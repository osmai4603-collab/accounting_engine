# مهارة سلامة التنفيذ

## 1. الغرض وحدود المسؤولية

تضمن هذه المهارة أن تنفيذ التغييرات البرمجية يتم بطريقة تحافظ على حالة المستودع وبيانات المشروع، وتمنع فقدان تعديلات سابقة، وتكشف المخاطر قبل تنفيذها، وتنتج أدلة تحقق موثوقة.

وهي مسؤولة عن:

- فحص المستودع وGit قبل التعديل.
- حماية تعديلات المستخدم والتغييرات السابقة غير المرتبطة بالمهمة.
- الالتزام بنطاق المهمة وملكية الملفات.
- ضبط التنفيذ المتوازي ومنع الكتابة المتعارضة.
- التعامل الآمن مع الأوامر والتغييرات الإتلافية.
- حفظ نقاط استعادة قابلة للاستئناف للمهام الطويلة أو عالية المخاطر.
- استعادة العمل بعد انقطاع الوكيل أو الجلسة.
- تحديد جودة الأدلة وربطها بمعايير القبول.
- إجراء تحقق مستقل متناسب مع خطورة التغيير.
- مراجعة الفروق والدمج والنتائج بعد الدمج.
- تسليم سجل أدلة واضح إلى مهارة `execute-plan-lifecycle` عند ارتباط العمل بخطة تنفيذية.

**ليست هذه المهارة مالكة للخطة.** لا تنشئ المراحل أو المهام ولا تعيد ترقيمها ولا تغير حالات المهام أو معايير قبولها ولا تعتمد المراحل ولا تنشئ قرارًا بأن المهمة `منفذة`. هذه مسؤولية مهارة `execute-plan-lifecycle` أو المستخدم. دور هذه المهارة هو تنفيذ العمل بأمان وتقديم أدلة قابلة للمراجعة.

يمكن استخدام هذه المهارة بصورة مستقلة دون ملف خطة. في هذه الحالة يجب أن يكون نطاق المهمة والنتيجة المطلوبة ومعايير التحقق محددة من المستخدم أو من سياق موثوق قبل إجراء أي تعديل.

## 2. متى تُستخدم

استخدمها قبل وأثناء:

- تعديل ملفات مصدر أو إعدادات أو سكربتات بناء.
- إضافة أو إزالة اعتماديات أو تحديثها.
- تغيير مخطط قاعدة البيانات أو بياناتها.
- تنفيذ أوامر Git أو الدمج أو إعادة التأسيس.
- تشغيل عدة وكلاء أو مسارات تنفيذ بالتوازي.
- تنفيذ إصلاحات أمنية أو تغييرات في المصادقة والصلاحيات.
- تعديل منطق مالي أو محاسبي أو معاملات أو أرصدة.
- استئناف عمل بعد انقطاع أو جلسة سابقة غير مكتملة.
- تقييم ما إذا كانت أدلة التنفيذ كافية لإغلاق المهمة.

## 3. مبادئ السلامة غير القابلة للتجاوز

1. **حماية الموجود:** لا تفقد أو تستبدل أو تتجاهل تعديلات المستخدم أو التغييرات السابقة غير المرتبطة بالمهمة.
2. **النطاق أولًا:** لا تعدّل ملفًا أو عقدًا أو سلوكًا خارج النطاق المصرح به. سجل الحاجة إليه واطلب الموافقة أو أنشئ طلب تغيير عبر مهارة دورة حياة الخطة.
3. **لا تخمّن حالة المستودع:** افحص الحالة الفعلية قبل أي تعديل، ولا تفترض أن المستودع نظيف أو أن كل تعديل يعود إلى المهمة الحالية.
4. **لا إجراءات إتلافية دون تفويض صريح ومحدد:** لا تنفذ حذفًا أو استعادة شاملة أو إعادة كتابة للتاريخ أو تغييرًا غير قابل للتراجع لمجرد تسهيل التنفيذ.
5. **لا ادعاء بلا دليل:** لا تقل إن أمرًا أو اختبارًا أو مراجعة أو دمجًا نجح ما لم تنفذه وتتحقق من نتيجته.
6. **التوقف الآمن أفضل من تجاوز الحماية:** إذا تعذر تحديد ملكية التغيير أو أثره أو استعادة الحالة، توقف عن الجزء الخطر وقدم سببًا محددًا.
7. **التراجع محدود:** لا تتراجع إلا عن تغييراتك أنت التي أمكن عزلها بوضوح، ولا تستخدم التراجع لمسح تغييرات سابقة أو مجهولة المصدر.
8. **لا تكشف الأسرار:** لا تطبع مفاتيح أو كلمات مرور أو رموز وصول أو بيانات اعتماد في التقارير أو مخرجات الأوامر. اخفِ القيم الحساسة مع الإبقاء على وصف موضع المشكلة.

## 4. فحص ما قبل التنفيذ (Preflight)

نفّذ الفحوصات التالية قبل تعديل ملفات المشروع:

### 4.1 تثبيت سياق المهمة

1. حدّد المستودع ومجلد العمل والفرع الحالي.
2. اقرأ وصف المهمة ونطاقها ومعايير قبولها واعتمادياتها وملاحظة التوازي إن وجدت.
3. حدّد الملفات والحزم والعقود التي يُسمح بتعديلها، والملفات المشتركة المحظور تعديلها دون تنسيق.
4. حدّد الأوامر المتوقعة للاختبار والبناء والفحص الساكن، بحسب المشروع.
5. إذا لم يكن النطاق أو التفويض واضحًا، لا تبدأ تعديلًا قد يغير سلوك النظام؛ اطلب توضيحًا محددًا.

### 4.2 فحص Git وحالة الملفات

افحص وسجّل، بحسب ما يدعمه المستودع:

- `git status --short --branch`.
- الفرع الحالي وارتباطه بالفرع الأساسي إن كان ذلك معروفًا.
- `git diff` للتغييرات غير المرحّلة.
- `git diff --cached` للتغييرات المرحّلة.
- قائمة الملفات الجديدة وغير المتعقبة.
- آخر commit ذي صلة عند الحاجة لفهم السياق.

صنّف التغييرات الموجودة قبل البدء إلى:

- تغييرات سابقة للمستخدم أو للفريق.
- تغييرات تخص المهمة الحالية.
- تغييرات لا يمكن تحديد مالكها بثقة.

لا تنسب التغييرات الموجودة إلى المهمة الحالية دون دليل. إذا تداخلت تغييرات سابقة مع الملفات المطلوب تعديلها، احتفظ بها وافصل عملك عنها؛ وإذا تعذر الفصل بأمان، توقف واطلب توجيهًا.

### 4.3 خط أساس الاختبارات

1. حدّد الاختبارات أو الفحوصات الأساسية ذات الصلة.
2. شغّل خط الأساس قبل التعديل متى كان ذلك عمليًا وآمنًا.
3. سجّل الاختبارات التي فشلت قبل بدء العمل، ورسائل الفشل الأساسية، والأوامر وبيئة التشغيل.
4. لا تنسب فشلًا سابقًا إلى التغييرات الجديدة، ولا تخفِ فشلًا جديدًا باعتباره سابقًا دون مقارنة فعلية.
5. إذا تعذر تشغيل خط الأساس، وثّق السبب ولا تخترع نتيجة.

### 4.4 بوابة السماح بالتنفيذ

ابدأ التعديل فقط عندما:

- عُرف نطاق المهمة وحدودها.
- فُحصت حالة Git والتغييرات السابقة.
- لا يوجد تعارض غير محلول في ملكية الملفات.
- فُهمت مخاطر التعديل وإمكانية استعادته.
- لا توجد اعتمادية أو موافقة مطلوبة غير مستوفاة بحسب الخطة.

إذا لم تتحقق هذه الشروط، لا تنفذ الجزء المتأثر. قد تواصل أعمالًا أخرى مستقلة وآمنة ضمن النطاق إن كانت موجودة.

## 5. حماية Git والمستودع

### 5.1 أوامر وإجراءات محظورة افتراضيًا

لا تنفذ الإجراءات التالية إلا بعد تفويض صريح من المستخدم يحدد الهدف والنطاق والأثر:

- `git reset --hard`.
- `git clean -fd` أو أي صيغة تحذف ملفات غير متعقبة.
- `git checkout -- .` أو `git restore .` أو أي استعادة جماعية للملفات.
- حذف فرع أو worktree قد يحتوي تغييرات غير مدمجة.
- `git stash drop` أو حذف stash غير معروف الملكية.
- `git push --force` أو إعادة كتابة تاريخ فرع مشترك.
- إعادة تأسيس أو تغيير تاريخ فرع مشترك بطريقة قد تزيل عمل الآخرين.
- حذف مجلدات أو ملفات مشروع على نطاق واسع دون مراجعة دقيقة.

التفويض لا يلغي واجب فحص الأثر والتأكد من أن الإجراء لا يمس بيانات أو تعديلات غير مقصودة.

### 5.2 التعديل المرحلي والالتزام

1. لا تستخدم `git add .` أو `git add -A` بصورة عمياء.
2. افحص قائمة الملفات والتغييرات، ثم أضف المسارات المقصودة فقط.
3. قبل أي commit، راجع `git diff --cached` وتأكد أن كل سطر داخل الالتزام مرتبط بالمهمة ومصرح به.
4. لا تنشئ commit أو تدفعه إلى remote إلا إذا طلب المستخدم ذلك أو كان سير العمل المعتمد يمنح هذا التفويض صراحة.
5. لا تدمج تغييرات أشخاص أو وكلاء آخرين ضمن commit المهمة الحالية دون مراجعة وملكية واضحة.
6. إذا لم يُنشأ commit، لا تخترع معرّفًا؛ سجّل `غير متاح` مع السبب في تقرير التنفيذ.

### 5.3 الأسرار والملفات الحساسة

- لا تضع أسرارًا أو بيانات اعتماد في الكود أو ملفات التوثيق أو سجلات الاختبار.
- لا تعرض محتويات ملفات البيئة أو مفاتيح التوقيع أو كلمات المرور في مخرجات التقرير.
- لا تعدّل ملفات الأسرار أو ملفات الإنتاج الحساسة إلا إذا كان ذلك ضمن النطاق ومصرحًا به.
- انتبه إلى ملفات مثل `.env` وملفات مفاتيح الشهادات وملفات بيانات الإنتاج والنسخ الاحتياطية.

## 6. نطاق التغيير وملكية الملفات

1. أنشئ قائمة واضحة بالمسارات المسموح تعديلها عند وجود تنفيذ متوازٍ.
2. لا تسمح لوكيلين بتعديل الملف نفسه بالتزامن، حتى لو كانا يعملان في فروع منفصلة؛ يمكن أن يحدث التعارض عند الدمج.
3. إذا احتاجت مهمتان إلى ملف مشترك:
   - عيّن منفذًا واحدًا مالكًا للتعديل.
   - اجعل بقية المهام تقدم تغييرات مطلوبة بصيغة محددة بدل تحرير الملف مباشرة.
   - لا تدمج التغيير قبل مراجعة توافقه مع جميع المهام المتأثرة.
4. افحص التبعيات غير المباشرة، مثل العقود العامة والإعدادات المركزية وملفات التسجيل وهجرات قاعدة البيانات وملفات التوليد.
5. إذا كشف التنفيذ أن نطاق المهمة غير كافٍ، لا توسّعه بصمت. وثّق الحاجة وأثرها واطلب تحديث الخطة والموافقة اللازمة.
6. افصل الإصلاحات الجانبية عن المهمة الحالية، ولا تخلطها في التغييرات أو الالتزام نفسه.

## 7. التنفيذ الآمن ونقاط الاستعادة

1. نفّذ تغييرات صغيرة ومتماسكة يمكن مراجعتها.
2. بعد كل وحدة تغيير مهمة، افحص diff واختبر الجزء المتأثر متى أمكن.
3. لا تجمع إعادة هيكلة واسعة وتغيير سلوك حرج وتغيير قاعدة بيانات في دفعة واحدة غير قابلة للفحص.
4. قبل تغيير عالي المخاطر، تحقق من وجود مسار استعادة مناسب، مثل فرع عمل منفصل أو نسخة احتياطية معتمدة أو خطة تراجع موثقة، بحسب طبيعة التغيير.
5. لا تنفذ ترحيلًا يسبب فقد بيانات أو تحويلًا غير قابل للعكس دون فهم أثره وخطة نسخ احتياطي/استعادة وموافقة مناسبة.
6. لا تستخدم بيانات إنتاج حقيقية في الاختبار إلا وفق تفويض وضوابط المشروع. فضّل بيانات اختبار غير حساسة.
7. عند وجود خطوات غير متكررة أو ذات آثار جانبية، سجّل أنها نُفذت حتى لا تعاد تلقائيًا عند الاستئناف.

### 7.1 سجل نقطة الاستعادة الاختياري

للمهام الطويلة أو عالية المخاطر أو متعددة الوكلاء، أو عند توقع انقطاع الجلسة، أنشئ سجل متابعة مؤقتًا في:

`docs/execution/EXEC-<task-id>.md`

لا تنشئه للمهام الصغيرة التي يمكن إكمالها والتحقق منها ضمن جلسة واحدة. لا تستبدل ملفًا موجودًا؛ حدّثه مع الاحتفاظ بالتاريخ المهم.

يحتوي السجل على:

- معرّف المهمة ونطاقها والفرع أو worktree.
- حالة Git عند بدء العمل والتغييرات السابقة التي يجب الحفاظ عليها.
- خطوات التنفيذ المكتملة وغير المكتملة.
- الملفات التي عُدلت وسبب تعديل كل منها.
- الأوامر التي نُفذت ونتائجها الفعلية.
- العمليات ذات الآثار الجانبية التي لا يجوز تكرارها دون فحص.
- المخاطر والعوائق والقرارات المطلوبة.
- نقطة الاستئناف التالية بدقة.

هذا السجل ليس تقرير ARD نهائيًا ولا يجيز تغيير حالة المهمة إلى `منفذة`.

## 8. بروتوكول الاستعادة بعد الانقطاع (Recovery Protocol)

استخدم هذا الإجراء عند بدء جلسة جديدة لمهمة غير مكتملة أو بعد توقف غير متوقع:

1. **لا تبدأ بإعادة تنفيذ الخطوات.** افحص الحالة الفعلية أولًا.
2. اقرأ ملف الخطة وتقرير ARD السابق إن وجد وسجل نقطة الاستعادة `docs/execution/EXEC-<task-id>.md` إن وجد.
3. افحص الفرع وworktree وحالة Git والتغييرات المرحّلة وغير المرحّلة والملفات الجديدة وآخر commits.
4. قارن الحالة الفعلية بما تقوله الخطة وسجل الاستعادة. قد تكون حالة الخطة قديمة أو لم تُحدّث قبل الانقطاع.
5. صنّف كل خطوة إلى:
   - مكتملة بدليل.
   - بدأت لكن لم يثبت اكتمالها.
   - لم تبدأ.
   - غير معروفة الحالة أو ذات أثر جانبي يحتمل التكرار.
6. تحقق من الملفات المتغيرة ومن عدم وجود تعديلات خارج نطاق المهمة أو تعديلات مستخدم يجب الحفاظ عليها.
7. لا تكرر عملية ذات أثر جانبي قبل تحديد ما إذا كانت قد نُفذت بالفعل، خصوصًا: ترحيلات قاعدة البيانات، إنشاء الموارد، إرسال الرسائل، استدعاءات الخدمات الخارجية، إنشاء القيود أو القيود المالية، أو عمليات النشر.
8. إذا كانت إعادة العملية آمنة ومثبتة القابلية للتكرار، واصل من آخر نقطة صحيحة. وإلا توقف واطلب تحققًا أو قرارًا.
9. أعد تشغيل الاختبارات اللازمة لتأكيد الحالة الحالية، ولا تعتمد على نتائج جلسة سابقة إذا تغيرت الملفات أو البيئة.
10. حدّث سجل الاستعادة بنقطة التقدم الجديدة، ثم سلّم الأدلة إلى مهارة دورة حياة الخطة.

لا تستخدم الانقطاع مبررًا لمسح التغييرات أو إعادة المستودع إلى حالة نظيفة قسرًا.

## 9. جودة الأدلة والتحقق من معايير القبول

### 9.1 قاعدة التتبع

يجب أن يقابل كل معيار قبول دليل واضح ومحدد. أنشئ جدول تتبع داخلي أو في سجل الاستعادة/تقرير ARD يتضمن:

| معيار القبول | نوع الدليل المطلوب | الأمر أو الملف أو المراجعة | النتيجة | القيود |
| --- | --- | --- | --- | --- |
| <المعيار> | <اختبار/ساكن/تكامل/مراجعة> | <الدليل المحدد> | محقق/فاشل/لم يُنفذ/متعذر | <الحدود> |

لا تكتفِ بعبارة «الاختبارات نجحت». اذكر الأمر الفعلي والنتيجة وبيئة التشغيل ذات الصلة، بما في ذلك رمز الخروج عندما يكون متاحًا.

### 9.2 أنواع الأدلة

استخدم نوع الدليل المناسب لطبيعة المعيار:

- **دليل تنفيذ مباشر:** تشغيل اختبار أو أمر أو بناء أو ترحيل والتحقق من نتيجته.
- **دليل ساكن:** مراجعة الكود أو المخطط أو الإعدادات أو ناتج أداة تحليل ساكن.
- **دليل تكاملي:** اختبار تفاعل المكونات أو العقود أو قاعدة البيانات أو الخدمات.
- **دليل مراجعة:** مراجعة فنية موثقة من شخص أو وكيل لم ينفذ التغيير محل المراجعة، متى كانت المراجعة المستقلة مطلوبة.

الدليل الواحد لا يثبت تلقائيًا كل المعايير. نجاح البناء لا يثبت صحة منطق الأعمال، ونجاح اختبار وحدة لا يثبت سلامة تكامل قاعدة البيانات.

### 9.3 تصنيف النتيجة

استخدم نتائج صريحة:

- `محقق`: يوجد دليل كافٍ وملائم للمعيار.
- `فاشل`: نُفذ التحقق وفشل.
- `لم يُنفذ`: لم يُشغّل التحقق.
- `متعذر`: تعذر تنفيذه بسبب قيد محدد.
- `غير منطبق`: فقط مع تفسير موثق لعدم انطباق المعيار.

لا تحول `لم يُنفذ` أو `متعذر` إلى `محقق` بالاستنتاج أو بتوقع النتيجة.

### 9.4 المقارنة بخط الأساس

- قارن النتائج بخط الأساس المسجل قبل التعديل.
- ميّز فشلًا سابقًا عن فشل أدخلته التغييرات الجديدة.
- إذا تغيرت البيئة أو التبعيات أو بيانات الاختبار، اذكر ذلك عند تفسير النتائج.
- لا تحذف سجل فشل سابق لمجرد أن محاولة لاحقة نجحت؛ وثّق المحاولتين والنتيجة النهائية.

## 10. المراجعة المستقلة حسب الخطورة

ليست كل مهمة بحاجة إلى مراجع منفصل، لكن يجب أن تتناسب استقلالية التحقق مع أثر الخطأ.

### 10.1 مهام تتطلب تحققًا مستقلًا

اطلب مراجعة مستقلة قبل الإغلاق عندما تمس المهمة واحدًا أو أكثر مما يلي:

- المصادقة أو التفويض أو إدارة الصلاحيات.
- الأمان أو حماية الأسرار أو حدود الثقة.
- مخطط قاعدة البيانات أو ترحيلات البيانات أو حذفها أو تحويلها.
- المعاملات والتزامن والعزل وإعادة المحاولة وIdempotency.
- الأرصدة أو القيود أو الترحيل المحاسبي أو الثوابت المالية.
- عقود API العامة أو التوافق مع الإصدارات السابقة.
- عمليات النشر أو النسخ الاحتياطي أو الاستعادة أو فقد البيانات.
- تغييرات واسعة أو صعبة التراجع أو ذات أثر على عدة مكونات.

### 10.2 شكل المراجعة المستقلة

1. كلّف مراجعًا لم ينفذ التغيير بمراجعة diff والسلوك ومعايير القبول والمخاطر.
2. قدم للمراجع نطاق المهمة والمعايير والأدلة، لا النتيجة التي تريد منه تأكيدها فقط.
3. اطلب منه البحث عن العيوب والآثار الجانبية والحالات الحدية وعدم التوافق، لا مجرد تلخيص التغيير.
4. سجّل هوية/دور المراجع، وما راجعه، والنتيجة، والملاحظات وكيف عولجت.
5. إذا لم تتوفر جهة مستقلة، نفّذ مراجعة ذاتية منفصلة بعد التنفيذ مع التصريح بأنها **مراجعة ذاتية وليست مستقلة**. لا تدّعِ وجود مراجعة مستقلة.
6. لا تغلق المهمة ما دامت ملاحظة حرجة أو عالية الخطورة غير معالجة أو مقبولة صراحة من صاحب القرار.

## 11. قواعد إضافية للمهام الحساسة

### 11.1 قاعدة البيانات والبيانات

- افهم أثر الترحيل على البيانات الحالية، وترتيب تطبيقه، والتوافق بين نسخ التطبيق والمخطط.
- ميّز ترحيلات الإضافة المتوافقة عن التغييرات الكاسرة أو التي تحذف/تعيد كتابة بيانات.
- لا تشغّل ترحيلًا على قاعدة إنتاج أو بيانات فعلية دون تفويض واضح وإجراءات الحماية المعتمدة.
- وثّق خطة التراجع أو الاستعادة وحدودها؛ لا تفترض أن كل ترحيل قابل للعكس.
- اختبر الترحيل على بيئة مناسبة وبيانات غير إنتاجية متى أمكن.

### 11.2 المنطق المالي والمحاسبي

عند تعديل منطق مالي أو محاسبي:

- لا تضعف أو تتجاوز ثوابت التوازن أو صحة القيود أو قواعد الفترة المالية.
- تحقق من الحالات الحدية، الدقة العددية، التقريب، العملات، التزامن، التكرار، والعكس بحسب نطاق التغيير.
- اربط كل ثابت محاسبي باختبار أو دليل مناسب.
- أي تغيير في القواعد المحاسبية أو دلالة القيد أو توقيت الاعتراف أو سلوك الأرصدة يتطلب موافقة صريحة قبل التنفيذ.

### 11.3 التبعيات والأدوات

- افحص أثر إضافة أو تحديث أو حذف اعتماد برمجي على التوافق والأمان والبناء.
- لا تحدّث تبعيات غير مرتبطة بالمهمة لمجرد ظهور تحديث متاح.
- لا تتجاوز سياسات النظام أو ضوابط الأمان لتعطيل فحص أو تشغيل ملف محظور.
- إذا منع النظام تشغيل أداة أو أمرًا، وثّق المنع ولا تحاول الالتفاف على سياسة الحماية.

## 12. مراجعة الدمج وما بعده

قبل الدمج:

1. تأكد من انتهاء العمل المخصص لكل فرع/وكيل وعدم وجود تعديل متزامن على ملف مشترك.
2. افحص `git status` والفروق والملفات المضافة والمحذوفة والتغييرات المرحّلة وغير المرحّلة.
3. افحص تعارضات الدمج وعلامات حل التعارض المتبقية.
4. راجع توافق العقود العامة والإعدادات وترتيب هجرات قاعدة البيانات واعتماديات البناء.
5. تأكد أن الدمج ينفذه مسؤول واحد محدد وأنه لا يضم تغييرات غير مرتبطة.

بعد الدمج:

1. افحص حالة Git والنتيجة الفعلية للدمج.
2. شغّل اختبارات التكامل والانحدار والبناء والفحوصات المتأثرة.
3. افحص الملفات النهائية بعد الدمج، ولا تعتمد على نجاح حل التعارض وحده.
4. إذا فشل التحقق أو ظهرت مشكلة، وثّقها وأوقف إغلاق المهام المتأثرة. لا تُخفِ الفشل بإعادة كتابة السجل.
5. سلّم نتيجة الدمج والاختبارات إلى مهارة `execute-plan-lifecycle` لتحديث المهمة وبوابة المرحلة.

## 13. التعامل مع الفشل والحجب والتراجع

1. إذا فشل اختبار وما زال التحقيق أو الإصلاح ممكنًا، واصل العمل ضمن النطاق؛ لا تصف المهمة بأنها محجوبة لمجرد الفشل.
2. إذا تعذر العمل الآمن بالكامل، توقف عن الجزء المتأثر وحدد:
   - العائق بدقة.
   - ما الذي جُرب ونتيجته.
   - الملفات أو البيانات أو الوظائف المتأثرة.
   - أثر مواصلة التنفيذ دون حل.
   - القرار أو الصلاحية أو المدخل المطلوب.
3. لا تضعف الاختبارات أو تحذف assertions أو توسع الاستثناءات لإجبارها على النجاح دون موافقة ومبرر موثق.
4. لا تتراجع عن تغييرات المستخدم أو التغييرات السابقة.
5. إذا كان التراجع عن تغييرك ضروريًا، اعزل الملفات أو الأسطر التي تملكها، افحص diff قبل وبعد، ووثّق سبب التراجع ونتيجته.
6. إذا تعذر عزل تغييرك عن تغييرات أخرى، لا تنفذ تراجعًا آليًا؛ اطلب تنسيقًا.
7. سلّم وصف العائق إلى مهارة دورة حياة الخطة ليتم تحديث الحالة إلى `محجوبة` عند تحقق تعريف الحجب.

## 14. عقد التسليم إلى مهارة دورة حياة الخطة

عند ارتباط المهمة بخطة، سلّم تقريرًا موجزًا ومنظمًا يتضمن:

1. معرّف المهمة ونطاقها الذي نُفذ.
2. الفرع أو worktree وحالة Git قبل التنفيذ وبعده.
3. الملفات التي أُنشئت أو عُدلت أو حُذفت وسبب كل تغيير.
4. التغييرات السابقة أو غير المرتبطة التي جرى الحفاظ عليها.
5. أوامر الاختبار والبناء والفحص التي نُفذت، والنتيجة الفعلية لكل منها.
6. جدولًا يربط كل معيار قبول بدليله ونتيجته.
7. الاختبارات التي لم تُنفذ أو تعذر تنفيذها وسبب ذلك.
8. نتيجة المراجعة المستقلة أو توضيح أنها مراجعة ذاتية أو غير منطبقة.
9. نتائج فحص الدمج وما بعد الدمج إن وجد.
10. النواقص والمخاطر والقرارات التي تتطلب موافقة.
11. Commit إن أنشئ بتفويض، وإلا `غير متاح` مع السبب.
12. نقطة الاستئناف التالية إذا لم تكتمل المهمة.

لا تحدّث حالة المهمة إلى `منفذة` بنفسك؛ اترك قرار الحالة وإغلاق ARD لمهارة `execute-plan-lifecycle` بعد مراجعة الأدلة واكتمال شروط الإغلاق.

## 15. قائمة تحقق سريعة

- [ ] تم تثبيت سياق المهمة ونطاقها ومعاييرها قبل التعديل.
- [ ] تم فحص Git والفرع والتغييرات المرحّلة وغير المرحّلة والملفات غير المتعقبة.
- [ ] تم الحفاظ على تغييرات المستخدم والعمل السابق.
- [ ] تم تحديد الملفات المسموح تعديلها وملكية الملفات المشتركة.
- [ ] لم تُنفذ أوامر إتلافية دون تفويض صريح ومحدد.
- [ ] لم تُستخدم أوامر staging أو commit بصورة عمياء.
- [ ] تم تسجيل خط أساس الاختبارات أو سبب تعذر تشغيله.
- [ ] تم حفظ نقاط استعادة للمهام الطويلة أو عالية المخاطر عند الحاجة.
- [ ] تم تطبيق بروتوكول الاستعادة قبل إعادة تنفيذ مهمة بعد الانقطاع.
- [ ] لكل معيار قبول دليل مناسب ونتيجة صريحة.
- [ ] تم التمييز بين النجاح والفشل وعدم التنفيذ والتعذر وعدم الانطباق.
- [ ] تم إجراء مراجعة مستقلة للمهام عالية الخطورة أو التصريح بوضوح بعدم توفرها.
- [ ] تم فحص التغييرات والعقود والترحيلات قبل الدمج وبعده.
- [ ] لم يتم توسيع النطاق أو تغيير المتطلبات أو معايير القبول بصمت.
- [ ] تم تسليم الأدلة والنواقص ونقطة الاستئناف إلى مهارة دورة حياة الخطة عند انطباقها.
