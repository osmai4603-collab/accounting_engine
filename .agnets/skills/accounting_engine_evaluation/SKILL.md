# مهارة تقييم محركات المحاسبة (Accounting Engine Evaluation Skill)

## الغرض (Purpose)

هذه المهارة تُرشد وكيل الذكاء الاصطناعي (AI Agent) عبر منهجية تقييم منظمة وقابلة للتكرار
لأي محرك محاسبي (Accounting Engine). تعتمد المنهجية على معايير هندسية ومحاسبية دولية
لإنتاج تقارير تقييم قائمة على الأدلة (Evidence-Based)، قابلة للمقارنة، وذات نتائج
قابلة للتحقق المستقل.

> **ملاحظة حاسمة**: هذه المهارة عامة (Domain-Generic) — لا ترتبط بأي مشروع محدد.
> يجب أن تعمل مع أي محرك محاسبي بغض النظر عن لغة البرمجة أو بنية المشروع أو قاعدة البيانات،
> مع تعليمات خاصة لمشاريع Go عند الحاجة.

## 1. شروط التفعيل (Activation Conditions)

**يجب تفعيل هذه المهارة** عندما يتحقق أي من الشروط التالية:

| الشرط | أمثلة على أوامر المستخدم |
| -------- | -------------------------- |
| تقييم أو تدقيق محرك محاسبي | "قيّم هذا المحرك المحاسبي"، "Evaluate this accounting engine"، "أعطني تقييم شامل" |
| مراجعة جاهزية الإنتاج | "هل هذا المحرك جاهز للإنتاج؟"، "Is this production-ready?"، "ما مدى نضج هذا النظام؟" |
| مقارنة إصدارات المحرك | "قارن بين الإصدار القديم والجديد"، "Compare v1 vs v2 of the engine" |
| تدقيق الامتثال المحاسبي | "هل هذا المحرك متوافق مع IFRS؟"، "Check accounting compliance" |
| تقييم الجودة المعمارية | "راجع البنية المعمارية"، "Assess the architecture quality"، "هل البنية نظيفة؟" |
| تقييم سلامة البيانات المالية | "هل البيانات المالية آمنة؟"، "Check data integrity"، "هل القيود المحاسبية سليمة؟" |
| مراجعة الأمان والتدقيق | "هل سجل المراجعة (Audit Trail) غير قابل للتعديل؟"، "Security audit of the engine" |
| تحليل الفجوات | "ما الذي ينقص هذا المحرك؟"، "Gap analysis for this accounting system" |

**قاعدة**: عند الشك في ما إذا كان الطلب يستدعي تقييمًا كاملاً أو جزئيًا، اسأل المستخدم
عن النطاق المطلوب قبل البدء.

## 2. المعايير المرجعية (Reference Standards)

عند إجراء أي تقييم، **يجب** أن تستند إلى المعايير المرجعية الخمس التالية. لا تَستنتج
قواعد من عندك — استخدم هذه المعايير كمصدر وحيد للحقيقة:

### 2.1 ISO/IEC 25010:2023 — نموذج جودة المنتج البرمجي (Software Product Quality Model)

يُحدد ثمانية خصائص جودة رئيسية يجب تقييمها:

| الخاصية (Characteristic) | ما يجب تقييمه في محرك المحاسبة |
| -------------------------- | ------------------------------- |
| **Functional Suitability** | هل المحرك يؤدي الوظائف المحاسبية المُعلنة بشكل صحيح وكامل؟ |
| **Performance Efficiency** | هل الأداء مقبول تحت الحمل المتوقع؟ |
| **Compatibility** | هل يمكن التكامل مع أنظمة أخرى؟ |
| **Usability** | هل الـ API واضحة وسهلة الاستخدام؟ |
| **Reliability** | هل المحرك يتعامل مع الأخطاء بشكل صحيح؟ |
| **Security** | هل البيانات المالية محمية؟ هل سجل المراجعة غير قابل للتعديل؟ |
| **Maintainability** | هل الكود قابل للصيانة والتعديل والاختبار؟ |
| **Portability** | هل يمكن نقل المحرك بين بيئات مختلفة؟ |

### 2.2 ISO/IEC 25040:2024 — إطار تقييم الجودة (Quality Evaluation Framework)

يُحدد خطوات التقييم التي يجب اتباعها:

1. **تحديد متطلبات التقييم** — ما الذي نُقيّمه ولماذا؟
2. **تحديد مقاييس التقييم** — ما المعايير المحددة لكل بُعد؟
3. **تصميم التقييم** — ما الأدوات والتقنيات المستخدمة؟
4. **تنفيذ التقييم** — جمع الأدلة وتحليلها
5. **إصدار الحكم** — استنتاج النتائج بناءً على الأدلة

### 2.3 IFRS Conceptual Framework ومعايير IAS/IFRS

المبادئ المحاسبية الأساسية التي يجب التحقق منها:

| المبدأ | ما يجب التحقق منه في المحرك |
| -------- | --------------------------- |
| **Double-Entry Principle** | كل قيد يجب أن يحتوي على طرف مدين وطرف دائن متساويين |
| **Accrual Basis (IAS 1)** | هل يدعم المحرك مبدأ الاستحقاق؟ |
| **Going Concern** | هل يدعم الفترات المحاسبية المستمرة؟ |
| **Faithful Representation** | هل البيانات المالية تعكس الواقع بدقة؟ |
| **Comparability** | هل يمكن مقارنة البيانات بين الفترات؟ |
| **Verifiability** | هل يمكن التحقق من كل قيد بشكل مستقل؟ |
| **Timeliness** | هل يتم تسجيل القيود في الوقت المناسب؟ |
| **IAS 8** | هل يدعم تعديل السياسات المحاسبية وتصحيح الأخطاء؟ |
| **IAS 21** | هل يدعم المعاملات بالعملات الأجنبية (إن أُعلن ذلك)؟ |
| **IFRS 15** | هل يدعم الاعتراف بالإيراد (إن كان ذلك ضمن النطاق)؟ |

### 2.4 NIST SSDF — إطار تطوير البرمجيات الآمن (Secure Software Development Framework)

| الممارسة | ما يجب التحقق منه |
| ---------- | ------------------- |
| **PO: Prepare the Organization** | هل يوجد توثيق لمتطلبات الأمان؟ |
| **PS: Protect Software** | هل الكود محمي من التعديل غير المصرح به؟ |
| **PW: Produce Well-Secured Software** | هل يتم التحقق من المدخلات؟ هل يتم التعامل مع الأخطاء بأمان؟ |
| **RV: Respond to Vulnerabilities** | هل يوجد آلية للتعامل مع الثغرات؟ |

### 2.5 مبادئ العمارة البرمجية (Architecture Principles)

| المبدأ | الوصف | ما يجب التحقق منه |
| -------- | ------- | ------------------- |
| **Separation of Concerns (SoC)** | فصل المسؤوليات | هل منطق المحاسبة منفصل عن البنية التحتية؟ |
| **Dependency Inversion (DIP)** | عكس التبعيات | هل الطبقة الأساسية (Domain) لا تعتمد على البنية التحتية؟ |
| **Modularity** | الوحدات المستقلة | هل يمكن استبدال مكون دون التأثير على الآخرين؟ |
| **Encapsulation** | التغليف | هل التفاصيل الداخلية مخفية خلف واجهات؟ |
| **Extensibility** | قابلية التوسع | هل يمكن إضافة ميزات دون تعديل الكود الأساسي؟ |
| **Interoperability** | قابلية التكامل | هل يمكن التكامل مع أنظمة خارجية عبر واجهات واضحة؟ |
| **Testability** | قابلية الاختبار | هل يمكن اختبار كل مكون بشكل مستقل؟ |

## 3. مراحل التقييم (Evaluation Phases)

يجب اتباع هذه المراحل الثمانية بالترتيب. **لا تتخطَّ أي مرحلة** — إذا كانت مرحلة
غير قابلة للتطبيق، وثِّق ذلك صراحةً مع السبب.

---

### المرحلة 1: هوية المشروع والنطاق (Project Identity & Scope)

**الهدف**: فهم ما يفعله المحرك وما لا يفعله قبل إصدار أي حكم.

**التعليمات**:

1. **اقرأ ملف README** (أو ما يعادله) واستخرج:
   - اسم المشروع ووصفه المُعلن
   - الغرض الرئيسي (Core Purpose)
   - الميزات المُعلنة (Declared Features)
   - القيود المُعلنة (Declared Limitations)
   - الجمهور المستهدف (Target Audience)

2. **اقرأ نقاط الدخول الرئيسية** (`main.go`، `doc.go`، أو ما يعادلها):
   - حدد نقطة الدخول الرئيسية للبرنامج
   - حدد ما إذا كان المحرك مكتبة (Library) أو تطبيق (Application) أو خدمة (Service)

3. **ارسم خريطة بنية المشروع** (Project Structure Map):
   - أدرج جميع الحزم/المجلدات (Packages/Directories) على المستوى الأعلى
   - صنِّف كل حزمة: `domain` / `application` / `infrastructure` / `interface` / `test` / `config` / `docs`
   - وثِّق الملفات الرئيسية في كل حزمة

4. **وثِّق النطاق المُعلن** (Declared Scope):
   - ما الذي يدّعي المحرك أنه يفعله؟
   - ما الذي يصرّح أنه لا يفعله؟
   - ما الذي لا يذكره (وقد يكون متوقعًا)؟

**مخرجات هذه المرحلة**:

```markdown
## Project Identity
- **Name**: [اسم المشروع]
- **Type**: Library | Application | Service
- **Purpose**: [الغرض المُعلن]
- **Declared Features**: [قائمة الميزات]
- **Declared Limitations**: [قائمة القيود]
- **Package Count**: [عدد الحزم]
- **Structure Classification**: [تصنيف البنية]
```

> [!IMPORTANT]
> لا تُصدر أي حكم في هذه المرحلة. الهدف هو الفهم فقط.
> إذا لم تجد README أو توثيقًا، وثِّق ذلك كـ Finding واستنتج النطاق من الكود.

### المرحلة 2: استخراج المتطلبات (Requirements Extraction)

**الهدف**: بناء قائمة شاملة بالمتطلبات التي سيتم قياس المحرك مقابلها.

**التعليمات**:

1. **استخرج المتطلبات الوظيفية (Functional Requirements)**:
   - افحص الواجهات العامة (Public Interfaces/API) — كل method عامة هي متطلب وظيفي ضمني
   - افحص العقود (Contracts) — ما الذي تضمنه كل واجهة؟
   - افحص أنواع البيانات (Types) — ما الكيانات المحاسبية الموجودة؟
     (مثل: `JournalEntry`, `Account`, `Ledger`, `Period`, `Transaction`)
   - أدرج كل متطلب وظيفي مع مصدره (ملف:سطر)

2. **استخرج المتطلبات غير الوظيفية (Non-Functional Requirements)**:
   - من التوثيق: الأداء المتوقع، السعة، التوافق
   - من الاختبارات: ما الذي تختبره الاختبارات الموجودة؟
   - من الإعدادات (Configs): ما الذي يمكن تكوينه؟
   - من الـ CI/CD: ما الفحوصات المُؤتمتة الموجودة؟

3. **استخرج القواعد المحاسبية (Accounting Rules)**:
   - من منطق المجال (Domain Logic): ما القواعد المحاسبية المُطبقة في الكود؟
   - هل يوجد تحقق من التوازن (Balance Validation)؟
   - هل يوجد تحقق من الحسابات (Account Validation)؟
   - هل يوجد إدارة للفترات (Period Management)؟
   - هل يوجد قيود عكسية (Reversals)؟

4. **استخرج العقود المعمارية (Architectural Contracts)**:
   - من بنية الحزم (Package Structure): ما التبعيات بين الحزم؟
   - من الاستيرادات (Imports): هل تتبع اتجاه التبعية الصحيح؟
   - من الواجهات (Interfaces): أين يتم تعريفها وأين يتم تنفيذها؟

**مخرجات هذه المرحلة**:

```markdown
## Requirements Register
| ID | Type | Requirement | Source | Standard |
|----|------|-------------|--------|----------|
| FR-001 | Functional | يجب ترحيل القيود المحاسبية | api.go:L45 | IFRS CF |
| FR-002 | Functional | يجب رفض القيود غير المتوازنة | entry.go:L23 | Double-Entry |
| NFR-001 | Non-Functional | يجب دعم العمليات المتزامنة | README.md | ISO 25010 |
| AR-001 | Accounting | يجب التحقق من توازن المدين والدائن | validator.go:L12 | IFRS CF |
```

> [!WARNING]
> **لا تفترض متطلبات غير موجودة** — إذا لم يُعلن المحرك عن دعم العملات المتعددة،
> لا تُضف ذلك كمتطلب. سجِّله فقط كـ "ميزة غائبة محتملة" في تحليل الفجوات.

### المرحلة 3: التحليل المعماري (Architecture Analysis)

**الهدف**: تقييم البنية المعمارية للمحرك وفقًا لمبادئ Clean Architecture.

**التعليمات**:

1. **ارسم خريطة الحزم والتبعيات** (Package & Dependency Map):
   - أدرج جميع الحزم مع أدوارها
   - حدد التبعيات بين الحزم (أي حزمة تستورد أي حزمة)
   - ارسم مخطط التبعيات (Dependency Graph) ذهنيًا أو نصيًا

   بالنسبة لمشاريع Go، نفِّذ:

   ```bash
   # عرض جميع الحزم
   go list ./...

   # عرض التبعيات الخارجية
   go list -m all

   # التحقق من التبعيات الدائرية (إن وجدت أداة)
   go vet ./...
   ```

2. **تحقق من اتجاه التبعيات** (Dependency Direction):
   - **القاعدة الذهبية**: طبقة المجال (Domain Layer) يجب ألا تستورد أي حزمة بنية تحتية
     (Infrastructure)
   - تحقق أن الواجهات (Interfaces/Ports) مُعرَّفة في طبقة المجال أو التطبيق
   - تحقق أن التنفيذات (Implementations/Adapters) في طبقة البنية التحتية
   - **مثال على انتهاك**:

     ```go
     // ❌ خطأ: حزمة domain تستورد حزمة database
     package domain
     import "myengine/infrastructure/postgres"

     // ✅ صحيح: حزمة domain تُعرِّف واجهة
     package domain
     type Repository interface {
         Save(entry JournalEntry) error
     }
     ```

3. **تحقق من فصل الطبقات** (Layer Separation):
   - هل يوجد فصل واضح بين:
     - **Domain Layer**: الكيانات والقواعد المحاسبية
     - **Application Layer**: حالات الاستخدام (Use Cases)
     - **Infrastructure Layer**: قاعدة البيانات، الملفات، الشبكة
     - **Interface Layer**: HTTP handlers, CLI, gRPC
   - هل الفصل حقيقي (بالحزم) أم شكلي (بالتسمية فقط)؟

4. **تحقق من نمط Port/Adapter**:
   - هل الواجهات (Ports) مُعرَّفة حيث يحتاجها المُستدعي؟
   - هل التنفيذات (Adapters) قابلة للاستبدال؟
   - هل يوجد حقن تبعيات (Dependency Injection)؟

5. **تحقق من التبعيات الدائرية** (Circular Dependencies):
   - في Go: المُترجم يمنع ذلك على مستوى الحزم، لكن تحقق من التبعيات الدائرية المنطقية
   - في لغات أخرى: ابحث عن دورات في مخطط الاستيرادات

6. **تحقق من تدفق البيانات** (Data Flow):
   - كيف تتدفق البيانات من المدخل إلى التخزين؟
   - هل يوجد تحويل بيانات (Data Transformation) بين الطبقات؟
   - هل كيانات المجال (Domain Entities) محمية من التسرب إلى الطبقات الخارجية؟

**مخرجات هذه المرحلة**:

```markdown
## Architecture Assessment
- **Layer Count**: [عدد الطبقات]
- **Dependency Direction**: Correct | Violated (details)
- **Port/Adapter Pattern**: Present | Partial | Absent
- **Circular Dependencies**: None | Found (details)
- **Domain Purity**: Pure | Contaminated (details)
```

### المرحلة 4: تحليل الصحة المحاسبية (Accounting Correctness Analysis)

**الهدف**: التحقق من أن المحرك يُطبق القواعد المحاسبية الأساسية بشكل صحيح.

> [!CAUTION]
> هذه هي المرحلة الأكثر أهمية. أي خلل محاسبي هو عيب حاسم (Critical Defect)
> بغض النظر عن جودة الكود الهندسية.

**التعليمات**:

1. **تحقق من إنفاذ القيد المزدوج (Double-Entry Enforcement)**:
   - ابحث عن الكود الذي يتحقق من `debit_total == credit_total`
   - تحقق أن هذا التحقق **إلزامي** وليس اختياريًا
   - تحقق أنه لا يمكن تجاوز هذا التحقق بأي طريقة
   - **الدليل المطلوب**: ملف:سطر حيث يتم رفض القيود غير المتوازنة
   - **مثال على التحقق الصحيح**:

     ```go
     func (e *JournalEntry) Validate() error {
         if e.DebitTotal() != e.CreditTotal() {
             return ErrUnbalancedEntry
         }
         // ...
     }
     ```

2. **تحقق من التحقق من التوازن (Balance Validation)**:
   - هل يتم التحقق من أن مجموع المدين = مجموع الدائن **قبل** الحفظ؟
   - هل يتم التحقق على مستوى القيد الواحد (Entry-Level)؟
   - هل يتم التحقق على مستوى الدفتر (Ledger-Level) أيضًا؟

3. **تحقق من إدارة الفترات المحاسبية (Period Management)**:
   - هل يوجد مفهوم فترة محاسبية (Accounting Period)؟
   - هل يمكن فتح وإغلاق الفترات؟
   - هل يمنع المحرك الترحيل في فترة مُغلقة؟
   - **الدليل المطلوب**: كود يرفض الترحيل عندما `period.IsClosed() == true`

4. **تحقق من التحقق من الحسابات (Account Validation)**:
   - هل يتحقق المحرك من وجود الحساب قبل الترحيل؟
   - هل يتحقق من نوع الحساب (مدين/دائن، أصول/خصوم/إيرادات/مصروفات)؟
   - هل يتحقق من أن الحساب نشط (Active) وليس مجمّدًا؟

5. **تحقق من ذرية الترحيل (Posting Atomicity)**:
   - هل يتم حفظ جميع أسطر القيد في عملية واحدة (Single Transaction)؟
   - **ما يحدث إذا فشل حفظ سطر واحد**: هل يتم التراجع عن الكل (Rollback)
     أم تبقى أسطر مكتوبة جزئيًا (Partial Write)؟
   - **الدليل المطلوب**: كود يُظهر استخدام transaction أو ما يعادله

6. **تحقق من آليات العكس (Reversal Mechanisms)**:
   - هل يوجد دعم لعكس القيود (Reversal Entries)؟
   - هل يتم العكس بقيد عكسي (Counter-Entry) أم بحذف القيد الأصلي؟
   - **المعيار**: وفقًا لـ IFRS، يجب أن يتم التصحيح بقيد عكسي، لا بالحذف

7. **تحقق من دعم العملات المتعددة (Multi-Currency Support)** — إن أُعلن:
   - هل يوجد فصل بين عملة المعاملة (Transaction Currency) وعملة التقرير
     (Reporting Currency)؟
   - هل يتم تخزين سعر الصرف مع كل معاملة؟
   - هل يتم معالجة فروقات الصرف (Exchange Differences) وفقًا لـ IAS 21؟

8. **تحقق من حساب ميزان المراجعة (Trial Balance Computation)**:
   - هل يمكن حساب ميزان المراجعة؟
   - هل يتم التحقق من أن مجموع المدين = مجموع الدائن على مستوى الدفتر؟
   - هل يمكن حسابه لفترة محددة؟

| Check | Status | Evidence | Standard |
|-------|--------|----------|----------|
| Double-Entry Enforcement | ✅/❌/⚠️ | file:line | IFRS CF |
| Balance Validation | ✅/❌/⚠️ | file:line | IFRS CF |
| Period Management | ✅/❌/⚠️/N/A | file:line | IAS 1 |

### المرحلة 5: تحليل سلامة التنفيذ (Implementation Safety Analysis)

**الهدف**: التحقق من أن التنفيذ يحمي البيانات المالية من الفساد والفقدان.

**التعليمات**:

1. **تحقق من ذرية المعاملات (Transaction Atomicity — ACID)**:
   - هل جميع العمليات المحاسبية مُغلَّفة في معاملات (Transactions)؟
   - هل يتم استخدام `BEGIN/COMMIT/ROLLBACK` أو ما يعادله؟
   - هل يتم التراجع (Rollback) عند حدوث أي خطأ؟
   - **ابحث عن**:

     ```go
     tx, err := db.Begin()
     if err != nil { return err }
     defer tx.Rollback()
     // ... operations ...
     return tx.Commit()
     ```

2. **تحقق من التحكم بالتزامن (Concurrency Control)**:
   - هل يوجد قفل (Locking) عند تعديل الأرصدة؟
   - هل يتم استخدام Optimistic Locking أو Pessimistic Locking؟
   - هل يوجد مفاتيح تكرار (Idempotency Keys) لمنع الترحيل المزدوج؟
   - **ابحث عن**: `SELECT ... FOR UPDATE`، `sync.Mutex`، `version` fields

3. **تحقق من التراجع عند الفشل (Rollback on Failure)**:
   - ماذا يحدث عند فشل عملية الحفظ في منتصفها؟
   - هل يتم ترك بيانات جزئية (Partial Data)؟
   - **اختبر السيناريو**: إذا تم حفظ 3 من 5 أسطر قيد ثم حدث خطأ

4. **تحقق من عزل الشركات/المستأجرين (Company/Tenant Isolation)**:
   - إذا كان المحرك يدعم شركات متعددة: هل البيانات معزولة تمامًا؟
   - هل يمكن لشركة أن تقرأ أو تعدّل بيانات شركة أخرى؟
   - **ابحث عن**: `company_id` أو `tenant_id` في كل استعلام

5. **تحقق من عدم قابلية التعديل لسجل المراجعة (Audit Trail Immutability)**:
   - هل يوجد سجل مراجعة (Audit Log)؟
   - هل هو غير قابل للتعديل (Append-Only)؟
   - هل يتم تسجيل: مَن، متى، ماذا، قبل، بعد؟
   - **الانتهاك**: إذا كان يمكن تعديل أو حذف سجلات المراجعة

6. **تحقق من التحقق من البيانات عند الحدود (Boundary Validation)**:
   - هل يتم التحقق من المدخلات عند نقاط الدخول (Entry Points)؟
   - هل يتم التحقق من الأنواع والقيم والنطاقات؟
   - هل يتم رفض المدخلات غير الصالحة قبل وصولها إلى منطق المجال؟

**مخرجات هذه المرحلة**:

```markdown
## Implementation Safety
| Check | Status | Evidence | Risk Level |
|-------|--------|----------|------------|
| Transaction Atomicity | ✅/❌/⚠️ | file:line | Critical/High/Medium/Low |
| Concurrency Control | ✅/❌/⚠️ | file:line | Critical/High/Medium/Low |
| Rollback on Failure | ✅/❌/⚠️ | file:line | Critical/High/Medium/Low |
| Tenant Isolation | ✅/❌/⚠️/N/A | file:line | Critical/High/Medium/Low |
| Audit Trail | ✅/❌/⚠️ | file:line | Critical/High/Medium/Low |
| Boundary Validation | ✅/❌/⚠️ | file:line | Critical/High/Medium/Low |
```

### المرحلة 6: تنفيذ الاختبارات والتحقق (Test Execution & Verification)

**الهدف**: تشغيل الاختبارات الموجودة وتحليل نتائجها وجودتها.

> [!CAUTION]
> **قاعدة مطلقة**: لا تدّعِ أبدًا أنك شغّلت اختبارات إذا لم تفعل ذلك فعلًا.
> إذا لم تتمكن من تشغيل الاختبارات، صرّح بذلك بوضوح.

**التعليمات**:

1. **شغّل جميع الاختبارات**:

   بالنسبة لمشاريع Go:

   ```bash
   # تشغيل جميع الاختبارات مع تفاصيل
   go test ./... -v -count=1

   # تشغيل اختبارات السباق (Race Condition Detection)
   go test -race ./...

   # تشغيل اختبارات التغطية (Coverage)
   go test -cover ./...

   # تشغيل الفحص الثابت (Static Analysis)
   go vet ./...
   ```

   بالنسبة للغات الأخرى: استخدم أداة الاختبار المناسبة وسجِّل الأمر المُستخدم.

2. **سجِّل النتائج بدقة**:

   ```markdown
   ## Test Execution Results
   - **Command**: `go test ./... -v -count=1`
   - **Date/Time**: [التاريخ والوقت]
   - **Total Tests**: [العدد]
   - **Passed**: [العدد]
   - **Failed**: [العدد]
   - **Skipped**: [العدد]
   - **Duration**: [المدة]
   ```

3. **شغّل اختبارات Race Condition** (لمشاريع Go):

   ```bash
   go test -race ./...
   ```

   - سجِّل أي سباقات (Races) تم اكتشافها
   - كل سباق مكتشف هو عيب حاسم (Critical) في محرك مالي

4. **حلّل تغطية الاختبارات** (Test Coverage):

   ```bash
   go test -cover ./...
   # أو للحصول على تغطية تفصيلية:
   go test -coverprofile=coverage.out ./...
   go tool cover -func=coverage.out
   ```

   - سجِّل نسبة التغطية الكلية ولكل حزمة
   - **لا تكتفِ بنسبة التغطية** — حلّل ما إذا كانت المسارات الحرجة مُغطاة

5. **حلّل جودة الاختبارات** (Test Quality) — ليس فقط النجاح/الفشل:
   - هل الاختبارات تختبر **السلوك الصحيح** (Happy Path)؟
   - هل الاختبارات تختبر **حالات الخطأ** (Error Cases)؟
   - هل الاختبارات تختبر **حالات الحدود** (Edge Cases)؟
   - هل الاختبارات تختبر **القواعد المحاسبية** بشكل صريح؟
   - **أمثلة على اختبارات حاسمة يجب أن تكون موجودة**:
     - اختبار رفض القيد غير المتوازن
     - اختبار رفض الترحيل في فترة مغلقة
     - اختبار ذرية الترحيل (Atomicity)
     - اختبار التزامن (Concurrency)

6. **حدد المسارات الحرجة غير المُختبرة** (Untested Critical Paths):
   - أي عملية محاسبية ليس لها اختبار هي فجوة حاسمة
   - أدرج جميع المسارات الحرجة وحالة اختبارها

7. **شغّل اختبارات الأداء** (Benchmarks) — إن وُجدت:

   ```bash
   go test -bench=. -benchmem ./...
   ```

**مخرجات هذه المرحلة**:

```markdown
## Test Execution Summary
| Metric | Value |
|--------|-------|
| Total Tests | [n] |
| Passed | [n] |
| Failed | [n] |
| Coverage | [n]% |
| Race Conditions | [n] found |
| Critical Paths Tested | [n]/[total] |
| Test Quality | High/Medium/Low |
```

### المرحلة 7: تحليل الفجوات والمخاطر (Gap & Risk Analysis)

**الهدف**: مقارنة المتطلبات المستخرجة (المرحلة 2) مع التنفيذ الفعلي وتحديد الفجوات.

**التعليمات**:

1. **قارن كل متطلب مع تنفيذه**:
   - لكل متطلب في سجل المتطلبات (Requirements Register):
     - هل يوجد تنفيذ مقابل؟
     - هل التنفيذ كامل أم جزئي؟
     - هل يوجد اختبار يثبت صحة التنفيذ؟

2. **حدد الميزات الغائبة** (Missing Features):
   - ما الميزات المحاسبية المتوقعة لمحرك من هذا النوع ولكنها غير موجودة؟
   - **تنبيه**: ميّز بين "ميزة غائبة ضمن النطاق المُعلن" (Gap)
     و"ميزة غائبة خارج النطاق المُعلن" (Out of Scope)

3. **صنِّف الفجوات حسب الخطورة**:

   | الخطورة | المعيار | مثال |
   | --------- | --------- | ------ |
   | **Critical** | يُهدد صحة البيانات المالية | عدم التحقق من توازن القيد |
   | **High** | يُهدد الموثوقية أو الأمان | عدم وجود ذرية في الترحيل |
   | **Medium** | يُقلل الجودة أو الكفاءة | نقص في التغطية الاختبارية |
   | **Low** | تحسين مرغوب | نقص في التوثيق |

4. **حدد المخاطر** (Risks):
   - لكل فجوة: ما التأثير المحتمل إذا لم تُعالج؟
   - ما احتمالية حدوث التأثير؟
   - ما الإجراء التصحيحي المُقترح؟

**مخرجات هذه المرحلة**:

```markdown
## Gap Analysis
| ID | Requirement | Status | Severity | Risk | Recommendation |
|----|-------------|--------|----------|------|---------------|
| GAP-001 | [المتطلب] | Missing/Partial | Critical/High/Medium/Low | [الخطر] | [التوصية] |
```

### المرحلة 8: حكم التقييم (Evaluation Verdict)

**الهدف**: تجميع جميع النتائج في حكم نهائي مُدعم بالأدلة.

**التعليمات**:

1. **أنتج سجل النتائج** (Findings Register):
   - كل نتيجة يجب أن تحتوي على:

     ```
     ID: F-XXX
     Description: [وصف النتيجة]
     Standard: [المعيار المُنتهك أو المُحقق]
     Evidence: file:line أو "test output" أو "code review"
     Impact: [التأثير]
     Severity: Critical | High | Medium | Low
     Test: [هل يوجد اختبار يثبت ذلك؟]
     Recommendation: [التوصية]
     ```

2. **سجّل النضج لكل بُعد** (Maturity Scoring):
   - استخدم مقياس 0-4 (انظر القسم 6.2)
   - **لا تدمج** درجة النضج مع مستوى الخطورة

3. **صنِّف المخاطر** (Risk Classification):
   - استخدم مصفوفة التأثير × الاحتمالية
   - حدد المخاطر التي تمنع الإنتاج (Production Blockers)

4. **حدد جاهزية الإنتاج** (Production Readiness):

   | المستوى | المعيار |
   | --------- | --------- |
   | **جاهز (Ready)** | لا توجد مخاطر حاسمة أو عالية، تغطية اختبارية كافية |
   | **جاهز بشروط (Conditionally Ready)** | مخاطر عالية محدودة مع خطة معالجة |
   | **غير جاهز (Not Ready)** | مخاطر حاسمة موجودة |

5. **قدّم توصيات قابلة للتنفيذ** (Actionable Recommendations):
   - رتّب التوصيات حسب الأولوية (Critical أولاً)
   - كل توصية يجب أن تكون محددة وقابلة للقياس
   - **لا تقترح إعادة تصميم كاملة** إلا إذا كانت المشاكل جوهرية

## 4. أبعاد التقييم (Evaluation Dimensions)

**يجب** تقييم المحرك عبر 12 بُعدًا. لكل بُعد، اتّبع الهيكل: ماذا تبحث عنه → كيف تتحقق
→ ما الذي يُشكّل دليلاً → ما الذي يُشكّل فشلاً.

### البُعد 1: الصحة المحاسبية (Accounting Correctness)

| العنصر | التفاصيل |
| -------- | --------- |
| **ماذا تبحث عنه** | إنفاذ القيد المزدوج، التحقق من التوازن، قواعد محاسبية صحيحة |
| **كيف تتحقق** | افحص كود التحقق (Validation)، شغّل اختبارات القيود المحاسبية، حاول ترحيل قيد غير متوازن |
| **دليل النجاح** | كود يرفض القيود غير المتوازنة + اختبار يُثبت ذلك |

| العنصر | التفاصيل |
| -------- | --------- |
| **ماذا تبحث عنه** | دورة محاسبية كاملة: إنشاء حسابات → ترحيل قيود → استعلام أرصدة → ميزان مراجعة |

| العنصر | التفاصيل |
| -------- | --------- |
| **ماذا تبحث عنه** | ذرية المعاملات، عدم فقدان البيانات، تناسق البيانات |

| **دليل النجاح** | كل عملية مُغلَّفة في معاملة مع Rollback عند الفشل |

### البُعد 4: العمارة (Architecture)

| العنصر | التفاصيل |
| -------- | --------- |
| **ماذا تبحث عنه** | فصل الطبقات، اتجاه التبعيات، نمط Port/Adapter |
| **كيف تتحقق** | افحص الاستيرادات، ارسم مخطط التبعيات، تحقق من Domain Purity |

| العنصر | التفاصيل |

| العنصر | التفاصيل |

| العنصر | التفاصيل |
| -------- | --------- |
| **ماذا تبحث عنه** | فصل منطق التخزين، قابلية استبدال قاعدة البيانات، Repository Pattern |

### البُعد 9: الأمان وقابلية التدقيق (Security & Auditability)

| العنصر | التفاصيل |
| -------- | --------- |
| **ماذا تبحث عنه** | سجل مراجعة غير قابل للتعديل، التحقق من الصلاحيات، حماية البيانات |
| **كيف تتحقق** | هل يوجد Audit Log؟ هل هو Append-Only؟ هل يتم تسجيل كل عملية؟ |
| **دليل النجاح** | Audit Trail مع Timestamp، User، Action، Before/After Values |
| **دليل الفشل** | لا يوجد سجل مراجعة، أو يمكن تعديل/حذف السجلات |

### البُعد 10: الأداء (Performance)

| العنصر | التفاصيل |
| -------- | --------- |
| **ماذا تبحث عنه** | كفاءة الاستعلامات، اختبارات أداء، قابلية التوسع |
| **كيف تتحقق** | شغّل Benchmarks، افحص تعقيد الخوارزميات، ابحث عن N+1 Queries |

### البُعد 11: الاختبار (Testing)

| العنصر | التفاصيل |
| -------- | --------- |
| **ماذا تبحث عنه** | تغطية اختبارية كافية، اختبارات للمسارات الحرجة، اختبارات الحدود |

## 5. قائمة التحقق المحاسبي (Accounting Verification Checklist)

**يجب** الإجابة على كل سؤال من الأسئلة التالية بـ: **نعم (مع دليل)** أو **لا (مع تأثير)**
أو **غير قابل للتطبيق (مع سبب)**.

### 5.1 التحقق من القيد المزدوج (Double-Entry Verification)

| # | السؤال | كيفية التحقق |
| --- | -------- | ------------- |
| 1 | **هل يرفض المحرك القيود غير المتوازنة؟** | ابحث عن كود يقارن `debit_total` مع `credit_total`. تحقق من أن المقارنة تتم **قبل** أي عملية حفظ. ابحث عن اختبار يُمرر قيدًا غير متوازن ويتوقع خطأ. |
| 2 | **هل يتحقق المحرك من صحة الحسابات؟** | ابحث عن كود يتحقق من وجود الحساب في دليل الحسابات (Chart of Accounts). تحقق من أنه يرفض الحسابات غير الموجودة أو غير النشطة. |
| 3 | **هل يمنع الترحيل في فترات مغلقة؟** | ابحث عن فحص حالة الفترة (`period.Status`, `period.IsClosed()`, `period.IsOpen()`). تحقق من رفض الترحيل عندما تكون الفترة مغلقة. |
| 4 | **هل الترحيل ذري (Atomic)؟** | ابحث عن استخدام Database Transactions أو ما يعادلها. تحقق من أن جميع أسطر القيد تُحفظ أو لا يُحفظ أيٌّ منها. |
| 5 | **ماذا يحدث إذا فشل حفظ سطر واحد؟** | تتبّع مسار الكود عند حدوث خطأ أثناء الحفظ. تحقق من Rollback. ابحث عن اختبار يُحاكي فشل الحفظ. |
| 6 | **هل يمكن أن تتسبب الطلبات المكررة في ترحيل مزدوج؟** | ابحث عن Idempotency Key أو Unique Constraint. تحقق من أن إرسال نفس الطلب مرتين لا يُنتج قيدين. |
| 7 | **هل يمكن تعديل القيود المرحّلة بما ينتهك سياسة التدقيق؟** | ابحث عن آلية منع التعديل (Immutability). تحقق من أن القيود المرحّلة لا يمكن تعديلها أو حذفها إلا عبر قيد عكسي. |
| 8 | **هل أرصدة الحسابات تتطابق مع دفتر الأستاذ العام؟** | ابحث عن كود يحسب الأرصدة من القيود. تحقق من أن الأرصدة المُخزنة (إن وُجدت) تتطابق مع المحسوبة. |

### 5.2 نموذج توثيق النتائج

لكل سؤال، وثِّق النتيجة بالشكل التالي:

```markdown
### السؤال 1: هل يرفض المحرك القيود غير المتوازنة؟

**الإجابة**: نعم ✅

**الدليل**:
- ملف التحقق: `domain/entry.go:L45-L52`
- الكود:
  ```go

      return ErrUnbalancedEntry
  }
  ```

- الاختبار: `domain/entry_test.go:L78` — TestRejectUnbalancedEntry

**المعيار**: IFRS Conceptual Framework — Double-Entry Principle

```

## 6. قواعد الحكم القائم على الأدلة (Evidence-Based Judgment Rules)

### 6.1 ثالوث التقييم (Evaluation Triad)

كل حكم يجب أن يستند إلى ثلاثة عناصر:

```

المتطلب (Requirement) → التنفيذ (Implementation) → الدليل (Evidence)

```

| العنصر | الوصف | مثال |
|--------|-------|------|
| **المتطلب** | ماذا يجب أن يفعل المحرك | "يجب رفض القيود غير المتوازنة" |
| **التنفيذ** | كيف يفعله الكود | `entry.go:L45 — if debit != credit` |
| **الدليل** | ما يُثبت أنه يعمل | `entry_test.go:L78 — TestRejectUnbalanced → PASS` |

**قاعدة**: إذا كان أي عنصر من الثالوث مفقودًا، يجب تخفيض درجة التصنيف.

### 6.2 مخطط التصنيف (Classification Scheme)

| التصنيف | المعنى | الشرط |
|---------|--------|-------|
| **Verified** ✅ | مُتحقق منه بالكامل | المتطلب + التنفيذ + الدليل (اختبار ناجح) |
| **Partially Verified** ⚠️ | مُتحقق منه جزئيًا | التنفيذ موجود لكن الاختبار غير كافٍ أو جزئي |
| **Failed** ❌ | فشل التحقق | الاختبار فشل، أو التنفيذ غير صحيح |
| **Not Implemented** 🔴 | غير مُنفَّذ | المتطلب موجود لكن لا يوجد تنفيذ |
| **Not Verified** ❓ | غير مُتحقق منه | التنفيذ موجود لكن لم يتم تشغيل اختبارات |
| **Out of Scope** ⬜ | خارج النطاق | المتطلب ليس ضمن النطاق المُعلن |

### 6.3 مقياس النضج (Maturity Scale)

| الدرجة | المستوى | الوصف |
|--------|---------|-------|
| **0** | غائب (Absent) | لا يوجد تنفيذ ولا تخطيط |
| **1** | أوّلي (Initial) | تنفيذ جزئي، غير مُختبر، غير مُوثق |
| **2** | مُدار (Managed) | تنفيذ يعمل، اختبارات أساسية، توثيق جزئي |
| **3** | مُحدد (Defined) | تنفيذ كامل، اختبارات شاملة، توثيق جيد، أنماط واضحة |
| **4** | محسّن (Optimized) | تنفيذ مُحسّن، اختبارات متقدمة (Performance, Fuzz)، توثيق ممتاز |

### 6.4 تصنيف المخاطر (Risk Classification)

| المستوى | المعيار | التأثير | يجب المعالجة |
|---------|---------|---------|-------------|
| **Critical** 🔴 | يُهدد صحة البيانات المالية أو يُسبب خسائر | فقدان بيانات، أرصدة خاطئة | **فورًا — يمنع الإنتاج** |
| **High** 🟠 | يُهدد الموثوقية أو الأمان | تسرب بيانات، فشل متقطع | **قبل الإنتاج** |
| **Medium** 🟡 | يُقلل الجودة أو الكفاءة | أداء بطيء، صعوبة صيانة | **مُخطط له** |
| **Low** 🟢 | تحسين مرغوب | تجربة مطور، توثيق | **عند الإمكان** |

> [!IMPORTANT]
> **لا تدمج أبدًا** درجة النضج (Maturity) مع مستوى الخطورة (Risk) في درجة واحدة.
> هما بُعدان مستقلان:
> - النضج يقيس **مدى اكتمال التنفيذ**
> - الخطورة تقيس **تأثير الفجوة على النظام**
>
> مثال: نظام بنضج 3 (مُحدد) قد يحتوي على خطر Critical واحد.

## 7. قواعد النزاهة (Integrity Rules)

**يجب** الالتزام بهذه القواعد العشر في كل تقييم. انتهاك أي قاعدة يُبطل مصداقية التقييم:

### القاعدة 1: وجود الكود ≠ الصحة الوظيفية
```

❌ "الكود يتحقق من التوازن" (بدون تشغيل اختبار)
✅ "الكود يتحقق من التوازن في entry.go:L45، والاختبار TestBalanceCheck يُثبت ذلك"
✅ "الكود يتحقق من التوازن في entry.go:L45، لكن لم يتم تشغيل الاختبار (Not Verified)"

```

### القاعدة 2: وجود الاختبارات ≠ صحة المحرك بدون تشغيلها
```

❌ "المحرك يعمل بشكل صحيح لأن الاختبارات موجودة"
✅ "الاختبارات موجودة لكن لم يتم تشغيلها — التصنيف: Not Verified"
✅ "تم تشغيل 45 اختبارًا: 43 ناجح، 2 فاشل — التفاصيل أدناه"

```

### القاعدة 3: نجاح الاختبارات ≠ تغطية كاملة
```

❌ "جميع الاختبارات ناجحة، إذن المحرك سليم"
✅ "جميع الاختبارات (45/45) ناجحة، لكن التغطية 60% — المسارات غير المُختبرة: [قائمة]"

```

### القاعدة 4: اسم الميزة أو التوثيق ≠ اكتمال الميزة
```

❌ "المحرك يدعم Multi-Currency لأن الملف README يذكر ذلك"
✅ "الملف README يذكر Multi-Currency، لكن الفحص يُظهر أن التنفيذ جزئي: [تفاصيل]"

```

### القاعدة 5: لا تصف انتهاكًا محاسبيًا بدون ذكر المعيار
```

❌ "المحرك لا يتحقق من التوازن — هذا خطأ"
✅ "المحرك لا يتحقق من التوازن — ينتهك مبدأ القيد المزدوج (IFRS Conceptual Framework)"

```

### القاعدة 6: لا تقترح إعادة تصميم لمجرد اختلاف في الأسلوب
```

❌ "يجب إعادة هيكلة الكود لاستخدام CQRS بدلاً من النمط الحالي"
✅ "النمط الحالي يعمل بشكل صحيح. CQRS خيار بديل لكنه ليس ضروريًا"

```
**الاستثناء**: إذا كان النمط الحالي يُسبب مشكلة فعلية مُوثقة بدليل.

### القاعدة 7: ميّز بين المشاكل الفعلية والتحسينات الاختيارية
```

❌ خلط Finding (مشكلة فعلية) مع Recommendation (تحسين اختياري) في نفس الفئة
✅ "Finding F-001: عدم وجود Rollback — Severity: Critical"
✅ "Recommendation R-001: إضافة Benchmarks — Priority: Low"

```

### القاعدة 8: لا تحكم بدون دليل قابل للمراجعة
```

❌ "البنية المعمارية جيدة" (بدون تفاصيل)
✅ "البنية المعمارية تتبع Clean Architecture:
    - Domain في pkg/domain/ (لا تستورد infrastructure) ✅
    - Ports مُعرَّفة في pkg/domain/ports/ ✅
    - Adapters في pkg/infrastructure/ ✅"

```

### القاعدة 9: لا تدّعِ تنفيذ اختبارات لم تُنفَّذ
```

❌ "تم تشغيل الاختبارات بنجاح" (بدون مخرجات فعلية)
✅ "تم تشغيل: `go test ./... -v -count=1`
    النتيجة: 45 passed, 0 failed, 2 skipped (12.3s)"
✅ "لم يتم تشغيل الاختبارات بسبب [السبب] — التصنيف: Not Verified"

```

### القاعدة 10: وثِّق كل افتراض ونقطة غير مُتحقق منها
```

✅ "**افتراض**: المحرك مُصمم كمكتبة (Library) — مُستنتج من غياب main.go ووجود
    واجهات عامة فقط. لم يتم التأكيد مع فريق التطوير."
✅ "**غير مُتحقق منه**: أداء المحرك تحت الحمل العالي — لا توجد اختبارات أداء."

```

## 8. تقييم استقلالية المجال (Domain Independence Assessment)

**الهدف**: تحديد ما إذا كان المحرك قابلًا لإعادة الاستخدام في مشاريع مختلفة.

**يجب** الإجابة على الأسئلة السبعة التالية:

### السؤال 1: هل المحرك محايد لمجال العمل (Business Domain Neutral)؟

**كيف تتحقق**:
- ابحث عن مصطلحات خاصة بمجال عمل معين (مثل: `invoice`, `order`, `customer`, `product`)
  في طبقة Domain
- تحقق أن طبقة Domain تحتوي فقط على مصطلحات محاسبية عامة
  (مثل: `Account`, `JournalEntry`, `Ledger`, `Period`)

**التصنيف**:
- ✅ **محايد**: لا يوجد منطق خاص بمجال عمل معين
- ⚠️ **شبه محايد**: وجود تلميحات قليلة لمجال عمل لكنها قابلة للإزالة
- ❌ **غير محايد**: منطق خاص بمجال عمل مُضمّن في الكود الأساسي

### السؤال 2: هل يمكن التكامل عبر واجهات واضحة (Clear Interfaces)؟

**كيف تتحقق**:
- هل يوجد واجهة (Interface) أو عقد (Contract) واضح للتكامل؟
- هل يحتاج النظام المُستضيف (Host System) إلى استيراد حزم داخلية؟
- هل يوجد فصل بين الـ API العامة والتفاصيل الداخلية؟

### السؤال 3: هل يمكن تخصيص دليل الحسابات والسياسات (Chart of Accounts & Policies)؟

**كيف تتحقق**:
- هل دليل الحسابات (Chart of Accounts) مُكوّن عبر إعدادات أم مُرمّز في الكود (Hardcoded)؟
- هل السياسات المحاسبية (مثل: طريقة الإهلاك) قابلة للتكوين؟
- هل يمكن تعريف أنواع حسابات مخصصة؟

### السؤال 4: هل يمكن إضافة أبعاد محاسبية (Accounting Dimensions) بدون تعديل الكود الأساسي؟

**كيف تتحقق**:
- هل يمكن إضافة أبعاد مثل: مركز تكلفة (Cost Center)، مشروع (Project)، قسم (Department)
  بدون تعديل بنية القيد الأساسية؟
- هل يوجد آلية للأبعاد المُخصصة (Custom Dimensions)؟

### السؤال 5: هل يمكن استبدال قاعدة البيانات بدون إعادة كتابة منطق المحاسبة؟

**كيف تتحقق**:
- هل يوجد نمط Repository أو Port/Adapter؟
- هل منطق المحاسبة مستقل عن تقنية التخزين؟
- **اختبار**: إذا استبدلت PostgreSQL بـ SQLite أو In-Memory Store، هل يحتاج
  أي ملف في طبقة Domain إلى تعديل؟

### السؤال 6: هل يحتاج النظام المُستضيف إلى معرفة التفاصيل الداخلية للمحرك؟

**كيف تتحقق**:
- هل الـ API العامة كافية للتكامل؟
- هل يحتاج المُتكامل إلى فهم بنية الجداول الداخلية؟
- هل يحتاج إلى استخدام أنواع بيانات داخلية (Internal Types)؟

### السؤال 7: هل يمكن التكامل بدون الارتباط ببروتوكول أو إطار عمل محدد؟

**كيف تتحقق**:
- هل الـ API متاحة كمكتبة (Library) بدون إلزام باستخدام HTTP أو gRPC؟
- هل يمكن استخدام المحرك كمكتبة Go (أو المكافئ في لغات أخرى) بدون تشغيل خادم؟
- هل يوجد فصل بين واجهة النقل (Transport) ومنطق المحاسبة؟

**مخرجات هذا القسم**:

## 11. الأنماط المضادة الواجب الإبلاغ عنها (Anti-Patterns to Flag)

عند فحص الكود، **يجب** الإبلاغ فورًا عن أي من الأنماط المضادة التالية إذا وُجدت.
كل نمط مضاد يجب أن يُسجَّل كـ Finding مع درجة خطورة مناسبة.

---

### 11.1 منطق المحاسبة في معالجات HTTP (Accounting Logic in HTTP Handlers)

**الوصف**: وضع قواعد محاسبية (تحقق من التوازن، حساب الأرصدة) مباشرة في HTTP handlers
أو gRPC handlers بدلاً من طبقة Domain أو Application.

**كيف تكتشفه**:

```go
// ❌ نمط مضاد
func PostEntryHandler(w http.ResponseWriter, r *http.Request) {
    var entry JournalEntry
    json.NewDecoder(r.Body).Decode(&entry)

    // ❌ منطق محاسبي في handler!
    if entry.DebitTotal() != entry.CreditTotal() {
        http.Error(w, "unbalanced", 400)
        return
    }

    db.Save(entry) // ❌ وصول مباشر لقاعدة البيانات!
}
```

**الخطورة**: High
**المعيار المُنتهك**: Separation of Concerns (ISO 25010 — Maintainability)
**التأثير**: صعوبة الاختبار، تكرار المنطق، خطر تجاوز القواعد

---

### 11.2 قواعد العمل في استعلامات SQL (Business Rules in SQL Queries)

**الوصف**: وضع قواعد محاسبية في استعلامات SQL بدلاً من طبقة Domain.

**كيف تكتشفه**:

```sql
-- ❌ نمط مضاد: قاعدة محاسبية في SQL
INSERT INTO journal_entries (...)
SELECT ... WHERE debit_total = credit_total  -- القاعدة في SQL!
```

**الخطورة**: High
**المعيار المُنتهك**: Dependency Inversion Principle
**التأثير**: القواعد المحاسبية مُبعثرة بين Go و SQL، صعوبة التتبع

---

### 11.3 حدود معاملات مفقودة (Missing Transaction Boundaries)

**الوصف**: تنفيذ عمليات كتابة متعددة بدون تغليفها في Database Transaction.

**كيف تكتشفه**:

```go
// ❌ نمط مضاد: كتابات متعددة بدون Transaction
func (r *Repo) SaveEntry(entry JournalEntry) error {
    err := r.db.Insert("journal_entries", entry.Header)
    if err != nil { return err }

    for _, line := range entry.Lines {
        err := r.db.Insert("journal_lines", line)  // ❌ قد يفشل هنا!
        if err != nil { return err }  // ❌ الأسطر السابقة مكتوبة بالفعل!
    }
    return nil
}
```

**الخطورة**: Critical
**المعيار المُنتهك**: ACID — Atomicity
**التأثير**: بيانات مالية غير متسقة (Partial Writes)

---

### 11.4 سجلات تدقيق قابلة للتعديل (Mutable Audit Records)

**الوصف**: إمكانية تعديل أو حذف سجلات التدقيق (Audit Trail).

**كيف تكتشفه**:

```go
// ❌ نمط مضاد
func (r *AuditRepo) UpdateAuditLog(id string, newData AuditEntry) error {
    return r.db.Update("audit_logs", id, newData)  // ❌ يمكن تعديل السجل!
}

func (r *AuditRepo) DeleteAuditLog(id string) error {
    return r.db.Delete("audit_logs", id)  // ❌ يمكن حذف السجل!
}
```

**الخطورة**: Critical
**المعيار المُنتهك**: IFRS — Verifiability, NIST SSDF
**التأثير**: فقدان مسار التدقيق، عدم إمكانية المراجعة

---

### 11.5 حالة عامة للمستأجرين المتعددين (Global State for Multi-Tenant)

**الوصف**: استخدام متغيرات عامة (Global Variables) لتخزين بيانات خاصة بمستأجر محدد.

**كيف تكتشفه**:

```go
// ❌ نمط مضاد
var currentCompanyID string  // ❌ متغير عام!
var currentPeriod Period     // ❌ متغير عام!

func PostEntry(entry JournalEntry) error {
    entry.CompanyID = currentCompanyID  // ❌ يعتمد على حالة عامة!
    // ...
}
```

**الخطورة**: Critical
**المعيار المُنتهك**: ISO 25010 — Security (Isolation)
**التأثير**: تسرب بيانات بين المستأجرين، سباقات بيانات

---

### 11.6 مفاتيح تكرار مفقودة (Missing Idempotency Keys)

**الوصف**: عدم وجود آلية لمنع تنفيذ نفس العملية مرتين عند إعادة المحاولة.

**كيف تكتشفه**:

- لا يوجد حقل `idempotency_key` أو `request_id` في كيان القيد
- لا يوجد `UNIQUE CONSTRAINT` على مُعرِّف الطلب
- لا يوجد فحص "هل تم تنفيذ هذا الطلب سابقًا؟"

**الخطورة**: High
**المعيار المُنتهك**: Reliability (ISO 25010)
**التأثير**: ترحيل مزدوج (Double Posting) عند إعادة المحاولة

---

### 11.7 كتابات جزئية بدون تراجع (Partial Writes Without Rollback)

**الوصف**: عند حدوث خطأ أثناء كتابة متعددة الخطوات، تبقى البيانات الجزئية المكتوبة
بدون تنظيف.

**كيف تكتشفه**:

- ابحث عن عمليات كتابة متتابعة (Sequential Writes) بدون Transaction
- تحقق من مسار الخطأ (Error Path): هل يتم تنظيف ما كُتب قبل الخطأ؟
- ابحث عن `defer tx.Rollback()` أو ما يعادله — غيابه مؤشر على المشكلة

**الخطورة**: Critical
**المعيار المُنتهك**: ACID — Atomicity
**التأثير**: بيانات مالية تالفة، أرصدة غير صحيحة

---

   ```

4. قدّم توصيات للإصدار القادم

## ملحق د: التعامل مع الحالات الخاصة (Handling Edge Cases)

### حالة 1: المشروع لا يُترجم (Build Failure)

```markdown
⚠️ **Build Failure Detected**
- **Command**: `go build ./...`
- **Error**: [رسالة الخطأ]
- **Impact**: لا يمكن تشغيل الاختبارات — جميع أبعاد الاختبار = Not Verified
- **Action**: سجّل كـ Finding بخطورة High، أكمل التحليل الثابت (Static Analysis) فقط
```

### حالة 2: لا توجد اختبارات (No Tests)

```markdown
⚠️ **No Tests Found**
- **Impact**: جميع التصنيفات = Not Verified (بدلاً من Verified)
- **Finding**: F-XXX — غياب كامل للاختبارات
- **Severity**: High
- **Action**: أكمل التحليل الثابت، وثِّق أن جميع الأحكام مبنية على مراجعة الكود فقط
```

### حالة 3: المحرك ليس Go (Non-Go Engine)

- استخدم أدوات الاختبار المكافئة في اللغة المعنية
- استبدل أوامر Go بما يقابلها (مثل: `pytest` لـ Python، `mvn test` لـ Java)
- جميع المبادئ المحاسبية والمعمارية تبقى سارية بغض النظر عن اللغة

### حالة 4: المحرك في مرحلة مبكرة (Early Stage)

- لا تُعاقب المشروع على ميزات غير مُخطط لها بعد
- ركّز على: هل الأساسيات (Foundation) صحيحة؟
- قدّم خارطة طريق (Roadmap) بدلاً من قائمة عيوب

### حالة 5: لا يوجد وصول لقاعدة البيانات (No Database Access)

- حلّل كود الـ Repository/Persistence من المصدر فقط
- وثِّق أن التحقق من ACID تم على مستوى الكود فقط (لم يتم التحقق الفعلي)
- صنِّف جميع أبعاد Persistence كـ "Partially Verified"
