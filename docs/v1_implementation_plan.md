# الخطة التنفيذية لإغلاق فجوات إعلان `v1`

## 1. الغرض والمرجعية

تحدد هذه الخطة الأعمال اللازمة لمعالجة نتائج التحقق الواردة في
[`v1_declaration_verification.md`](./v1_declaration_verification.md)، وتحويلها إلى
مهام قابلة للتنفيذ والاختبار والتوازي. لا تعيد هذه الخطة تقييم نتائج الوثيقة؛
تُعدّ الوثيقة المرجع لتحديد الفجوات الحالية، وتُعدّ معايير القبول هنا شروط
إغلاق كل مهمة.

**القرار الابتدائي:** لا يُعلن `v1` ولا يُعتمد المسار الجديد لترحيل قيود مالية
حقيقية قبل اجتياز بوابة الاعتماد النهائية في القسم 5.

**مبدأ التوازي:** تُنفّذ المهام المتوازية على فروع/مساحات عمل منفصلة عند تعديل
المناطق نفسها، وتُدمج تغييرات العقود أولاً. لا يبدأ عمل يعتمد على عقد عام غير
مستقر. تعتمد الخطة على معرّفات المهام لتوضيح الاعتماديات؛ ترتيب عرض المهام ليس
بديلاً عن تلك الاعتماديات.

## 2. مراحل التنفيذ وبواباتها

| المرحلة | الهدف | المهام | بوابة الانتقال |
| --- | --- | --- | --- |
| 0. تثبيت خط الأساس | إعادة إنتاج الحالة وتحديد الاختبارات التي تثبت كل فجوة | `F0-01` | توثيق نتائج الأوامر، وربط كل شرط `v1` باختبار أو فحص قابل للتكرار |
| 1. تثبيت العقود العامة | إتاحة SDK وMaster Data بعقود عامة، وتحديد حدود التطبيق والمعاملة | `C1-01`، `C1-02`، `C1-03`، `C1-04`، `C1-05` | استقرار واجهات عامة typed، وعدم الحاجة إلى `internal/*` لتهيئة SDK |
| 2. إغلاق سلامة مسار المحاسبة | فرض Application/Posting، ذرية Idempotency، صحة الأحداث، وإغلاق اختبارات الفجوات | `W2-01` إلى `W2-04` | اجتياز الاختبارات السلوكية وPostgreSQL، وعدم وجود مسار يتجاوز ضوابط الترحيل |
| 3. إثبات قابلية الاستهلاك والتبديل | إثبات الاستهلاك من Module مستقل وتكافؤ Memory/PostgreSQL واكتمال الأثر القطاعي | `P3-01` إلى `P3-05` | بناء المستهلك الخارجي، واجتياز اختبارات السائقين والأثر المحاسبي |
| 4. جاهزية الخدمة والتوزيع | إكمال HTTP/gRPC، الجاهزية والمقاييس، التشغيل الآمن، وCI/Docker | `S4-01` إلى `S4-04` | بناء الخدمة وتشغيل اختبارات التكامل على إصدارات بيئة متطابقة |
| 5. اعتماد `v1` | إعادة تشغيل بوابات الجودة وإثبات شروط الإعلان الثمانية | `G5-01` | كل شروط الاعتماد خضراء، ولا توجد فجوات حرجة مؤجلة أو اختبارات متجاوزة بلا مبرر معتمد |

### مسارات العمل المستقلة

بعد إنجاز `F0-01`، يمكن بدء المسارات التالية بالتوازي:

1. **العقد العام:** `C1-01`، `C1-02`، `C1-03` (مع دمج تغييرات العقد بتنسيق
   مشترك)، ثم `C1-04` و`C1-05`.
2. **الخدمة:** `S4-01` و`S4-02` مستقلان عن أعمال SDK، على أن تعتمد جاهزية
   الخدمة في `S4-03` على توافر واجهة فحص صحة التخزين.
3. **اختبارات فجوات التخزين والحوكمة:** يمكن تجهيز حالات الاختبار بالتوازي مع
   تطوير العقود، لكن لا يُغلق التنفيذ قبل توفر حدود المعاملة المعتمدة في
   `C1-02`.
4. بعد استقرار عقود المرحلة 1، تتوازى `W2-01` و`W2-02` و`W2-03` بحسب
   الاعتماديات التفصيلية أدناه. ويمكن تطوير `W2-04` بالتوازي بعد تثبيت نماذج
   الحدث وواجهات Master Data.
5. بعد إغلاق مسار المحاسبة، يمكن تنفيذ المستهلك الخارجي واختبارات التبديل
   ومصفوفة القطاعات كمسارات متوازية، مع عدم تعديل ملفات العقد العامة نفسها.

## 3. تفاصيل المهام

### المرحلة 0 — تثبيت خط الأساس

#### `F0-01` — تثبيت خط أساس التحقق ومصفوفة شروط `v1`

- **المشكلة التي تحلها:** نتائج الوثيقة تصف حالة محددة من الشجرة، وبعض اختبارات
  `gapred` لا تصل إلى assertion الذي يفترض أن تختبره. من دون خط أساس واضح قد
  تُفسّر أعطال إعداد الاختبار على أنها إثبات لسلوك المنتج، أو قد تختفي فجوة
  دون اختبار يغطيها.
- **النطاق:** إعادة إنتاج البناء والاختبارات والفحوصات الواردة في وثيقة
  التحقق، وتصنيف كل نتيجة إلى نجاح/فشل منتج/فشل إعداد اختبار/غير قابلة للتكرار.
  ربط شروط `v1` الثمانية بالاختبارات أو البوابات المستهدفة.
- **خارج النطاق:** إصلاح عيوب التنفيذ، تغيير عقود عامة، أو تحديث نتائج تقرير
  التحقق الأصلي.
- **خطوات التنفيذ:**
  1. تشغيل أوامر البناء والفحص والاختبارات الافتراضية واختبارات PostgreSQL
     وبوابات التنسيق ونقاء API الواردة في المرجع.
  2. إعادة تشغيل اختبارات `gapred` وتسجيل assertion المتوقع وما إذا كان الاختبار
     يصل إليه؛ إصلاح بيانات/تهيئة الاختبار فقط إذا كانت تمنع قياس الفجوة،
     دون تغيير سلوك الإنتاج في هذه المهمة.
  3. إنشاء مصفوفة داخل وصف/نتائج المهمة تربط كل شرط `v1` باختبار حالي أو اختبار
     مطلوب ضمن المهام اللاحقة.
  4. تثبيت إصدار PostgreSQL المستخدم فعلياً لكل تشغيل وتسجيل المتطلبات البيئية.
- **الاعتماديات:** لا شيء.
- **معايير القبول:**
  - نتائج الأوامر الأساسية موثقة مع الإصدار والبيئة والأمر الدقيق.
  - لكل فشل معروف تصنيف واضح، ولا يُعد فشل إعداد الاختبار نجاحاً أو فشلاً
    للمنتج.
  - لكل شرط من الشروط الثمانية مهمة إغلاق واختبار/بوابة إثبات محددان.

### المرحلة 1 — تثبيت العقود العامة وحدود التطبيق

#### `C1-01` — توفير عقد Master Data عام

- **المشكلة التي تحلها:** لا يستطيع المستهلك العام إنشاء الشركة والحسابات
  والفترات اللازمة لاستخدام SDK دون استيراد `internal/masterdata`، كما تتسرب
  أنواع داخلية من تواقيع التخزين.
- **النطاق:** تصميم وتوفير API/SPI عامة typed لعمليات Master Data التي يحتاجها
  مستهلك SDK، على الأقل إنشاء/قراءة الشركة والحساب والسنة المالية والفترة،
  والتحقق من الأخطاء والقدرات غير المدعومة. اختيار موضع العقد بين
  `pkg/spi/masterdata` و`pkg/api/v1/masterdata` قرار تنفيذ يلتزم بأنواع عامة
  مستقرة.
- **خارج النطاق:** واجهة إدارة شاملة لكل بيانات المؤسسة، تغيير قواعد الترحيل،
  أو كشف أنواع `internal/*` تحت أسماء مستعارة.
- **خطوات التنفيذ:**
  1. حصر عمليات Master Data التي يحتاجها مثال مستهلك مستقل واختبارات SDK.
  2. تعريف DTOs ومعرّفات عامة typed، وعقود التخزين/الخدمة اللازمة دون اعتماد
     الحزمة العامة على `internal/*`.
  3. تنفيذ موائمات Memory وPostgreSQL على العقد نفسه، مع أخطاء واضحة للقدرات
     غير المنفذة.
  4. إضافة اختبارات عقد مشتركة للتحقق من السلوك نفسه للمخزنين.
- **الاعتماديات:** `F0-01`.
- **معايير القبول:**
  - يمكن إعداد الشركة والحساب والسنة والفترة عبر حزم عامة فقط.
  - لا يحتوي العقد العام على أنواع أو imports من `internal/*`.
  - موائمات Memory وPostgreSQL تجتازان اختبارات العقد نفسها، ولا يوجد نجاح
    صوري عند غياب قدرة مطلوبة.

#### `C1-02` — تعريف حدود المعاملة وعقود Application/Posting العامة

- **المشكلة التي تحلها:** عمليات الترحيل وIdempotency موزعة بين استدعاءات تخزين
  منفصلة، كما أن SPI الحالي لا يعبّر عن حدود وحدة العمل أو بوابات السياسة
  والاعتماد.
- **النطاق:** تحديد عقود عامة typed لحدود المعاملة/وحدة العمل، وواجهات
  Idempotency، وبوابات السياسة والاعتماد اللازمة لمسار التطبيق. تحديد ملكية
  المعاملة وتسلسل الحجز والتحقق والترحيل وحفظ النتيجة، وكيفية تمثيل حالة
  قابلة للاستئناف إذا لم يمكن تنفيذها في معاملة واحدة.
- **خارج النطاق:** إعادة تصميم كل واجهات التخزين أو نقل كل منطق المجال إلى
  SPI، وإضافة نظام رسائل/Outbox ما لم تثبت الحاجة إليه في التصميم.
- **خطوات التنفيذ:**
  1. رسم تسلسل ProcessEvent/Post/Reverse الحالي وتحديد حدود الاتساق المطلوبة.
  2. اعتماد واجهات transaction manager/unit of work وidempotency repository
     والـ ports الضرورية، بما يتيح المعاملة الواحدة أو State Machine موثقة.
  3. تحديد سلوك التعارض، إعادة المحاولة، الانهيار، وطلب المفتاح نفسه بحمولة
     مختلفة.
  4. اعتماد العقود قبل تنفيذ تغييرات التخزين وSDK، وتوثيق متطلبات كل سائق.
- **الاعتماديات:** `F0-01`.
- **معايير القبول:**
  - العقد يعبّر صراحة عن ذرية الحجز/الترحيل/حفظ النتيجة أو عن آلية استئناف
    مكافئة، ولا يترك المعاملة ضمنية.
  - حالات `processing` العالقة والتعارض وإعادة المحاولة محددة السلوك.
  - الواجهات مستقلة عن تفاصيل PostgreSQL وMemory، ومناسبة لاختبار عقد
    مشترك لكليهما.

#### `C1-03` — تصحيح أنواع API وإكمال التحويل ذهاباً وإياباً

- **المشكلة التي تحلها:** بعض معرفات API aliases متبادلة لأنواع UUID، وحقول
  مثل معرف السنة والفترة ومعرف سطر القيد تستخدم أنواعاً غير صحيحة. كما أن
  التحويل الداخلي/الخارجي يفقد حقولاً مثل `SourceModule`.
- **النطاق:** أنواع معرفات مستقلة ومناسبة لكل كيان، وتصحيح أنواع حقول
  `FiscalYear` و`FiscalPeriod` و`EntryLine` والأبعاد، وإكمال mapping ثنائي
  الاتجاه لكل الحقول المدعومة.
- **خارج النطاق:** تغيير دلالة الحقول المحاسبية أو إضافة بيانات لم يطلبها
  العقد العام، وإعادة تسمية API عامة دون خطة توافق.
- **خطوات التنفيذ:**
  1. جرد DTOs وحقول التحويل ومواضع استخدام المعرفات.
  2. استبدال aliases المتداخلة بأنواع مميزة مع تحويلات صريحة عند حدود
     التخزين/المحرك.
  3. إضافة اختبارات round-trip لكل DTO مع تغطية الحقول الاختيارية والحقول
     التي كانت تفقد عند الإرجاع.
  4. معالجة التوافق المصدرّي إذا كانت أنواع API منشورة أو مستخدمة داخلياً.
- **الاعتماديات:** `F0-01`؛ التنسيق مع `C1-01` لتوحيد أنواع Master Data
  العامة قبل الدمج.
- **معايير القبول:**
  - لا يمكن تمرير `CompanyID` بدلاً من `EntryLineID` دون تحويل صريح.
  - جميع الحقول المعرّفة في API تحفظ في اتجاهي التحويل أو يُرفض عدم دعمها
    صراحة.
  - اختبارات round-trip تثبت عدم فقدان الحقول، ومنها `SourceModule`.

#### `C1-04` — جعل تهيئة SDK تفشل مبكراً وبوضوح

- **المشكلة التي تحلها:** يمكن لـ Builder إرجاع Reporting/Governance services
  مع مخزن غير متوفر، ولا يظهر الخطأ إلا عند أول استخدام؛ كما أن غياب
  اعتماديات التطبيق لا يمنع دائماً إنشاء Engine.
- **النطاق:** التحقق عند البناء من المكونات الإلزامية بحسب القدرات المفعلة،
  وإرجاع أخطاء typed واضحة، وتوحيد عقد `RunScheduledJobs` ليكون typed بدلاً
  من `interface{}` عند الحاجة.
- **خارج النطاق:** جعل كل مكون اختيارياً أو تغيير إعدادات وحدات المعايير
  خارج الحالات المتعلقة بتهيئة SDK وعقوده.
- **خطوات التنفيذ:**
  1. تعريف قائمة الاعتماديات الإلزامية والاختيارية لكل قدرة عامة.
  2. تعديل Builder لرفض التركيب غير المكتمل قبل إرجاع Engine.
  3. إزالة `interface{}` من عقود الوظائف المجدولة واستبداله بواجهة واضحة
     واختبارها.
  4. إضافة اختبارات حالات النجاح والفشل ونقص كل اعتماد إلزامي.
- **الاعتماديات:** `C1-01` و`C1-02`.
- **معايير القبول:**
  - يفشل البناء فوراً برسالة قابلة للتشخيص عند غياب Reporting/Governance أو
    أي اعتماد مطلوب لقدرة مفعّلة.
  - لا يعاد كائن خدمة يبدو صالحاً ثم يفشل عند أول استدعاء بسبب تركيب ناقص.
  - عقود الوظائف المجدولة typed، واختبارها يغطي أخطاء التهيئة والتسجيل.

#### `C1-05` — اختبار وحدات المعايير وسلوك قواعدها الفعلي

- **المشكلة التي تحلها:** وحدات IFRS/IAS تسجل قواعدها، لكن لا توجد اختبارات
  تثبت تسجيل الوحدات الفعلية أو أن القواعد تنتج الحسابات والأثر المتوقعين؛
  اختبار Builder بوحدة وهمية لا يثبت سلوك الوحدات الحقيقية.
- **النطاق:** اختبارات وحدات للمعايير المتاحة، والتحقق من تسجيل القواعد،
  الاعتماديات، والحسابات/الأثر المحاسبي الذي تنتجه كل قاعدة قابلة للاختبار.
- **خارج النطاق:** إعادة تفسير المعايير أو اعتماد محتوى محاسبي جديد دون مراجعة
  مالك المجال، وتنفيذ وحدات معايير غير موجودة.
- **خطوات التنفيذ:**
  1. حصر الوحدات الفعلية (`ifrs15` و`ifrs16` و`ifrs9` و`ias12`) والقواعد
     المسجلة وعقودها.
  2. إضافة اختبارات تهيئة وتسجيل تثبت عدم إسقاط أخطاء الاعتماديات أو التسجيل.
  3. اختبار مخرجات قواعد مختارة، بما فيها الحسابات المتوقعة حيث تنص القاعدة
     عليها (مثل حسابات IFRS 15 المشار إليها في التقرير)، واتزان القيد.
  4. إثبات أن الوحدة لا تستخدم حساباً غير معتمد من Master Data ولا تنتج
     أحداثاً غير مدعومة بصمت.
- **الاعتماديات:** `C1-01` و`C1-04`؛ يعتمد اختبار الأثر النهائي كذلك على
  `W2-04` عند استخدام Mapping الحدث العام.
- **معايير القبول:**
  - لكل وحدة موجودة اختبار يثبت تسجيل قواعدها ومعالجة الاعتماديات والأخطاء.
  - اختبارات القواعد المختارة تتحقق من الحسابات والمبالغ والتوازن، لا من
    عدد القواعد أو السطور فقط.
  - فشل قاعدة أو اعتماد مطلوب ينتج خطأ واضحاً ولا يُسقط بصمت.

### المرحلة 2 — إغلاق سلامة مسار المحاسبة

#### `W2-01` — توحيد الترحيل والعكس عبر Application/Posting Engine

- **المشكلة التي تحلها:** يستطيع SDK تجاوز محرك Posting عبر fallback مباشر إلى
  `store.PostEntry` أو عكس يدوي، كما أن محرك SDK لا يطبق سياسات واعتماداً
  وأبعاداً ومراقبة، ويخلط بين منشئ القيد ومنفذ ترحيله.
- **النطاق:** حصر كل عمليات Ledger العامة في مسار التطبيق ومحرك Posting؛
  توصيل إعدادات السياسة والاعتماد والأبعاد والمراقبة وMaker-Checker؛ فصل
  هوية المنشئ عن هوية المرحّل؛ حذف المسارات الاحتياطية التي تتجاوز المحرك
  أو تحويلها إلى أخطاء قدرة صريحة.
- **خارج النطاق:** إعادة كتابة محرك Posting أو فرض سياسة أعمال جديدة غير
  معرفة حالياً، وتغيير واجهات المستهلك بقدر يتجاوز ما يتطلبه فصل Maker/Checker.
- **خطوات التنفيذ:**
  1. تتبع كل طرق Post/Reverse في SDK والجذر وموائمات التخزين وتحديد أي تجاوز.
  2. تركيب Posting Engine مع وحدات السياسة والاعتماد والأبعاد والمراقبة
     الموجودة، مع سلوك fail-closed عند وجوب اعتماد غير مهيأ.
  3. إزالة fallback المباشر إلى التخزين؛ إرجاع `ErrCapabilityNotImplemented`
     أو خطأ typed مكافئ عند غياب قدرة لازمة.
  4. إضافة هوية منفذ الترحيل منفصلة عن `CreatedBy` وتطبيق Maker-Checker.
  5. حفظ سبب العكس وتحديد/التحقق من تاريخ العكس عبر العقد العام.
- **الاعتماديات:** `C1-02` و`C1-04`.
- **معايير القبول:**
  - كل استدعاء SDK للترحيل/العكس يمر عبر Application/Posting Engine، ولا
    يوجد fallback ينفذ الترحيل مباشرة.
  - السياسة والاعتماد والأبعاد والمراقبة موصولة، وغياب بوابة اعتماد مطلوبة
    يرفض الترحيل.
  - المنشئ والمرحّل هويتان منفصلتان، وسبب العكس محفوظ في السجل الناتج.
  - اختبارات تثبت أن السائق ذي القدرات الناقصة يفشل بوضوح ولا يتجاوز المحرك.

#### `W2-02` — جعل Idempotency العامة ذرية وقابلة للاسترداد

- **المشكلة التي تحلها:** حجز المفتاح والترحيل وإكمال النتيجة تتم بمعاملات
  منفصلة؛ قد ينجح الترحيل وتفشل كتابة النتيجة، وتظل الحالة `processing`.
  كما لا تغطي بصمة الطلب كل بياناته، ولا توجد اختبارات PostgreSQL للمسار
  العام.
- **النطاق:** تنفيذ التسلسل على عقود `C1-02` في PostgreSQL وMemory، وتغطية
  بصمة الحمولة لكل المدخلات المؤثرة، ومعالجة حالات الانهيار والتزامن وإعادة
  التشغيل.
- **خارج النطاق:** تغيير سياسة الاحتفاظ بسجلات Idempotency أو بناء نظام
  Outbox مستقل إلا إذا كان ذلك هو النمط المعتمد في `C1-02`.
- **خطوات التنفيذ:**
  1. تنفيذ حجز المفتاح والتحقق من البصمة والترحيل وحفظ النتيجة ضمن المعاملة
     أو State Machine القابلة للاستئناف المتفق عليها.
  2. شمول البصمة `EventID` و`Payload` و`Dimensions` وبيانات JournalDraft
     والحقول الأخرى التي تغيّر الأثر.
  3. تعريف معالجة الانهيار في كل نقطة انتقال، وآلية استعادة/إعادة محاولة
     للحالات العالقة دون ترحيل مكرر.
  4. إضافة اختبارات PostgreSQL متزامنة للمفتاح نفسه، وإعادة الطلب، وتعارض
     الحمولة، والفشل بين المراحل، وإعادة التشغيل.
  5. إضافة اختبارات مكافئة على Memory ضمن عقد مشترك.
- **الاعتماديات:** `C1-02` و`W2-01`.
- **معايير القبول:**
  - لا ينتج عن إعادة الطلب المتماثل أكثر من قيد واحد، وتُعاد النتيجة الأصلية
    وفق العقد.
  - طلب مختلف تحت المفتاح نفسه يرفض بتعارض صريح، بما في ذلك اختلاف `EventID`
    أو `Payload` أو `Dimensions`.
  - حالات الانهيار لا تترك مفتاحاً عالقاً بلا مسار استرداد، ولا تسمح بترحيل
    مكرر عند الاستئناف.
  - اختبارات PostgreSQL للتزامن وإعادة التشغيل والفشل تمر، ولا تقتصر
    التغطية على `subledger`.

#### `W2-03` — إغلاق فجوات Posting والحوكمة المختبرة بـ `gapred`

- **المشكلة التي تحلها:** اختبارات الفجوات تكشف غياب إعادة فحص الفترة داخل
  المعاملة، وبصمات غير كاملة، وثغرات في العكس وإعادة فتح الفترات وبوابة
  الاعتماد. وبعض الاختبارات الحالية لا تصل إلى الحالة المقصودة بسبب إعداد
  غير صحيح.
- **النطاق:** إصلاح وإثبات `GAP-PST-01` إلى `GAP-PST-06` و`GAP-GOV-01`
  و`GAP-GOV-03` وفق الحالات المحددة في وثيقة التحقق، مع معالجة إعداد
  الاختبارات عند الحاجة.
- **خارج النطاق:** إدخال فجوات جديدة غير مذكورة في المرجع، أو إخفاء الاختبارات
  الحمراء بتحويلها إلى `Skip` من دون سبب وخطة إغلاق معتمدة.
- **خطوات التنفيذ:**
  1. إصلاح `GAP-PST-01` بإعادة فحص صلاحية الفترة داخل حدود المعاملة لمنع
     TOCTOU.
  2. إصلاح `GAP-PST-02` لتشمل بصمة المسودة الفترة ورقمها وتفويض التسوية
     ومعرف القيد الأصلي.
  3. إصلاح `GAP-PST-03` لتشمل بصمة القيد `SourceEventID`.
  4. إصلاح `GAP-PST-04` و`GAP-PST-05` و`GAP-PST-06` للعكس الذري والتحقق
     من السطور والحالات المستهدفة، مع جعل إعداد الاختبار صالحاً للوصول إلى
     assertion.
  5. إصلاح `GAP-GOV-01` لمنع إعادة فتح فترة مغلقة نهائياً، و`GAP-GOV-03`
     لجعل الاعتماد يفشل مغلقاً.
  6. تشغيل اختبارات PostgreSQL وذاكرة لكل الحالات ذات الصلة.
- **الاعتماديات:** `C1-02` و`W2-01`. يمكن إعداد/تصحيح fixtures بالتوازي مع
  `C1-02`، لكن لا تُعتمد النتائج قبل استقرار حدود المعاملة.
- **معايير القبول:**
  - كل اختبار فجوة يصل إلى assertion المقصود ويفشل على السلوك القديم/ينجح
    بعد الإصلاح.
  - الفترة يعاد فحصها داخل المعاملة؛ والبصمات تشمل الحقول المذكورة.
  - العكس ذري ومتحقق من سلامة السطور، والفترة المغلقة نهائياً لا يعاد فتحها،
    والاعتماد المطلوب لا يفشل مفتوحاً.
  - لا توجد حالات `Skip` جديدة لإخفاء فجوة، وتشغيل مصفوفة `gapred` لا ينتج
    إخفاقات غير مصنفة.

#### `W2-04` — تصحيح بناء الأحداث والتحويلات المحاسبية في SDK

- **المشكلة التي تحلها:** مسار الحدث يضع سعر صرف `1` بدلاً من سعر حقيقي،
  ولا يملأ قالب الوصف، ويتجاهل `Payload` و`Dimensions`، كما توجد دالة عامة
  قديمة تخمّن حسابات.
- **النطاق:** جعل Mapping حدث SDK صريحاً وكاملاً: تحويل العملة عند توفر
  اعتماد سعر الصرف، إدراج بيانات الحدث في الوصف، التعامل مع Payload والأبعاد،
  وإزالة إنشاء الحسابات التخمينّية من المسار العام.
- **خارج النطاق:** تحديد أسعار صرف أو قواعد تحويل محاسبية من دون مصدر/سياسة
  معتمدة، أو وضع حسابات افتراضية بديلة داخل SDK.
- **خطوات التنفيذ:**
  1. تحديد عقد مصدر سعر الصرف وعملة الشركة الوظيفية، وسلوك typed صريح عند
     عدم توافر السعر أو البيانات المطلوبة.
  2. تطبيق التحويل وفق المصدر والسياسة المعتمدين، ورفض العملية بدلاً من
     افتراض `ExchangeRate=1`.
  3. تنسيق `DescriptionTemplate` من حقول الحدث بقواعد موثقة واختبارات.
  4. ربط `Payload` و`Dimensions` بالـ mapping والبصمات، أو رفضها صراحة عند
     عدم دعم الحقل.
  5. إزالة/تعطيل `events.EvaluateAndConstructEntry` العامة التي تنشئ حسابات
     عشوائية أو إحالتها إلى واجهة عامة تتطلب حسابات معتمدة.
- **الاعتماديات:** `C1-01` و`C1-03` و`C1-04`.
- **معايير القبول:**
  - لا يستخدم سعر صرف افتراضي `1` عند اختلاف العملة؛ غياب السعر ينتج خطأ
    واضحاً ولا يولد قيداً.
  - الوصف النهائي يعكس بيانات الحدث ولا يبقى نص القالب حرفياً.
  - Payload والأبعاد إما تؤثر في mapping والبصمة أو تُرفض صراحة.
  - لا ينشئ SDK أو دالة عامة قيداً بحسابات عشوائية/افتراضية.

### المرحلة 3 — إثبات الاستهلاك والتبديل والأثر المحاسبي

#### `P3-01` — إنشاء مستهلك خارجي مستقل فعلياً

- **المشكلة التي تحلها:** اختبار الاستهلاك الحالي داخل الوحدة نفسها ويستورد
  `internal/masterdata`؛ لذلك لا يثبت أن مستهلكاً مستقلاً يستطيع استعمال SDK.
- **النطاق:** مشروع اختبار تحت `test/external_consumer/` بملف `go.mod` خاص،
  يستخدم العقود العامة فقط، ويبني ويشغّل رحلة إعداد Master Data واستخدام SDK.
- **خارج النطاق:** نشر الحزمة إلى سجل عام أو إدارة إصدار/توزيع الإنتاج.
- **خطوات التنفيذ:**
  1. إنشاء وحدة Go مستقلة مع `replace` محلي مؤقت أو آلية الإصدار المتاحة.
  2. تنفيذ مثال يستخدم API العامة لإعداد الشركة والحساب والفترة ثم إنشاء
     حدث/قيد وقراءة النتيجة.
  3. إضافة فحص يمنع أي import من `internal/*` داخل مشروع المستهلك.
  4. إضافة أمر build/test للمشروع إلى CI بعد استقرار العقود.
- **الاعتماديات:** `C1-01` و`C1-03` و`C1-04`.
- **معايير القبول:**
  - `go build ./...` و`go test ./...` ينجحان من مجلد وحدة المستهلك المستقلة.
  - المستهلك لا يستورد أي مسار `internal/*` ولا يحتاج إلى DTO داخلي.
  - الرحلة تستخدم Master Data العامة وSDK فقط، وتثبت النتيجة المحاسبية.

#### `P3-02` — إثبات تبديل Memory وPostgreSQL دون تغيير كود المستهلك

- **المشكلة التي تحلها:** اختبار الاستقلالية الحالي يستخدم Memory فقط، واختبار
  parity يتجاوز SDK ويستدعي التخزين مباشرة؛ لذلك لا يثبت ثبات سلوك المستهلك
  عند تغيير السائق.
- **النطاق:** تشغيل نفس سيناريو المستهلك/العقد على Memory وPostgreSQL، ومقارنة
  المخرجات والأخطاء والحالات الأساسية عبر SDK وواجهات التطبيق.
- **خارج النطاق:** ضمان تطابق الأداء أو الخصائص الخاصة بكل قاعدة بيانات،
  واختبارات الضغط/التحمل.
- **خطوات التنفيذ:**
  1. استخراج سيناريو المستهلك في اختبار عقد قابل لإعادة الاستخدام.
  2. تشغيل السيناريو نفسه على Memory وPostgreSQL مع إعدادات مختلفة للسائق
     فقط، من دون تغيير منطق المستهلك.
  3. مقارنة نتيجة الترحيل والعكس وIdempotency والتقارير الأساسية والأخطاء
     ذات الدلالة.
  4. التأكد من أن السائق الذي لا يدعم قدرة لا ينفذ fallback صامتاً.
- **الاعتماديات:** `P3-01` و`W2-01` و`W2-02` و`C1-01`.
- **معايير القبول:**
  - نفس مصدر كود المستهلك ينجح على Memory وPostgreSQL.
  - النتائج المحاسبية والحالات المرئية للمستهلك متكافئة في السيناريوهات
    المشتركة، مع توثيق أي اختلاف مقصود.
  - لا يعتمد الاختبار على استدعاءات مباشرة إلى `SaveDraftContext` أو
    `PostAtomicContext` بدلاً من SDK.

#### `P3-03` — تنفيذ موائمات قطاعية واختبارات أثر محاسبي

- **المشكلة التي تحلها:** توجد قوالب فقط للتجزئة والزراعة وSaaS، والاختبار
  الحالي يتوقع رفض أحداث القطاع ولا يثبت الحسابات أو الأثر المحاسبي.
- **النطاق:** موائمات قطاعية منفصلة للتجزئة والزراعة وSaaS، تسجيلها بعقود
  typed في Builder، وربط أوامر القطاع بـ AccountingCommand/JournalDraft
  باستخدام Master Data معتمدة.
- **خارج النطاق:** محرك ERP خاص بكل قطاع، افتراض دليل حسابات عالمي، أو اعتماد
  معالجة معيارية غير موثقة في قواعد القطاع.
- **خطوات التنفيذ:**
  1. تعريف عقد إدخال/إخراج لكل Adapter مع توثيق الحقول والافتراضات.
  2. ربط القواعد/القوالب الحالية بمسار تسجيل عام typed، واسترجاع الحسابات
     من Master Data بدلاً من توليد حسابات.
  3. بناء Adapter واختبارات لكل قطاع؛ يمكن تنفيذ القطاعات بالتوازي بعد
     استقرار العقد.
  4. اختبار الحسابات المدينة والدائنة والمبالغ والعملات وتوازن القيد وحالات
     البيانات الناقصة.
  5. إثبات اختلاف الأثر المحاسبي بين القطاعين/الثلاثة بطريقة متوقعة ومراجعة.
- **الاعتماديات:** `C1-01` و`C1-03` و`W2-04`. تعتمد اختبارات الترحيل النهائي
  أيضاً على `W2-01`.
- **معايير القبول:**
  - يوجد Adapter قابل للاستخدام لكل من التجزئة والزراعة وSaaS، وليس قالباً
    غير مربوط بمسار التنفيذ.
  - الاختبارات تثبت الحسابات الفعلية والمبالغ والعملة والتوازن، لا عدد السطور
    أو قبول الحدث فقط.
  - الحسابات المعتمدة تأتي من Master Data، والحساب غير الموجود ينتج خطأ
    صريحاً.
  - يثبت الاختبار أن قواعد القطاعات تنتج آثاراً محاسبية متمايزة وفق المدخلات.

#### `P3-04` — إزالة تسرب `internal/*` وتقوية بوابة نقاء API

- **المشكلة التي تحلها:** حزم `pkg/sdk` وبعض الأنواع العامة تعتمد مباشرة على
  `internal/*`، كما أن سكربت النقاء الحالي يكتشف مخالفة لكنه غير مشغّل في CI
  ولا يغطي كل السطح العام.
- **النطاق:** إزالة الاعتماد الداخلي من الحزم العامة أو عزل سطح legacy بقرار
  واضح، توسيع فحص النقاء، وتشغيله ضمن CI.
- **خارج النطاق:** نقل كل تنفيذ داخلي من مكانه أو منع الحزم الداخلية من
  الاعتماد بعضها على بعض.
- **خطوات التنفيذ:**
  1. جرد كل استيرادات `internal/*` من الحزم العامة والجذر.
  2. استبدال الاعتماد بعقود عامة/محولات عند الحدود، أو وضع واجهات الجذر
     الملوثة في مسار legacy موثق غير مقدم كـ API عام.
  3. توسيع `check_public_api_purity.sh` لتغطية جميع الحزم العامة ذات الصلة
     ومعالجة النتائج الإيجابية الكاذبة إن وجدت.
  4. إضافة تشغيل البوابة إلى CI مع اختبار يثبت أنها تفشل عند إدخال import
     داخلي ممنوع.
- **الاعتماديات:** `C1-01` و`C1-02` و`C1-03` و`C1-04`.
- **معايير القبول:**
  - فحص النقاء ينجح على كل الحزم العامة المستهدفة.
  - CI يشغّل الفحص، وأي مخالفة جديدة توقف البناء.
  - المستهلك الخارجي لا يعتمد على أنواع داخلية، ولا تُعرض الواجهات الملوثة
    باعتبارها API مستقرة.

#### `P3-05` — إصلاح التنسيق وتفعيل بوابات اختبارات الفجوات في CI

- **المشكلة التي تحلها:** توجد ملفات Go غير منسقة، كما أن مصفوفة `gapred`
  الحمراء لا تعمل كبوابة مستمرة؛ لذلك قد تتراكم عيوب أو يتراجع إصلاح بعد
  دمجه.
- **النطاق:** تنسيق الملفات المتأثرة، تثبيت فحص `gofmt` في CI، وتشغيل اختبارات
  `gapred`/اختبارات PostgreSQL التي أصبحت صالحة بعد `W2-03` ضمن بوابة مناسبة.
- **خارج النطاق:** تخفيف شروط الاختبارات أو تحويل إخفاقات المنتج إلى `Skip`
  لتجاوز CI.
- **خطوات التنفيذ:**
  1. تشغيل `scripts/check_gofmt.sh` وتنسيق الملفات التي يفحصها؛ مراجعة diff
     لضمان عدم إدخال تغييرات وظيفية غير مقصودة.
  2. إضافة بوابة التنسيق إلى CI إن لم تكن فعالة على كامل الشيفرة المقصودة.
  3. إضافة مصفوفة `gapred` بعد استقرار الاختبارات في `W2-03` مع توفير
     PostgreSQL وإعداداته على نحو صريح.
  4. جعل تقارير الفشل تحدد الاختبار والحزمة والسبب، وتوثيق أي استثناء مؤقت
     وفق آلية واضحة وموعد إزالة.
- **الاعتماديات:** `F0-01` و`W2-03` و`P3-04`.
- **معايير القبول:**
  - `scripts/check_gofmt.sh` ينجح، وCI يمنع إدخال ملفات غير منسقة.
  - اختبارات الفجوات المعتمدة تنفذ في CI على PostgreSQL المطابق ولا تُتجاوز
    بسبب غياب اتصال أو إعداد.
  - لا توجد `Skip` جديدة لإخفاء assertion فاشل أو فجوة حرجة.

### المرحلة 4 — جاهزية الخدمة والتوزيع

#### `S4-01` — إكمال عقود gRPC وتسجيل الخدمات الفعلية

- **المشكلة التي تحلها:** خادم gRPC يبدأ دون تسجيل خدمات، ولا توجد ملفات
  مولدة من ملفات Proto؛ لذلك المنفذ لا يقدم API gRPC قابلة للاستهلاك.
- **النطاق:** مراجعة/إكمال تعريفات Proto الموجودة، توليد الكود بأسلوب موحد،
  تنفيذ الخدمات المعلنة وتسجيلها، وإضافة اختبارات عميل/خادم.
- **خارج النطاق:** تصميم خدمات لا تدعمها متطلبات المنتج، أو بناء بوابة
  gRPC-HTTP شاملة ما لم تكن جزءاً من العقد الحالي.
- **خطوات التنفيذ:**
  1. حصر ملفات `proto/accounting/v1/*.proto` والعمليات المطلوبة والرسائل
     العامة الموافقة لعقود SDK.
  2. تثبيت أداة/أمر توليد قابل لإعادة الإنتاج وإضافة الناتج أو توليده في CI
     وفق نمط المشروع.
  3. تنفيذ وربط الخدمات بخدمات التطبيق العامة وتسجيلها على الخادم.
  4. إضافة اختبارات RPC للنجاح، والتحقق من المدخلات، والأخطاء، وعمليات
     الترحيل/الاستعلام المدعومة.
- **الاعتماديات:** `F0-01` و`C1-03`.
- **معايير القبول:**
  - الخدمات المطلوبة مسجلة ويمكن للعميل اكتشافها واستدعاؤها.
  - إعادة التوليد لا تنتج فرقاً غير مفسر، وCI يتحقق من التوليد أو اتساقه.
  - اختبارات gRPC تثبت الاستجابة والأخطاء دون استدعاء غير موصول.

#### `S4-02` — جعل HTTP آمناً تشغيلياً واختباره

- **المشكلة التي تحلها:** خدمة HTTP تستخدم `uuid.MustParse` بما قد يسبب panic،
  وتفتقر إلى حدود للطلب وtimeouts وgraceful shutdown وحماية مناسبة.
- **النطاق:** تحقق المدخلات وإرجاع 4xx بدلاً من panic، حدود حجم الطلب،
  timeouts، إيقاف منظم، ومصادقة/تفويض وفق نموذج الخدمة المعتمد، مع اختبارات
  HTTP.
- **خارج النطاق:** إعادة تصميم كل API أو إضافة نظام هوية جديد مستقل عن
  البنية المعتمدة.
- **خطوات التنفيذ:**
  1. استبدال parsing الذي قد يسبب panic بتحقق صريح ورسائل/رموز HTTP مناسبة.
  2. ضبط `ReadHeaderTimeout` وبقية timeouts وحدود جسم الطلب وفق الخدمة.
  3. تنفيذ `http.Server.Shutdown` وإغلاق الموارد عند الإيقاف أو الإشارة.
  4. تطبيق المصادقة والتفويض أو تكامل الخدمة مع الآلية المعتمدة، وتوثيق
     endpoints العامة والاستثناءات.
  5. اختبار حالات المدخلات غير الصالحة، الحجم الزائد، timeout، الرفض غير
     المصرح، والإيقاف.
- **الاعتماديات:** `F0-01`؛ يعتمد تطبيق المصادقة على آلية الهوية المتاحة
  بالمشروع ويجب عدم اختراع عقد بديل ضمن هذه المهمة.
- **حالة المصادقة للخدمة:** لم يُعثر على تكامل هوية HTTP معتمد في
  `accounting-service`؛ تبقى المصادقة/التفويض غير مطبقين، ولا تُعد نقاط
  النهاية المحمية مستوفاة حتى يُعتمد ذلك التكامل.
- **معايير القبول:**
  - معرف غير صالح ينتج 400 ولا يسبب panic.
  - حدود الطلب والـ timeouts فعالة ومختبرة.
  - الإيقاف المنظم يغلق الخادم والموارد ضمن المهلة.
  - endpoints المحمية ترفض الطلب غير المصرح، واختبارات HTTP تغطي ذلك.

#### `S4-03` — تنفيذ readiness ومقاييس تشغيلية حقيقية

- **المشكلة التي تحلها:** `/readyz` و`/metrics` تعيدان استجابات ثابتة لا تثبت
  اتصال التخزين أو جاهزية الخدمة ولا تعرضان قياسات فعلية.
- **النطاق:** readiness تعتمد على صحة الاتصالات والاعتماديات الإلزامية، ومقاييس
  فعلية للترحيل والفشل والكمون، مع اختبار الحالة السليمة وغير السليمة.
- **خارج النطاق:** منظومة مراقبة خارجية كاملة أو مقاييس مالية تكشف بيانات
  حساسة.
- **خطوات التنفيذ:**
  1. إضافة/استعمال واجهة فحص صحة للتخزين والاعتماديات المطلوبة.
  2. جعل `/readyz` يعيد نجاحاً فقط عندما تكون الخدمة قادرة على تنفيذ وظائفها
     الإلزامية، وإرجاع حالة غير جاهز عند فشل الاعتماد.
  3. ربط `/metrics` بمقاييس Posting/Failure/Latency فعلية باستخدام مكتبة
     الرصد الموجودة.
  4. إضافة اختبارات readiness مع مخزن متاح وغير متاح واختبارات تنسيق
     المقاييس.
- **الاعتماديات:** `C1-02` و`W2-01` و`S4-02`.
- **معايير القبول:**
  - `/readyz` يتغير تبعاً لحالة PostgreSQL/الاعتماد الإلزامي ولا ينجح
    اعتماداً على استجابة ثابتة.
  - المقاييس تتغير عند ترحيل ناجح وفشل، وتتضمن قياساً للكمون دون أبعاد
    تكشف بيانات حساسة.
  - اختبارات الحالة السليمة وغير السليمة تمر.

#### `S4-04` — توحيد بيئة Docker/CI والتحقق من تشغيل الخدمة

- **المشكلة التي تحلها:** إصدار PostgreSQL في Compose يختلف عن CI، ولا توجد
  بوابة موثوقة لبناء Docker وتشغيل اختبارات الخدمة والبروتوكولات.
- **النطاق:** توحيد إصدارات الأدوات/قاعدة البيانات، إضافة بناء صورة الخدمة
  واختبارات التكامل والخدمة إلى CI، وإثبات تشغيل readiness وHTTP/gRPC.
- **خارج النطاق:** نشر إنتاجي أو إدارة أسرار حقيقية أو تعديل إعدادات إنتاج
  غير لازمة لإعادة الإنتاج.
- **خطوات التنفيذ:**
  1. توحيد إصدار PostgreSQL بين Compose وCI (الإصدار المعتمد في خط الأساس أو
     إصدار أحدث متفق عليه).
  2. إضافة Docker build قابل للتكرار ويفشل عند أخطاء البناء.
  3. إضافة اختبارات خدمة HTTP/gRPC وreadyz على البيئة المطابقة.
  4. حفظ تقارير الاختبارات كجزء من نتائج CI وإظهار سبب الفشل بوضوح.
- **الاعتماديات:** `S4-01` و`S4-02` و`S4-03` و`F0-01`.
- **معايير القبول:**
  - إصدار PostgreSQL متطابق في ملفات التشغيل وCI.
  - صورة Docker تُبنى بنجاح من CI.
  - اختبارات HTTP وgRPC وreadiness تنفذ على الخدمة الفعلية لا على handlers
    معزولة فقط حيث يتطلب الاختبار التكامل.
  - لا تمر بوابة CI عند فشل build أو readiness أو اختبارات البروتوكول.

### المرحلة 5 — اعتماد النسخة

#### `G5-01` — تشغيل بوابة اعتماد `v1` وتوثيق القرار

- **المشكلة التي تحلها:** اجتياز بناء أو عدد محدود من الاختبارات لا يثبت
  شروط الاستهلاك الخارجي أو السلامة المحاسبية أو جاهزية الخدمة؛ كما لا يجوز
  وصف النسخة بأنها جاهزة مع فجوات حاسمة مؤجلة.
- **النطاق:** تشغيل مصفوفة اعتماد موحدة على commit مرشح، مراجعة الأدلة،
  وتوثيق قبول/رفض إعلان `v1`.
- **خارج النطاق:** إصلاح مهام غير منجزة داخل بوابة الاعتماد؛ تُعاد المهام إلى
  مساراتها الأصلية ثم يعاد تشغيل البوابة.
- **خطوات التنفيذ:**
  1. تشغيل `gofmt` و`go vet` و`go build` و`go test ./... -count=1`.
  2. تشغيل اختبارات `gapred` وPostgreSQL للعكس والترحيل وIdempotency،
     واختبارات عقد Memory/PostgreSQL.
  3. بناء واختبار المستهلك الخارجي والتحقق من عدم استيراده `internal/*`.
  4. تشغيل اختبارات القطاعات الثلاثة والتحقق من الحسابات والأثر والتوازن.
  5. تشغيل بوابة نقاء API وCI الكامل وDocker وHTTP/gRPC/readiness على
     إصدارات بيئة مطابقة.
  6. مراجعة شروط `v1` الثمانية وتسجيل رابط كل دليل ونتيجة كل شرط.
- **الاعتماديات:** كل مهام المراحل 1 إلى 4.
- **معايير القبول:**
  - شروط `v1` الثمانية مجتازة بأدلة قابلة لإعادة التشغيل.
  - لا توجد اختبارات فجوات حمراء أو `Skip` غير معتمد يخفي شرطاً حرجاً.
  - المستهلك الخارجي يعمل، وتبديل Memory/PostgreSQL لا يتطلب تغيير كود
    المستهلك.
  - خدمة HTTP/gRPC مبنية ومختبرة، والجاهزية والمقاييس تعكسان الحالة الفعلية.
  - قرار الإعلان موثق بوضوح؛ عند وجود شرط غير مجتاز يكون القرار «عدم إعلان
    `v1`» مع إرجاع المهمة إلى مسارها، لا قبولاً مشروطاً غير محدد.

## 5. بوابة شروط إعلان `v1`

لا يُعتمد الإعلان إلا بعد تحقق الأدلة التالية:

| شرط `v1` | دليل الإغلاق المطلوب |
| --- | --- |
| 1. مستهلك خارجي دون `internal/*` | `P3-01` ناجح مع فحص imports |
| 2. Ledger عبر Application/Posting | `W2-01` ناجح، ولا يوجد fallback يتجاوز المحرك |
| 3. ذرية الترحيل والعكس وIdempotency على PostgreSQL | `W2-02` و`W2-03` واختبارات PostgreSQL ناجحة |
| 4. بيانات وتقارير حقيقية وأخطاء قدرات صريحة | اختبارات العقد المشتركة في `C1-01` وعدم وجود stubs ضمن المسار المفعّل |
| 5. وحدات المعايير والعقود typed | `C1-04` و`C1-05` واختبارات تسجيل/اعتماديات الوحدات ومخرجات القواعد |

وتُشغّل كذلك بوابات الجودة: `gofmt`، `go vet`، `go build`، الاختبارات
الافتراضية، اختبارات `gapred`، وفحص نقاء API ضمن CI.

## 6. آلية التنفيذ وإدارة التوازي

1. كل مهمة لها فرع/PR مستقل، مع ذكر معرّف المهمة والاختبارات التي تثبت
   معايير قبولها.
2. تعيّن جهة واحدة لتنسيق تغييرات `C1-01` إلى `C1-03`، لأنها تغيّر حدود
   العقود العامة. تُدمج تلك التغييرات قبل اعتماد المستهلك الخارجي أو بدء
   موائمات تعتمد على API غير مستقر.
3. لا يعدّ «نجاح البناء» معيار قبول بدلاً من الاختبارات السلوكية المحددة لكل
   مهمة، خصوصاً اختبارات PostgreSQL وIdempotency والعكس.
4. عند اكتشاف فجوة إضافية، تسجل كمهمة جديدة مع نطاق واعتماديات ومعايير قبول،
   ولا تُضاف بصمت إلى مهمة جارية.
5. لا تحول الاختبارات الحمراء إلى `Skip` لإمرار CI. أي استثناء مؤقت يحتاج
   سبباً ومخاطر ومالكاً وموعد إزالة، ولا يعفي من شرط `v1` الحرج.
6. بعد كل دمج في مسار الترحيل أو API العامة، يعاد تشغيل الاختبارات المتأثرة
   وبوابات التكامل ذات الصلة قبل بدء الأعمال التابعة.
