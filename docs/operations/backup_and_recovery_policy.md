# سياسة النسخ الاحتياطي والاستعادة لـ PostgreSQL

- **الحالة:** سياسة تشغيلية؛ يجب اعتماد القيم التشغيلية لكل بيئة قبل الإطلاق
- **المالك:** مالك الخدمة + مسؤول قاعدة البيانات
- **النطاق:** قواعد PostgreSQL التي تخزن بيانات المحاسبة
- **آخر مراجعة:** 2026-11-16

## 1. متطلبات التشغيل

- عرّف واعتمد لكل بيئة **RPO** و**RTO** وفترة الاحتفاظ قبل الإنتاج. لا يفرض المستودع مزوداً سحابياً أو أرقاماً ثابتة؛ سجل الأهداف المعتمدة ومكان النسخ ومشغل الاستعادة ضمن وثائق تشغيل البيئة.
- خذ نسخاً مشفرة في نطاق فشل منفصل عن قاعدة البيانات، وقيّد صلاحيات الإنشاء والقراءة والاستعادة. لا تضع كلمات المرور في سطر الأوامر أو الملفات الموثقة؛ استخدم آلية أسرار معتمدة أو `PGPASSFILE`.
- للاستعادة الزمنية الحقيقية (PITR)، يلزم **نسخ قاعدة أساسي متوافق وأرشيف WAL متصل ومتحقق منه** من نقطة النسخ وحتى الهدف. نسخة `pg_dump` وحدها ليست PITR.
- لا تعلن عن نجاح سياسة النسخ قبل نجاح استعادة دورية في قاعدة معزولة، وتسجيل نقطة الاستعادة والمدة ونتائج فحوصات ما بعد الاستعادة.

## 2. تكوين النسخ

اختر وادعم أحد المسارين أو كليهما، وفق نسخة PostgreSQL وطريقة تشغيلها:

### نسخ مادية وPITR

فعّل أرشفة WAL حسب دليل إصدار PostgreSQL المستخدم، وانقل سجلات WAL إلى تخزين مستقل مع التحقق من نجاح كل أرشفة ومراقبة تأخرها ومساحتها. خذ نسخاً أساسياً باستخدام أداة PostgreSQL أو ميزة النسخ الاحتياطي المعتمدة لدى المشغل. مثال لأمر `pg_basebackup` بصيغة tar مع تضمين WAL المتدفق:

```bash
pg_basebackup --host="$PGHOST" --username="$PGUSER" --pgdata="$BACKUP_DIR" \
  --format=tar --gzip --wal-method=stream --progress
```

وفّر `PGHOST` و`PGUSER` و`BACKUP_DIR` ومصادقة قاعدة البيانات من بيئة التشغيل الآمنة. تحقق من رمز الخروج، حجم الملفات، سلامة النقل، ووجود سلسلة WAL المطلوبة؛ نجاح الأمر وحده لا يثبت إمكانية الاستعادة.

### نسخة منطقية

لنسخة منطقية كاملة قابلة للاستعادة إلى إصدار PostgreSQL متوافق، يمكن استخدام:

```bash
pg_dump --host="$PGHOST" --username="$PGUSER" --dbname="$PGDATABASE" \
  --format=custom --file="$BACKUP_FILE"
```

استعدها إلى قاعدة فارغة متوافقة باستخدام `pg_restore --exit-on-error --dbname="$RESTORE_DATABASE" "$BACKUP_FILE"`. تحقّق من الأدوار والامتدادات والصلاحيات المطلوبة كلٌّ على حدة؛ تفريغ قاعدة البيانات لا يضمن حفظ إعدادات الخادم أو الأدوار العامة. لا تستخدم تفريغ جداول منتقاة كنسخة مستأجر محاسبية متسقة دون أداة تصدير مدركة لحدود الشركة والقيود والعلاقات وRLS.

## 3. نشر الهجرات والنسخ الاحتياطي

1. راجع التوافق Expand/Contract وخطة المعالجة في [`migration_policy.md`](../migration_policy.md).
2. قبل هجرة إنتاجية، تحقق من وجود نقطة استعادة حديثة يمكن الوصول إليها، ومن استعادة سابقة ناجحة ضمن فترة التشغيل المعتمدة؛ سجّل معرّف النسخة/هدف PITR وآخر نسخة WAL مؤكدة.
3. سجل إصدار التطبيق، `schema_migrations` (الإصدارات والأسماء والبصمات)، وقت البدء والانتهاء ومخرجات الهجرة. لا تعدّل ملفات هجرة مطبقة.
4. شغّل أمر الهجرة من إصدار النشر المقصود وبـ`DATABASE_URL` الصحيح:

   ```bash
   go run ./cmd/agy db migrate up
   ```

   واجهة الخدمة `postgres.New` تنفذ `EnsureSchema` أيضاً عند بدء التشغيل؛ لذلك يجب تنسيق نشر النسخ وتوافق كل إصدار مع المخطط. لا تعتبر تشغيل الأمر وحده اختبار توافق النسخ القديمة.
5. تحقق من اكتمال السلسلة والجاهزية بعد تشغيل إصدار الخدمة. لا تستخدم rollback للمخطط بديلاً عن استعادة النسخ.

## 4. تمرين الاستعادة الدورية

نفّذ تمريناً وفق RPO/RTO المعتمدين، وعلى بيئة معزولة لا تتصل بمسار الإنتاج:

1. اختر نسخة أساسية وأرشيف WAL موثقين ونقطة استعادة، أو نسخة منطقية معروفة.
2. استعدها بالطريقة الرسمية للمشغل/إصدار PostgreSQL إلى قاعدة جديدة معزولة؛ لا تستعد فوق قاعدة المصدر.
3. استخدم إصدار التطبيق المقصود. بدء الخدمة قد يطبق الهجرات المعلقة تلقائياً؛ افحص سجل الهجرات بعد الإقلاع، ولا تعتبر مجرد بدء الخدمة برهاناً على استعادة سليمة.
4. تحقق من `/readyz` عبر عنوان الخدمة الفعلي. يفحص هذا المسار اتصال PostgreSQL وتوافق سجل الهجرات وبصماتها، ولا يفحص أرصدة جميع الشركات.
5. افحص أرصدة كل شركة وفترة وعملة معنية باستخدام `Driver.AssertBalancesMatchMoves(ctx, companyID, periodID, currencyID)` ضمن أداة تحقق مصرح بها. هذه الدالة تتطلب معرفات محددة؛ لا يوفر المستودع أمراً عاماً يفحص تلقائياً كل الشركات والفترات والعملات.
6. شغّل التحقق من سلسلة التدقيق عبر `governance.VerifyAuditIntegrity` باستخدام Repository موثوق، إن كان ذلك مفعلاً لتلك البيئة؛ لا يوجد أمر CLI عام لهذا الفحص.
7. سجل النسخة والهدف، إصدار PostgreSQL والتطبيق، مدة الاستعادة، نتائج الفحوصات، الفجوات، القائم بالإجراء والإجراءات التصحيحية. قارن القياس الفعلي بأهداف البيئة المعتمدة.

## 5. حدود اختبارات المستودع وتمرين الاستعادة المكتمل

1. **تمرين الاستعادة الفعلي (P12-01):** تم إنجاز تمرين استعادة فعلي مؤتمت بالكامل عبر `test/dr/dr_drill_test.go` يستخدم `pg_dump -Fc` و`pg_restore` فعليين على قواعد PostgreSQL مستقلة. أثبت التمرين استعادة المخطط بدون إعادة ترحيل، واجتياز فحوصات السلامة المحاسبية الستة بنسبة 100% (توازن القيود، مطابقة الأرصدة، سلامة سلسلة الهاش، عزل المستأجرين RLS، ثبات مفاتيح Idempotency، وسلامة التسلسلات)، واستئناف عمليات المحرك بالكامل (RTO ≈ 1.5s, RPO = 0). انظر [ARD-P12-01](../ard/ARD-P12-01.md) و [Disaster Recovery Runbook](runbooks/disaster_recovery_runbook.md).
2. **اختبار التكامل المعزول:** اختبار `TestBackupRestore_IntegrityVerification` في `internal/adapters/postgres/p6_06_observability_and_recovery_test.go` يهيئ مخططين PostgreSQL معزولين لبيان سلامة النقل وإعادة البناء.

تشغيل اختبارات التعافي والاستعادة:

```bash
# تمرين الاستعادة الفعلي الكامل (pg_dump / pg_restore وفحوصات السلامة الستة)
go test -v ./test/dr

# اختبارات التكامل الداخلي
go test ./internal/adapters/postgres -run 'TestBackupRestore_IntegrityVerification|TestValidateSchemaHealth'
```

تحتاج الاختبارات إلى PostgreSQL، وتستخدم `POSTGRES_URL` إن كان مضبوطاً وإلا تحاول قاعدة الاختبار المحلية؛ التخطي عند غياب قاعدة البيانات لا يعد تمرين استعادة ناجحاً.
