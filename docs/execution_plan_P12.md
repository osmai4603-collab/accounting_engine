# المرحلة `P12` — التصلب التشغيلي والأداء وجاهزية الإنتاج

- **الهدف:** إغلاق كافة الفجوات التشغيلية المتبقية: تمرين استعادة فعلي (PITR / Disaster Recovery) لإلغاء شرط NO-GO، حماية واجهات الخدمة المستقلة (Rate Limiting لنمط Standalone Service حصراً)، قياسات الأداء المرجعية (Benchmarks)، التحقق من تعافي معالجة الأحداث، وإصدار تقرير الجاهزية النهائي مع بوابات الإصدار G1–G12.
- **عدد المهام:** 5 مهام (`P12-01` إلى `P12-05`)
- **الاعتماديات:** `P9`، `P10`، و `P11` (جزئياً حسب طبيعة كل مهمة)
- **الحالة الحالية للميزات:**
  - PITR: **مكتملة في `P12-01`** — تمرين استعادة فعلي كامل (`pg_dump`/`pg_restore`) واجتياز فحوصات السلامة الستة بنسبة 100% مع RPO=0 و RTO ≈ 1.49s، ورفع شرط NO-GO رسمياً
  - Rate limiting: **مكتملة في `P12-02`** — Token Bucket، سياسات قراءة/كتابة، HTTP وgRPC، إعدادات بيئية واختبارات؛ النطاق محصور بالخدمة المستقلة
  - Performance benchmarks: **مكتملة في `P12-03`** — ستة قياسات على محول الذاكرة وPostgreSQL مع خط أساس موثق
  - Event recovery: **مكتملة في `P12-04`** — اختبارات حقن الفشل وإعادة التسليم والتعافي بعد إعادة تشغيل محرك SDK، مع توثيق ضمانات وحدود التشغيل
  - Release Readiness: **مكتملة في `P12-05`** — تقييم بوابات G1–G12 بنسبة 100%، تقرير الجاهزية v0.2.0، وتحديث RELEASE_NOTES.md واعتماد قرار GO للنواة المدمجة والخدمة المستقلة

## تفاصيل المهام

### `P12-01` — تمرين استعادة فعلي واختبار التعافي من الكوارث (PITR / Recovery Drill)

- **المشكلة التي تحلها:** تنص ملاحظات الإصدار (Release Notes v0.1.0) صراحةً على أن المحرك في حالة **NO-GO كخدمة مستقلة** حتى يتم تنفيذ وتوثيق تمرين نسخ واستعادة فعلي (`pg_dump`/`pg_restore`) يثبت استعادة قاعدة البيانات واجتيازها لفحوصات السلامة (Integrity Checks). الاختبارات الحالية كانت تقتصر على إعادة بناء الجداول وليس استعادة ملفات النسخ الاحتياطي الفعلية.

- **الهدف الذي تحققه:** إجراء تمرين استعادة عملي موثق ومؤتمت يُثبت:
  1. أخذ نسخة احتياطية من قاعدة بيانات تشغيلية تحتوي على قيود مرحلة ومعكوسة وإقفالات سنوية.
  2. استعادة النسخة في قاعدة بيانات فارغة ومستقلة تماماً.
  3. اجتياز كافة فحوصات السلامة المحاسبية والبيانات (توازن القيود، سلامة تسلسلات الهاش، عدم فقدان مفاتيح Idempotency، وسلامة الـ RLS).
  4. استئناف عمليات المحرك بالكامل على القاعدة المستعادة دون أخطاء.
  5. رفع شرط NO-GO وتوثيق Runbook الاستعادة.

- **نطاق المهمة:**
  - `docs/operations/backup_and_recovery_policy.md` — توثيق السياسة والنتائج
  - `docs/operations/runbooks/disaster_recovery_runbook.md` — خطوات الاستعادة الفعلية
  - نصوص وسكربتات الاختبار في `scripts/dr_drill/` أو `test/dr/`
  - **لا تشمل:** إدارة السحابة أو جدولة البنية التحتية

- **خطوات التنفيذ:**
  1. تجهيز قاعدة بيانات تمثيلية تحتوي على حركات كاملة: شركات متعددة، قيود عادية ومعكوسة، قيود تسوية، إقفال سنوي مكتمل (`P9-01`)، وسجل تدقيق مشفر بالهاش.
  2. أخذ نسخة احتياطية حقيقية: `pg_dump -Fc -f backup.dump`.
  3. إنشاء بيئة مستهدفة نظيفة واستعادة النسخة: `pg_restore -d restored_db backup.dump`.
  4. تشغيل حزمة فحوصات السلامة الصارمة (Integrity Verification Suite):
     - توازن كل قيد مرحّل: $\sum Debit = \sum Credit$.
     - مطابقة أرصدة الحسابات الإجمالية مع حاصل جمع حركات سطور القيود.
     - تكامل سلسلة تجزئة التدقيق (Hash Chain Integrity) وعدم وجود أي انقطاع.
     - عزل الشركات عبر RLS: التأكد من استحالة وصول الشركة (أ) إلى بيانات الشركة (ب).
     - الحفاظ على مفاتيح عدم التكرار (Idempotency Keys).
     - سلامة التسلسلات وعدم تكرار أرقام القيود عند الاستئناف.
  5. تشغيل المحرك على القاعدة المستعادة وإجراء حركات جديدة (إنشاء مسودة، ترحيل، إقفال).
  6. توثيق زمن الاستعادة (RTO) ومقدار فقدان البيانات (RPO=0 في هذا التمرين) وتحديث Runbook.

- **الاعتماديات:** `P9-01` (لاختبار قاعدة بيانات تتضمن قيود إقفال سنوي وافتتاح).

- **معايير القبول:**
  - [x] استعادة ناجحة لملف نسخة احتياطية فعلي (`pg_restore`) دون أخطاء.
  - [x] اجتياز جميع فحوصات السلامة المحاسبية الستة بعد الاستعادة بنسبة 100%.
  - [x] استئناف المحرك للترحيل الجديد بنجاح على القاعدة المستعادة.
  - [x] توثيق الإجراء في Runbook وتحديث حالة NO-GO في وثائق الإصدار.

- **مخرجات التحقق والتشغيل:**
  - `test/dr/dr_drill_test.go`, `test/dr/harness_test.go`, `test/dr/snapshot_test.go` — جناح الاختبار المؤتمت الكامل (اجتياز 11 مرحلة)
  - `docs/operations/runbooks/disaster_recovery_runbook.md` — دليل استعادة الكوارث والتحقق من السلامة المحاسبية
  - `docs/operations/backup_and_recovery_policy.md` — تحديث السياسة التشغيلية بنتائج التمرين
  - `docs/ard/ARD-P12-01.md` — قرار العمارة ورفع شرط NO-GO
  - مقاييس التشغيل: `RTO ≈ 1.49s` و `RPO = 0`، وحجم النسخة 251KB.
  - أمر التحقق: `go test -v ./test/dr`

### `P12-02` — حماية واجهات الخدمة المستقلة (Rate Limiting for Standalone Service)

- **المشكلة التي تحلها والتحديد المعماري للنطاق:**
  - واجهات HTTP و gRPC عند تشغيل المحرك كخدمة مستقلة (`cmd/accounting-service/`) معرضة لخطر استنزاف الموارد وهجمات الحرمان من الخدمة (DoS).
  - **توضيح معماري صارم (Architectural Scope Boundary):**
    - المحرك المحاسبي في جوهره هو **مكتبة برمجية مدمجة (Embedded SDK Core)**.
    - خاصية **Rate Limiting ليست جزءاً من النواة المحاسبية (Engine Core)** ولا تُفرض مطلقاً على الاستدعاءات البرمجية المباشرة للـ SDK داخل التطبيق المضيف (In-process Embedded calls).
    - في نمط Embedded، مسؤولية التحكم في معدل الطلبات تقع بالكامل على النظام المضيف في طبقات النقل الخاصة به.
    - خاصية Rate Limiting في هذه المهمة تنحصر فقط في **طبقة النقل للخدمة المستقلة (Transport Layer of Standalone Service Binary)** عبر Middleware لـ HTTP و Interceptor لـ gRPC.
    - استمرار قاعدة استقلال المصادقة: لا يعتمد الـ Rate Limiter على هويات المستخدمين أو أدوارهم التجارية، بل يعمل بحسابات عناوين الشبكة (Client IP) أو معرفات المستأجرين (Tenant/Company ID) أو السعة الإجمالية.

- **الهدف الذي تحققه:** حماية خدمة `cmd/accounting-service` المستقلة من الاستنزاف مع إبقاء نواة المحرك خفيفة وخالية من أعباء البنية التحتية.

- **نطاق المهمة:**
  - `cmd/accounting-service/middleware/ratelimit.go` — HTTP Middleware
  - `cmd/accounting-service/interceptors/ratelimit.go` — gRPC Interceptor
  - `internal/ratelimit/` — خوارزمية Token Bucket / Sliding Window المستقلة
  - **محظور ومستثنى:** تعديل `pkg/sdk/` لفرض أي rate limiting على الاستخدام المدمج.

- **خطوات التنفيذ:**
  1. تنفيذ خوارزمية Token Bucket أو Sliding Window داخلية تدعم العمل بالذاكرة (In-Memory).
  2. تصميم سياسات تحديد المعدل:
     - حد عام لطلبات القراءة والاستعلام.
     - حد منضبط لعمليات الكتابة والترحيل عالية الكلفة الحسابية.
     - إمكانية عزل الحدود لكل مستأجر (Per-Tenant / Company Isolation).
  3. ربط الـ Middleware في خادم HTTP ليعيد رمز الحالة `429 Too Many Requests` مع ترويسة `Retry-After`.
  4. ربط الـ Interceptor في خادم gRPC ليعيد حالة الخطأ `codes.ResourceExhausted`.
  5. جعل المعلمات (الحد، النافذة الزمنية، التفعيل) قابلة للتهيئة عبر متغيرات البيئة أو ملف الإعداد.
  6. اختبارات إرسال دفعات سريعة من الطلبات والتحقق من الاستجابة السليمة عند تجاوز الحد.

- **الاعتماديات:** لا شيء (مستقلة وتخص الخادم المستقل فقط).

- **معايير القبول:**
  - [x] خادم HTTP يعيد `429` مع ترويسة `Retry-After` وجسم خطأ مهيكل عند تجاوز الحد.
  - [x] خادم gRPC يعيد `RESOURCE_EXHAUSTED` مع بيانات `retry-after` عند تجاوز الحد.
  - [x] لا يوجد أي تأثير أو فرض لقيود Rate Limiting على النواة المدمجة (`pkg/sdk/` أو `pkg/spi/`).
  - [x] الحدود قابلة للتهيئة عبر البيئة وتُعزل حسب المستأجر الموثّق، مع الرجوع لعنوان IP عند غياب هوية مستأجر.
  - [x] لا تعتمد السياسات على المستخدم أو الدور التجاري؛ المصادقة تُجري فقط إثبات المستأجر الموثوق عند توفرها.
  - [x] اختبارات Token Bucket، حدود القراءة/الكتابة، عزل المستأجرين، حد الذاكرة، HTTP وgRPC unary/stream.

- **إعدادات التشغيل:** `RATE_LIMIT_ENABLED`، `RATE_LIMIT_READ_REQUESTS`، `RATE_LIMIT_WRITE_REQUESTS`، `RATE_LIMIT_CLIENT_READ_REQUESTS`، `RATE_LIMIT_CLIENT_WRITE_REQUESTS`، `RATE_LIMIT_WINDOW`، `RATE_LIMIT_MAX_KEYS`؛ موثقة في [حدود الخدمة](./architecture/service_boundary.md).
- **الأدلة:** [ARD-P12-02](./ard/ARD-P12-02.md).
- **التحقق:** `go test ./internal/ratelimit ./cmd/accounting-service/...` و`go test -race ./internal/ratelimit ./cmd/accounting-service/...`.
- **حد تشغيلي موثق:** التخزين داخل الذاكرة لكل عملية؛ لا تتشارك نسخ الخدمة حصة موزعة. يوجد حارس IP أعلى قبل المصادقة وحصة tenant منفصلة بعدها.

### `P12-04` — التحقق من التعافي من أخطاء الأحداث (Event Ingestion Recovery Verification)

- **المشكلة التي تحلها:** تدفق استقبال الأحداث (Event Ingestion) يمثل المدخل الرئيسي للأنظمة المدمجة، ويتطلب التحقق العملي من ضمانات التعافي عند انقطاع الاتصال أو فشل ترحيل الأحداث، لضمان عدم فقدان أي حركة أو تكرار ترحيلها.

- **الهدف الذي تحققه:** إثبات متانة خط استهلاك الأحداث وضمان تحقيق مبدأ "المعالجة مرة واحدة بدقة" (Effectively-Once Processing via At-Least-Once Delivery + Strict Idempotency).

- **نطاق المهمة:**
  - `pkg/sdk/event_ingestion.go` — مراجعة معالجة الأخطاء
  - `test/integration/event_fault_recovery_test.go` — اختبارات حقن الفشل للتدفق
  - `docs/sdk_developer_guide.md` — توثيق ضمانات الاستهلاك وحدودها
  - `docs/ard/ARD-P12-04.md` — قرار العمارة وأدلة التحقق

- **خطوات التنفيذ:**
  1. [x] اختبار فشل التحقق (Validation Fault): إرسال مسودة حدث تشير إلى حساب غير موجود، وتسجيل سبب الرفض في سجل الحدث دون تعطيل الأحداث التالية.
  2. [x] اختبار انقطاع الترحيل (Posting Failure): حقن فشل تسلسلي للمعاملة والتحقق من تسجيل الحالة القابلة لإعادة المحاولة ثم إكمالها عند إعادة الإرسال.
  3. [x] اختبار إعادة الإرسال والتكرار (Re-delivery & Idempotency): إعادة إرسال الحدث بعد إنشاء محرك جديد والتحقق من إرجاع القيد نفسه دون ترحيل مكرر.
  4. [x] اختبار التعافي بعد إعادة التشغيل (Crash Recovery): تجهيز سجل دائم في حالة `started` بهوية القيد والمسودة المحجوزتين، ثم تشغيل محرك جديد والتحقق من استئناف الحدث غير المؤكد. الاختبار يحاكي نقطة الانهيار بسجل مستمر ولا يدّعي اختبار قتل عملية نظام تشغيل فعلية.

- **الاعتماديات:** `P8-04`، `P10-01`، و `P11-05`.

- **معايير القبول:**
  - [x] عدم فقدان الحدث الصالح في سيناريو فشل المعاملة وإعادة المحاولة، مع حفظ سبب الرفض للأخطاء الدائمة بعد إنشاء المطالبة.
  - [x] منع تكرار إنشاء القيد عند إعادة إرسال الحدث بالمفتاح والحمولة نفسيهما.
  - [x] استئناف الحدث المعلق ذي الهوية المحجوزة بعد بدء محرك SDK جديد.
  - [x] توثيق ضمانات التسليم والحدود التشغيلية في [دليل المطور](./sdk_developer_guide.md#event-delivery-and-recovery) و[ARD-P12-04](./ard/ARD-P12-04.md).

- **التحقق:** `go test ./test/integration -run 'TestEvent(ValidationFault|PostingFailure|DuplicateDelivery|Recovery)' -count=1` — ناجح. تشمل اختبارات SDK القائمة أيضًا التزامن، تعارض الحمولة، غياب مخزن عدم التكرار، الفشل النهائي، والفشل بعد نجاح الترحيل وقبل إتمام سجل الحدث.
- **حدود الأدلة:** تستخدم اختبارات التكامل محول الذاكرة؛ محاكاة الانهيار بإعادة تشغيل محرك SDK مع سجل `started` مستمر، وليست تمرين تعطل نظام أو إثبات تحمل قاعدة بيانات إنتاجية. تعتمد متانة التخزين عبر العمليات على ضمانات المحول الدائم.

- **الهدف الذي تحققه:** إصدار وثيقة الجاهزية النهائية ومصفوفة بوابات الإصدار الشاملة وملاحظات الإصدار المحدثة.
