# المرحلة `P12` — التصلب التشغيلي والأداء وجاهزية الإنتاج

- **الهدف:** إغلاق جميع الفجوات التشغيلية المتبقية: اختبار PITR فعلي، حماية من الإساءة (rate limiting)، قياس الأداء، والتحقق النهائي من جاهزية الإصدار مع كل التحسينات
- **عدد المهام:** 5
- **الاعتماديات:** `P9`، `P10`، `P11` (جزئياً حسب كل مهمة)
- **الحالة الحالية للميزات:**
  - PITR: **غير مكتملة** — Release Notes تقول NO-GO حتى تمرين حقيقي
  - Rate limiting: **غير منفذة**
  - Performance benchmarks: **غير منفذة**
  - Event recovery: **تحتاج تحقق فعلي**

---

## تفاصيل المهام

### `P12-01` — تمرين PITR فعلي واختبار الاسترداد (Point-in-Time Recovery Exercise)

- **المشكلة التي تحلها:** Release Notes v0.1.0 تنص صراحةً على أن المحرك **NO-GO كخدمة مستقلة** حتى يتم إجراء تمرين `pg_dump`/`pg_restore` حقيقي. والمهمة `P7-03` لا تزال تحمل معيار قبول معلّق: *"Restore فعلي أو PITR مجرب وينتج DB تجتاز Integrity Checks"*. اختبار إعادة إنشاء البيانات الحالي لا يحقق هذا المعيار لأنه يعيد بناء قاعدة البيانات من الصفر بدل استعادة نسخة احتياطية فعلية.

- **الهدف الذي تحققه:** تمرين استعادة موثق ومجرب يُثبت أن:
  1. نسخة احتياطية من `pg_dump` يمكن استعادتها في بيئة منفصلة
  2. البيانات المستعادة تجتاز فحوصات سلامة المحرك (Integrity Checks)
  3. المحرك يعمل بشكل طبيعي بعد الاستعادة
  4. الإجراء قابل للتكرار وموثق في Runbook

- **نطاق المهمة:**
  - `docs/operations/backup_and_recovery_policy.md` — تحديث بالإجراء الفعلي
  - `docs/operations/runbooks/` — تحديث runbook الاستعادة
  - سكربتات النسخ والاستعادة في `scripts/` أو `test/`
  - اختبار تكاملي للاستعادة
  - **لا تشمل:** إعداد بنية تحتية سحابية أو automated backup scheduling

- **خطوات التنفيذ:**
  1. **إعداد بيئة الاختبار:** إنشاء قاعدة PostgreSQL مع بيانات تمثيلية: شركتان على الأقل، حسابات متعددة، قيود مرحّلة ومعكوسة، فترات مفتوحة ومغلقة، تدقيق.
  2. **تنفيذ النسخ الاحتياطي:** `pg_dump --format=custom --file=backup.dump`.
  3. **محاكاة الفقدان:** إسقاط القاعدة أو إنشاء قاعدة فارغة.
  4. **الاستعادة:** `pg_restore --dbname=restored_db backup.dump`.
  5. **فحوصات السلامة بعد الاستعادة:**
     - توازن كل القيود المرحّلة (Debit = Credit لكل قيد)
     - تطابق أرصدة الحسابات مع مجموع حركاتها
     - سلسلة تجزئة التدقيق (hash chain) سليمة
     - RLS يعمل — الشركة A لا ترى بيانات الشركة B
     - Idempotency keys محفوظة — إعادة طلب لا تكرر القيد
     - التسلسل (sequences) صحيح — الأرقام لا تتعارض مع القائم
  6. **تشغيل المحرك:** بناء المحرك على القاعدة المستعادة، تنفيذ عمليات جديدة (draft/post/reverse)، والتحقق من نجاحها.
  7. **PITR (اختياري إن توفر):** إذا كانت البيئة تدعم WAL archiving، اختبار استعادة إلى نقطة زمنية محددة.
  8. **توثيق الإجراء:** تحديث Runbook بالأوامر الفعلية والنتائج والوقت المستغرق.
  9. **إمكانية التكرار:** جعل الاختبار قابلاً للتشغيل في CI (اختياري — بعض بيئات CI لا تدعم pg_dump/pg_restore بسهولة).

- **الاعتماديات:** `P9-01` (لاختبار استعادة بيانات تتضمن قيود إقفال).

- **معايير القبول:**
  - [ ] `pg_dump` → `pg_restore` ينجح على قاعدة بيانات تمثيلية
  - [ ] كل فحوصات السلامة تمر بعد الاستعادة (6 فحوصات أعلاه)
  - [ ] المحرك يعمل بشكل طبيعي على القاعدة المستعادة — يمكن الترحيل والعكس
  - [ ] الإجراء موثق في Runbook مع الأوامر الفعلية والوقت المستغرق
  - [ ] الاختبار قابل للتكرار (سكربت أو Makefile target)
  - [ ] NO-GO الموجود في Release Notes يُرفع أو يُحدّث بنتيجة التمرين
  - [ ] معيار `P7-03` المعلّق يُستوفى

### `P12-02` — تنفيذ Rate Limiting لحماية واجهات الخدمة

- **المشكلة التي تحلها:** لا يوجد rate limiter في المحرك. هذا ثغرة وفق OWASP ASVS — واجهات HTTP/gRPC (عند تشغيلها كـ Standalone) معرضة لإساءة الاستخدام (DDoS, brute-force, resource exhaustion).

- **الهدف الذي تحققه:** حماية واجهات الخدمة المستقلة من الطلبات المسيئة مع الحفاظ على استقلال المحرك عن البنية التحتية.

- **نطاق المهمة:**
  - `cmd/accounting-service/` — middleware لـ HTTP و interceptor لـ gRPC
  - `internal/ratelimit/` (جديد) — منطق Rate Limiting
  - إعدادات الحدود
  - **لا تشمل:** WAF خارجي، أو فرض rate limiting على Embedded Library (مسؤولية المضيف)

> [!NOTE]
> **قاعدة استقلال المصادقة:** Rate limiting هو حماية بنية تحتية وليس تفويضاً تجارياً. لا يتطلب معرفة هوية المستخدم أو صلاحياته — يعمل على مستوى IP/Client أو إجمالي الطلبات. لا يُفرض على Embedded Library.

- **خطوات التنفيذ:**
  1. تحديد نمط النشر: Rate limiting مطلوب فقط عند تشغيل الخدمة المستقلة (`cmd/accounting-service/`). في Embedded mode، المضيف يتولى الحماية.
  2. تعريف سياسات الحدود: حد عام (طلبات/ثانية per IP)، حد خاص لعمليات الكتابة (Post/Reverse)، حد لتقارير ثقيلة.
  3. تنفيذ Token Bucket أو Sliding Window في `internal/ratelimit/`.
  4. دعم التخزين: في الذاكرة (نسخة واحدة) أو Redis/DB (نسخ متعددة — اختياري مع تصريح).
  5. إضافة HTTP Middleware يطبّق Rate Limit ويعيد `429 Too Many Requests` مع `Retry-After`.
  6. إضافة gRPC Interceptor مكافئ يعيد `RESOURCE_EXHAUSTED`.
  7. جعل الحدود قابلة للإعداد عبر Configuration.
  8. اختبار: طلبات متتابعة سريعة → 429 بعد تجاوز الحد، انتظار → يعود للقبول.
  9. التوثيق: حدود افتراضية، كيفية التخصيص، توصية بـ API Gateway في الإنتاج.

- **الاعتماديات:** لا شيء (مستقلة).

- **معايير القبول:**
  - [ ] HTTP يعيد `429 Too Many Requests` عند تجاوز الحد مع `Retry-After` header
  - [ ] gRPC يعيد `RESOURCE_EXHAUSTED` عند تجاوز الحد
  - [ ] الحدود قابلة للإعداد (لا hardcoded)
  - [ ] لا يُفرض على Embedded Library
  - [ ] عمليات الكتابة (Post/Reverse) يمكن أن يكون لها حد أقل من القراءة
  - [ ] لا يتسرب Rate limiting عبر شركات (Company A لا تؤثر على Company B إذا كان الحد per-tenant)
  - [ ] توثيق الحدود والتخصيص

- **ملاحظة التوازي:** مستقلة تماماً — لا تتداخل مع أي مهمة أخرى في P12.

### `P12-03` — قياس الأداء والمقاييس المرجعية (Performance Benchmarks)

- **المشكلة التي تحلها:** لا توجد benchmarks منشورة في المشروع. لا يوجد إثبات موضوعي لأداء المحرك تحت حمل معين، ولا يوجد خط أساس لاكتشاف تدهور الأداء في الإصدارات اللاحقة (performance regression).

- **الهدف الذي تحققه:** مجموعة benchmarks قابلة للتكرار تقيس العمليات الأساسية وتنتج تقريراً مرجعياً.

- **نطاق المهمة:**
  - `test/benchmark/` (جديد) — ملفات Benchmark
  - `internal/posting/` — benchmarks الترحيل
  - `internal/reporting/` — benchmarks التقارير
  - `storage/postgres/` — benchmarks التخزين
  - **لا تشمل:** اختبار حمل إنتاجي أو stress testing أو performance tuning

- **خطوات التنفيذ:**
  1. تحديد العمليات المرجعية:
     - `BenchmarkDraftCreate` — إنشاء مسودة قيد مع 2/5/20 سطراً
     - `BenchmarkPostAndSequence` — ترحيل قيد كامل (validation + sequence + balance update + audit + idempotency)
     - `BenchmarkReversal` — عكس قيد مرحّل
     - `BenchmarkTrialBalance` — حساب ميزان المراجعة لـ 100/1000/10000 حساب
     - `BenchmarkBalanceSheet` — الميزانية العمومية
     - `BenchmarkConcurrentPost` — ترحيل 10/50/100 قيد بالتوازي
  2. تنفيذ Benchmarks باستخدام `testing.B` في Go.
  3. تشغيل على PostgreSQL (مع قاعدة بيانات محلية) و Memory.
  4. تسجيل النتائج: ops/sec، ns/op، allocs/op، bytes/op.
  5. إنشاء خط أساس (baseline) للإصدار الحالي.
  6. إضافة CI gate اختيارية: تحذير عند تدهور > 20% عن الخط الأساسي (لا تمنع الإصدار — تنبّه فقط).
  7. توثيق بيئة الاختبار والنتائج.

- **الاعتماديات:** `P8-03` (لقياس أداء advisory locks vs mutex).

- **معايير القبول:**
  - [ ] 6 benchmarks أساسية على الأقل منفذة ومشغلة
  - [ ] النتائج على PostgreSQL و Memory موثقة
  - [ ] خط أساس محفوظ كملف مرجعي (benchmark baseline)
  - [ ] الاختبارات قابلة للتشغيل بـ `go test -bench=.`
  - [ ] لا performance regression غير مفسر > 20% بين الإصدارات (تنبيه)
  - [ ] بيئة الاختبار موثقة (CPU, RAM, PostgreSQL version, Go version)

### `P12-04` — تحقق Event Recovery والتعافي من فشل معالجة الأحداث

- **المشكلة التي تحلها:** تقرير التحليل يشير إلى أن Event Recovery **تحتاج تحقق فعلي**. يوجد `event_recovery_test.go` لكن يجب التأكد من أن:
  - الأحداث التي فشلت معالجتها تُعاد بشكل آمن
  - لا يتم فقدان حدث
  - لا يتم معالجة حدث مرتين (مع Idempotency)
  - التعافي يعمل بعد إعادة تشغيل الخدمة

- **الهدف الذي تحققه:** تحقق وظيفي يُثبت أن مسار معالجة الأحداث يتعافى بشكل صحيح من حالات الفشل المختلفة.

- **نطاق المهمة:**
  - `pkg/sdk/event_ingestion.go` — مراجعة وتحقق
  - `internal/` — منطق المعالجة والتعافي
  - اختبارات فشل وتعافي
  - **لا تشمل:** بناء نظام Event Streaming (Kafka/NATS)

- **خطوات التنفيذ:**
  1. مراجعة `event_ingestion.go` و `event_recovery_test.go` الموجودين.
  2. تحديد سيناريوهات الفشل:
     - فشل أثناء التحقق من الحدث (validation)
     - فشل أثناء الترحيل (posting failure)
     - فشل بعد الترحيل وقبل تأكيد المعالجة (ack)
     - انقطاع الخدمة أثناء المعالجة
  3. لكل سيناريو: تحديد السلوك المتوقع والتحقق منه.
  4. اختبار Idempotency: نفس الحدث يُرسل مرتين — يُعالج مرة واحدة فقط.
  5. اختبار التعافي بعد Restart: إعادة تشغيل الخدمة/المحرك والتحقق من أن الأحداث المعلقة تُعاد معالجتها.
  6. توثيق ضمانات التسليم: at-least-once مع Idempotency = effectively-once.
  7. توثيق الحدود: ما لا يضمنه المحرك (مثلاً: ترتيب المعالجة عبر الأحداث).

- **الاعتماديات:** `P10-01`، `P11-05` (لاختبار أحداث مع وحدات معيارية).

- **معايير القبول:**
  - [ ] كل سيناريو فشل (4 أعلاه) له اختبار ونتيجة متوقعة موثقة
  - [ ] لا فقدان حدث: كل حدث مُرسل يُعالج أو يُرفض بخطأ واضح
  - [ ] لا تكرار: Idempotency Key يمنع المعالجة المزدوجة
  - [ ] التعافي بعد Restart يعمل — الأحداث المعلقة تُعاد
  - [ ] ضمانات التسليم موثقة صراحةً
  - [ ] الحدود والاستثناءات موثقة

### `P12-05` — تقرير جاهزية الإصدار المحدّث (Updated Release Readiness)

- **المشكلة التي تحلها:** بعد استكمال P8–P12، يجب تحديث تقرير جاهزية الإصدار (`P7-05`) ليعكس الميزات الجديدة، البوابات الإضافية (G9–G12)، والفجوات المتبقية. هذا ليس تكراراً لـ P7-05 بل تحديث يشمل النطاق الموسع.

- **الهدف الذي تحققه:** قرار Go/No-Go محدّث مبني على:
  - جميع بوابات الإصدار G1–G12
  - نتائج P8–P12
  - Known Limitations المحدّثة
  - Compliance Matrices المحدّثة لكل معيار

- **نطاق المهمة:**
  - تقرير جاهزية محدّث
  - مصفوفة متطلبات شاملة
  - مراجعة Release Notes
  - **لا تشمل:** تطوير ميزات جديدة أو نشر الإصدار

- **خطوات التنفيذ:**
  1. تجميع نتائج جميع مهام P8–P12 من تقارير ARD.
  2. تقييم كل بوابة من G1–G12 مع الأدلة.
  3. تحديث Known Limitations:
     - ما لا يزال خارج النطاق في كل معيار IFRS/IAS
     - ما لم يُختبر بعد (إن وُجد)
     - القيود التشغيلية
  4. تحديث Compliance Matrix لكل معيار.
  5. مراجعة SemVer: هل التغييرات تتطلب MINOR أم MAJOR؟
  6. إعداد Release Notes المحدّثة.
  7. الحصول على مراجعة محاسبية نهائية (أو التصريح بعدم اكتمالها).
  8. إصدار قرار Go/No-Go صريح.

- **الاعتماديات:** `P12-01`، `P12-02`، `P12-03`، `P12-04` (جميع مهام P12 الأخرى).

- **معايير القبول:**
  - [ ] جميع بوابات G1–G12 مقيّمة مع أدلة
  - [ ] لا توجد بوابة حرجة فاشلة مع قرار Go
  - [ ] Known Limitations محدّثة وشاملة
  - [ ] Compliance Matrix لكل معيار محدّثة
  - [ ] Release Notes مكتملة مع Compatibility Policy
  - [ ] قرار Go/No-Go موثق مع الشروط المانعة (إن وُجدت)
  - [ ] الموافقات موثقة أو يُذكر أن التصديق غير مكتمل

## تعريف الإنجاز النهائي (بعد P8–P12)

لا يعد Accounting Engine جاهزاً كمنتج مكتمل إلا عند تحقق جميع النقاط التالية (إضافةً إلى النقاط الـ 10 في الخطة الأصلية):

 1. يستطيع المحرك تنفيذ إقفال سنوي تلقائي يولّد قيود الإقفال والافتتاح عبر Application Layer.
 2. يُنتج قائمة تدفقات نقدية تتصالح مع الميزانية العمومية.
 3. الدفاتر الفرعية الأساسية (AR/AP، أصول ثابتة، خزينة) متاحة عبر public SPI.
 4. كل وحدة معيارية مفعّلة تُرحّل قيودها عبر Application Layer — لا قياس بدون ترحيل.
 5. تم تمرين PITR فعلي وموثق، ورُفع شرط NO-GO.
 6. واجهات الخدمة المستقلة محمية بـ rate limiting (عند تشغيلها).
 7. توجد benchmarks مرجعية لاكتشاف تدهور الأداء.
 8. جميع بوابات الإصدار من G1 إلى G12 مجتازة.
