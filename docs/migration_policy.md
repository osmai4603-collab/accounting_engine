# سياسة هجرات PostgreSQL والتوافق أثناء النشر

- **الحالة:** سياسة تشغيلية
- **المالك:** مالك الخدمة + مسؤول قاعدة البيانات
- **النطاق:** `internal/adapters/postgres/migrations/` وواجهات ترحيل PostgreSQL
- **آخر مراجعة:** 2026-11-16

## 1. ما يفعله المحرك فعلياً

- ملفات الهجرة المرقمة مضمّنة في البرنامج، ويحسب المحرك SHA-256 لمحتوى كل ملف أمامي ويحفظه في `schema_migrations`.
- `postgres.MigrateUp` يطبق كل هجرة وبصمتها ضمن معاملة منفصلة، مع قفل PostgreSQL استشاري لمنع تشغيل مهاجرين متزامنين. فشل عبارة أو تسجيل البصمة يلغي معاملة تلك الهجرة؛ الهجرات الأسبق التي تم اعتمادها لا تُلغى.
- عند بدء `postgres.New`، يستدعي المحرك `EnsureSchema` ويطبق الهجرات المعلقة. كما يتطلب `/readyz` اتصالاً سليماً ومخططاً بلا هجرات معلقة وبصمات متطابقة. المخطط الذي يحتوي إصدار هجرة غير معروف للبرنامج الحالي غير متوافق.
- `postgres.MigrateDown(ctx, pool, steps)` ينفّذ ملفات `.down.sql` بترتيب عكسي؛ وتوجد واجهة CLI: `go run ./cmd/agy db migrate down --steps N`. توافر ملف down لا يعني أن التراجع آمن بعد كتابة بيانات جديدة.
- `cmd/agy db migrate up` يشغّل `EnsureSchema` باستخدام `DATABASE_URL`. لا تشغّل أداة الترحيل بالتوازي مع نشر غير منسق، ولا تستخدم `MigrateDown` كخطة استعادة بيانات.

## 2. التوافق والنشر المتدرج

تعتمد الخدمة نمط Expand/Backfill/Switch/Contract عبر إصدارات منفصلة:

1. **Expand:** إضافة مخطط اختياري/متوافق لا يتطلب من النسخة القديمة تغييراً.
2. **Backfill:** تعبئة على دفعات قابلة للاستئناف إذا تطلب التغيير ذلك؛ وثّق المؤشرات وآلية الإيقاف.
3. **Switch:** نشر التطبيق الذي يستخدم الشكل الموسع، والتحقق من النسخ التي لا تزال تعمل قبل الانتقال.
4. **Contract:** إزالة الشكل القديم في إصدار لاحق فقط بعد توقف كل نسخة قديمة والتأكد من عدم وجود اعتماد أو بيانات لازمة.

لا تجمع Expand وContract في هجرة واحدة. لأن بدء الخدمة ينفذ `EnsureSchema` تلقائياً، نسّق نشر عدة نسخ مع مرحلة الترحيل: الهجرات الموسعة يجب أن تكون متوافقة مع التطبيق القديم، وأي خطوة غير متوافقة تحتاج إيقافاً/نافذة صيانة وخطة نشر تمنع إقلاع نسخة قديمة على مخطط أحدث.

## 3. إصدار هجرة ومراجعتها

- الاسم: `<12 رقم إصدار>_<snake_case>.sql` مع ملف مقابل `.down.sql`. أضف هجرة جديدة ولا تعدّل أبداً ملفاً سبق تطبيقه.
- اختبر السلسلة الكاملة، والانتقال من أقدم مخطط مدعوم (الهجرة التأسيسية) مع بيانات ممثلة. لا تعتبر إعادة تشغيل نظيفة وحدها إثباتاً لحفظ البيانات.
- نفّذ الهجرات على PostgreSQL؛ كل ملف أمامي يعمل ضمن معاملة، لذلك لا تستخدم أوامر PostgreSQL التي لا تعمل داخل المعاملات (مثل `CREATE INDEX CONCURRENTLY`) عبر هذا المنفذ.
- الهجرات المدمرة أو التي تغير معنى/نوع البيانات تحتاج قراراً موثقاً، سبباً ومالكاً وموافقة، وخطة بيانات وتراجع/استعادة. الحارس `TestDangerousMigrationsRequireApproval` يرفض الأنماط المعروفة غير المعتمدة؛ اجتيازه لا يغني عن مراجعة SQL.
- القيود على البيانات الموجودة يجب إدخالها بخطوات قابلة للتحقق، مثل إضافة القيد غير موثّق ثم التحقق بهجرة منفصلة عند ملاءمة ذلك.
- سجل مالك التغيير، النطاق، زمن الأقفال المتوقع، أثره على النسخ القديمة، إجراءات المراقبة، وخطة التقدم للأمام. احتفظ بنسخة احتياطية قابلة للاستعادة قبل الإنتاج وفق سياسة النسخ الاحتياطي.

## 4. الفشل والبصمات

- لكل هجرة سجل مستقل. الفشل داخل الهجرة الحالية يُرجع DDL وكتابة سجلها معاً؛ قد تكون هجرات سابقة من نفس التشغيل ملتزمة. أوقف النشر، افحص `schema_migrations` ومخطط قاعدة البيانات، ولا تفترض أن القاعدة عادت إلى نقطة البداية.
- عند وجود هجرات معلقة، أعد تشغيل إصدار الترحيل نفسه بعد معالجة السبب؛ فشل الترحيل يجعل الجاهزية غير سليمة حتى اكتمال السلسلة.
- عند اختلاف checksum، أوقف التشغيل. لا تعدّل سجل قاعدة البيانات ولا تستبدل ملفاً مطبقاً بتخمين. استعد الملف الأصلي من الإصدار المعتمد، أو استخدم هجرة جديدة بعد تقييم الأثر. إذا كان المخطط مجهول الحالة، اعزل قاعدة البيانات واستعد نسخة موثوقة أو تقدّم بإصلاح معتمد.
- لا تشغّل إصداراً أقدم على قاعدة أحدث: سجل هجرة غير معروف لذلك الإصدار يُرفض باعتباره مخططاً غير متوافق.
- اتبع [`runbook_migration_failure.md`](runbooks/runbook_migration_failure.md) للتشخيص والتعافي.

## 5. اختبارات التحقق

من جذر المستودع:

```bash
go test ./internal/adapters/postgres -run 'TestMigrationsHaveReversiblePairs|TestDangerousMigrationsRequireApproval|TestCleanMigrationLifecycle|TestBaselineMigrationCleanRun|TestFailedMigrationRollsBackAndCanBeRetried|TestMigrationUpgradeFromOldestSupportedSchemaPreservesData|TestValidateSchemaHealth'
```

اختبارات PostgreSQL تستخدم `POSTGRES_URL` إن كان مضبوطاً، وإلا تحاول الاتصال بقاعدة الاختبار المحلية؛ اختبارات التكامل تتخطى نفسها إذا لم يتوفر PostgreSQL. يجب أن تنجح اختبارات التكامل في بيئة إصدار مجهزة بـPostgreSQL، ولا تعد نتيجة التخطي تحققاً.

## 6. حدود الإثبات

الاختبارات المذكورة تثبت سلوك سلسلة الهجرات على مخطط معزول وبيانات الاختبار المحددة. `TestBackupRestore_IntegrityVerification` يعيد إنشاء بيانات ممثلة في مخطط معزول آخر؛ **لا** ينفذ `pg_dump` أو `pg_restore` أو استعادة PITR من نسخة فعلية. لذلك تتطلب القدرة على استعادة النسخ الحقيقية تمريناً تشغيلياً منفصلاً وفق [`backup_and_recovery_policy.md`](operations/backup_and_recovery_policy.md) و[`runbook_database_restore.md`](runbooks/runbook_database_restore.md).
