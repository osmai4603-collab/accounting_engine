# Runbook: فشل هجرة PostgreSQL أو عدم توافق المخطط

- **الخطورة:** حادث نشر/قاعدة بيانات
- **المالك:** مسؤول قاعدة البيانات + مسؤول التطبيق
- **المكونات:** `internal/adapters/postgres/migrations.go`، `schema_migrations`، `/readyz`

## 1. مؤشرات الحادث

- فشل بدء الخدمة بسبب فشل `EnsureSchema`.
- رجوع `/readyz` بحالة `503` بسبب عدم اتصال PostgreSQL أو خطأ في `ValidateSchema`.
- رسائل مثل `applied migration ... checksum differs from source` أو `pending migration(s) unapplied` أو `unknown applied migration version`.
- فشل `go run ./cmd/agy db migrate up`.

## 2. أوقف التغيير واجمع الحالة

1. أوقف التوسع إلى نسخ جديدة، ولا توجه حركة إضافية إلى إصدار غير سليم. لا تحذف أو تعدل يدوياً صفوف `schema_migrations`.
2. سجل إصدار التطبيق، اسم/إصدار الهجرة، وقت الفشل، سجلات PostgreSQL والتطبيق، وهل كانت نسخ التطبيق القديمة لا تزال تعمل.
3. من اتصال مخول، اقرأ السجل:

   ```sql
   SELECT version, name, checksum, applied_at
   FROM schema_migrations
   ORDER BY version;
   ```

4. قارن السجل بملفات `internal/adapters/postgres/migrations/` المضمنة في **إصدار البرنامج المراد تشغيله**. افحص آخر سجل ملتزم ووجود التغييرات المتوقعة؛ الفشل في هجرة واحدة لا يلغي الهجرات الأسبق التي نجحت.
5. حافظ على نسخة قابلة للاستعادة قبل أي محاولة إصلاح أو تراجع إذا كانت قاعدة إنتاج.

## 3. المعالجة حسب السبب

### هجرة معلقة بعد فشل التنفيذ

يطبق المحرك كل ملف أمامي وسجل checksum في معاملة واحدة. عند فشل الهجرة الحالية، يفترض أن تكون تغييرات تلك المعاملة وسجلها قد تراجعا معاً؛ قد تبقى هجرات سابقة من التشغيل ملتزمة. عالج السبب (مثل صلاحية أو تعارض بيانات أو قفل) بعد مراجعة أثره، ثم أعد تشغيل **نفس إصدار البرنامج**:

```bash
go run ./cmd/agy db migrate up
```

الأمر يحتاج `DATABASE_URL` للهدف المقصود. لا تعِد المحاولة تلقائياً قبل فهم سبب الفشل. بعد نجاحه شغّل إصدار الخدمة المتوافق، وتحقق من سجل الهجرات والجاهزية.

### اختلاف checksum لهجرة مطبقة

أوقف الإقلاع والترحيل؛ لا تتجاوز فحص checksum ولا تعدل القيمة في قاعدة البيانات. استعد ملف الهجرة الأصلي من artifact/commit الإصدار المعتمد بعد التحقق منه، أو أصدر هجرة تكميلية جديدة بعد مراجعة المخطط والبيانات. إذا لم يكن الأصل متاحاً أو كان محتوى القاعدة غير معروف، اعزل القاعدة واستعد من نسخة موثوقة أو استخدم إصلاحاً موثقاً ومراجعاً.

### سجل يحتوي إصدار هجرة غير معروف

لا تشغل نسخة تطبيق أقدم على قاعدة أحدث. حدد الإصدار الذي أنشأ السجل؛ شغّل التطبيق/أداة الترحيل من إصدار متوافق بعد مراجعة نشره. لا تحذف سجل الهجرة لإجبار إصدار قديم على العمل.

### الحاجة إلى rollback

`MigrateDown` يشغل ملفات `.down.sql` بترتيب عكسي ويزيل سجل الهجرة في المعاملة نفسها. هذا لا يجعل التراجع آمناً تلقائياً: قد يحذف بيانات أو يتعارض مع كتابات الإصدار الجديد. لا تستخدمه إلا بعد تقييم أثره وموافقة مالك البيانات، وعلى نسخة مستعادة/بيئة اختبار أولاً. عند وجود بيانات جديدة تعتمد على المخطط أو فشل تراجع آمن، فضّل roll-forward بهجرة تصحيحية أو استعادة معتمدة.

## 4. التحقق والإغلاق

```bash
go test ./internal/adapters/postgres -run 'TestFailedMigrationRollsBackAndCanBeRetried|TestMigrationUpgradeFromOldestSupportedSchemaPreservesData|TestValidateSchemaHealth'
```

تختبر هذه الحالات التراجع الذري للهجرة الفاشلة وإعادة المحاولة، الترقية من المخطط التأسيسي، ورفض الجاهزية عند وجود هجرات معلقة أو إصدار غير معروف. اختبارات PostgreSQL تتخطى نفسها إذا لم تتوفر قاعدة؛ نتيجة التخطي لا تثبت إصلاح الحادث.

لا تغلق الحادث حتى يصبح سجل الهجرات معروفاً وبصماته مطابقة، تنجح جاهزية الإصدار المقصود، وتكتمل فحوصات البيانات المناسبة. أرفق الإصدار والهجرة والقرار والأثر ونتائج التحقق في سجل الحادث، وأضف اختبار انحدار عند الحاجة.
