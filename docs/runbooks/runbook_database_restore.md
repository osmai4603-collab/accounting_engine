# Runbook: استعادة PostgreSQL والتحقق قبل إعادة الخدمة

- **الخطورة:** حادث قاعدة بيانات أو تمرين استعادة
- **المالك:** مسؤول قاعدة البيانات + مسؤول التطبيق
- **المراجع:** [`سياسة النسخ والاستعادة`](../operations/backup_and_recovery_policy.md)

## 1. الاحتواء واختيار نقطة الاستعادة

1. أعلن الحادث، أوقف الكتابة إلى قاعدة المصدر أو اعزل مسار التطبيق حسب الإجراء المعتمد، وسجل وقت الحادث وإصدار التطبيق وآخر حالة معروفة.
2. حدد قاعدة الهدف ونقطة PITR المطلوبة بموافقة مالك الحادث؛ سجل أثر فقد البيانات المتوقع مقابل RPO المعتمد. لا تكتب فوق قاعدة المصدر.
3. تحقق من سلامة ملف النسخة، مصدره، إصدار PostgreSQL، توافر الامتدادات والأدوار اللازمة، واستمرارية WAL حتى نقطة الاستعادة. إذا كانت سلسلة WAL ناقصة أو نقطة الاستعادة غير مؤكدة فتوقف وصعّد القرار.

## 2. استعادة معزولة

استعد دائماً إلى قاعدة/خادم جديد معزول عن حركة الإنتاج. اتبع آلية المشغل وإصدار PostgreSQL الفعلي.

### نسخة منطقية

لقاعدة أُنشئت باستخدام `pg_dump --format=custom`، جهّز قاعدة فارغة متوافقة ثم:

```bash
pg_restore --exit-on-error --dbname="$RESTORE_DATABASE" "$BACKUP_FILE"
```

استعد الأدوار العامة والامتدادات المطلوبة بشكل منفصل وفق إعداد البيئة. لا تستعد تفريغاً منتقياً للجداول كقاعدة إنتاج متكاملة دون التحقق من العلاقات وسياسات RLS.

### نسخة مادية وPITR

لنسخة `pg_basebackup` بصيغة tar، أوقف PostgreSQL على الهدف، جهز `PGDATA` فارغاً ومملوكاً لمستخدم PostgreSQL، واستخرج `base.tar.gz` إلى `PGDATA` و`pg_wal.tar.gz` إلى `PGDATA/pg_wal`. قبل التشغيل، اضبط `restore_command` وطريقة إعداد الاستعادة وفق إصدار الخادم وتنسيق أرشيف WAL المستخدم. مثال فقط إذا كانت ملفات الأرشيف محفوظة باسم `%f.gz`:

```ini
restore_command = 'gzip -dc /path/to/wal_archive/%f.gz > %p'
recovery_target_time = '2026-11-16 00:00:00+00'
recovery_target_action = 'promote'
```

في PostgreSQL 12+ أنشئ `recovery.signal` في `PGDATA`، ثم ابدأ الخادم المعزول وتحقق من السجلات حتى بلوغ هدف الاستعادة أو ظهور خطأ. استبدل الوقت والمسار بما اعتمد للحادث؛ المثال ليس إعداداً جاهزاً للإنتاج. لا توجه حركة التطبيق إلى هذا الهدف بعد.

## 3. فحوصات ما بعد الاستعادة

نفّذ الفحوصات وسجل نواتجها قبل السماح بالكتابة:

1. **اتصال ومخطط:** افحص سجل `schema_migrations` ومخرجات سجل الخدمة. `postgres.ValidateSchemaHealth` يتحقق من الاتصال، وجود سجل الهجرات، عدم وجود هجرات معلقة، وتطابق بصمات ملفات المصدر، ويعتبر الإصدار غير المعروف غير متوافق. يبدأ `postgres.New` بتطبيق الهجرات المعلقة؛ لذلك تشغيل الخدمة ليس فحصاً للقراءة فقط وقد يغير المخطط. استخدم شبكة معزولة ولا تفتح مسار الحركة خلالها.
2. **جاهزية:** شغّل إصدار التطبيق المقصود على الهدف المعزول، ثم افحص `/readyz` عبر العنوان الذي ضبطته الخدمة. المتوقع `200 READY` فقط إذا نجح فحص التخزين والمخطط؛ نتيجة الجاهزية لا تفحص أرصدة الأستاذ.
3. **الأرصدة:** استخدم `Driver.AssertBalancesMatchMoves(ctx, companyID, periodID, currencyID)` لكل شركة/فترة/عملة ضمن نطاق الاستعادة المعتمد، مع مقارنة عدد القيود والأرصدة بمصادر مرجعية متاحة. لا يوفر المستودع أمراً عاماً للتعداد والتحقق الشامل، لذا لا تدّع اجتياز جميع الأرصدة دون تنفيذ هذا التعداد وتسجيله.
4. **سلسلة التدقيق:** إذا كانت بيانات التدقيق ضمن نطاق التحقق، نفذ `governance.VerifyAuditIntegrity` باستخدام Repository موثوق لكل النطاق المطلوب. لا يوجد أمر CLI عام لهذا الفحص. اختبار `TestVerifyAuditIntegrityDetectsChainTampering` يثبت اكتشاف العبث في اختبار، وليس سلامة قاعدة الاستعادة بعينها.
5. **اختبار سلوكي:** اختبر قراءة بيانات ممثلة ومسار كتابة مضبوطاً داخل بيئة التمرين فقط. لا تنشئ قيوداً تجريبية غير معتمدة في قاعدة مرشحة للإنتاج.

## 4. القرار وإعادة الخدمة

- ارفض الترقية إذا تعذر تفسير أي هجرة/بصمة، فشلت مطابقة أرصدة ضمن النطاق، أو فشل فحص التدقيق المطلوب.
- سجل مصدر النسخة والهدف الزمني، إصدار PostgreSQL والتطبيق، الهجرات قبل/بعد تشغيل التطبيق، نتائج الفحوصات، زمن الاستعادة، RPO/RTO الفعليين، وموافقة مالك الحادث.
- بعد اعتماد النتائج فقط، وجّه `DATABASE_URL` أو مسار الاتصال إلى الهدف المستعاد وافتح المرور تدريجياً وفق خطة الحادث. راقب السجلات والأخطاء والتسوية بعد إعادة الخدمة.

## 5. ما يثبته اختبار المستودع

```bash
go test ./internal/adapters/postgres -run 'TestBackupRestore_IntegrityVerification|TestValidateSchemaHealth'
```

`TestBackupRestore_IntegrityVerification` يعيد إنشاء بيانات ممثلة في مخطط PostgreSQL معزول ثانٍ، ثم يتحقق من صحة المخطط وتطابق الرصيد وقراءة القيد. **لا** يستعيد ملف `pg_dump` أو نسخة مادية، ولا ينفذ PITR، ولا يتحقق من جميع شركات/فترات قاعدة حقيقية. الاختبار يتخطى نفسه عند غياب PostgreSQL؛ التخطي ليس نتيجة تمرين. يجب تنفيذ تمرين مستقل من نسخة فعلية كما هو موضح في السياسة.
