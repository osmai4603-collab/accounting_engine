# مراجعة معمارية النسخة الجديدة من Accounting Engine

**تاريخ المراجعة:** 12 نوفمبر 2026  
**الملف محل المراجعة:** `engine.zip`  
**نطاق المراجعة:** قابلية إعادة الاستخدام كـ Go Library مستقلة، حدود Public API، SPI، تركيب الوحدات، ربط SDK بالمحرك الحالي، اختبارات الاستقلال، وخدمة التشغيل.

---

## 1. الحكم التنفيذي

النسخة الجديدة تمثل **تقدمًا معماريًا واضحًا في تنظيم واجهة المنتج** مقارنة بالتصميم السابق؛ إذ أضيفت طبقات `pkg/api/v1` و`pkg/sdk` و`pkg/spi`، وأصبحت هناك محاولة صريحة للفصل بين عقود المستهلك وعقود التخزين، مع إضافة اختبارات تحمل أسماء الاختبارات المعمارية الثلاثة.

لكن الحكم النهائي هو:

> **المشروع أصبح يملك نموذجًا أوليًا لواجهة SDK عامة، لكنه لم يصبح بعد منتج Accounting Engine مستقلًا وقابلًا لإعادة الاستخدام فعليًا.**

السبب الأهم: واجهة `pkg/sdk` لا تستدعي حاليًا محرك المحاسبة الفعلي الموجود في `internal/posting` ولا بقية خدمات التطبيق في `engine.go`. بدلًا من ذلك، تنفذ عمليات مبسطة بتمريرها مباشرة إلى Store interfaces جديدة. وفي الوقت نفسه، موائما التخزين الفعليان في `storage/postgres` و`storage/memory` لا يطبّقان عقود `pkg/spi/storage` الجديدة؛ فهما ما زالا مبنيين حول أنواع ومستودعات `internal`.

بالتالي توجد حاليًا **واجهتان ومساران منفصلان**:

1. المسار القديم: `AccountingEngine` وخدماته المحاسبية الفعلية، المبنية على `internal/*`.
2. المسار الجديد: `pkg/sdk` وعقوده العامة، وهو Facade أولي محدود لا يركّب المسار القديم.

هذه الفجوة أهم من أي تحسين شكلي آخر، ويجب حلها قبل توسيع الـ API أو إعلان اكتمال اختبارات الاستقلال.

## 2. ما تحسن فعلًا

### 2.1 إنشاء مساحة عامة واضحة

التقسيم الجديد:

```text
pkg/
├── api/v1/       # العقود والأنواع العامة
├── sdk/          # واجهة استخدام المحرك
└── spi/          # نقاط التوسعة التي يطبقها المستهلك أو الموائم
    ├── standards/
    └── storage/
```

هذا اتجاه صحيح؛ لأنه يهيئ مكانًا واضحًا للعقود العامة، ويقلل الحاجة إلى كشف الحزم الداخلية مباشرة.

### 2.2 فصل واجهات التخزين حسب المسؤولية

وجود `CoreLedgerStore` و`ReportingStore` و`GovernanceStore` أفضل من إجبار كل تخزين على تنفيذ واجهة ضخمة واحدة. كما أن `WithReporting` و`WithGovernance` يقدمان بداية جيدة لفكرة أن بعض القدرات اختيارية.

### 2.3 Versioned API

وضع العقود تحت `pkg/api/v1` خطوة صحيحة من ناحية إدارة التوافق المستقبلي. لكن وجود مسار `v1` لا يعني وحده أن العقد جاهز للتثبيت؛ فما زالت هناك أنواع غير دقيقة وتفاصيل غير مكتملة موضحة لاحقًا.

### 2.4 اختبارات مخصصة للاستقلال

إضافة ملفات منفصلة لـ External Consumption وIndustry Independence وInfrastructure Independence تحسن وضوح الأهداف المعمارية. لكن الاختبارات الحالية لا تثبت بعد ما تسميه؛ لأنها تختبر SDK المبسط باستخدام Fake Stores، لا المحرك الحقيقي وموائمات التخزين الفعلية.

## 3. الفجوات الحرجة

### P0 — واجهة SDK غير متصلة بمحرك المحاسبة الحقيقي

**المواضع:**

- `pkg/sdk/builder.go`
- `pkg/sdk/engine.go`
- `engine.go`
- `internal/posting/`
- `storage/postgres/`
- `storage/memory/`

في `defaultLedgerService.PostEntry` تنتهي العملية إلى:

```go
err := s.store.PostEntry(ctx, entry)
return entry, err
```

لا يوجد استدعاء لـ `internal/posting.Engine` ولا لطبقة التطبيق التي تنفذ قواعد الترحيل. وبذلك لا تستفيد واجهة SDK تلقائيًا من قدرات المحرك الحالي مثل التحقق من الحسابات والفترات والسياسات والموافقات والتوازن والقيود الذرية، إلا إذا أعاد كل Store خارجي تنفيذها بنفسه. وهذا يعيد مسؤولية قواعد المحاسبة إلى كل نظام مستهلك أو موائم تخزين، وهو عكس الغرض من Accounting Engine.

**القرار المطلوب:** يجب أن يكون المسار:

```text
External System
      |
      v
Public SDK / Commands
      |
      v
Application Services / Use Cases
      |
      v
Existing Accounting Domain Engines
(posting, masterdata, governance, valuation, reporting...)
      |
      v
Internal Persistence Ports
      |
      v
PostgreSQL / Memory / Other Adapter
```

تكون الـ SDK Facade على المحرك الحالي، لا تطبيقًا موازيًا له. ويمكن إبقاء الأنواع العامة مستقلة عن الأنواع الداخلية عبر Mapping/Adapters عند حد التطبيق.

### P0 — موائمات التخزين الفعلية لا تطبق SPI العامة الجديدة

**المواضع:**

- `pkg/spi/storage/core.go`
- `storage/postgres/driver.go`
- `storage/postgres/posting.go`
- `storage/memory/driver.go`
- `storage/memory/posting.go`

موائم PostgreSQL يعلن تطبيقه لواجهات داخلية مثل `posting.Repository` و`reporting.Repository`، وموائم الذاكرة مبني كذلك حول أنواع `internal`. لا توجد تصريحات أو دوال تثبت أن أيًا منهما يطبق `pkg/spi/storage.CoreLedgerStore` أو بقية واجهات SPI.

النتيجة العملية: لا يمكن تمرير `*postgres.Driver` الحالي إلى `sdk.WithCoreStorage` باعتباره تطبيقًا للعقد العام. والاختبار الحالي لا يكشف هذه الفجوة لأنه يستخدم Fake Store مكتوبًا خصيصًا للواجهة الجديدة.

**القرار المطلوب:** بناء Adapters واضحة تربط العقود العامة بالخدمات والمستودعات الداخلية، أو إعادة تصميم Ports بحيث تكون هي Ports التطبيق الفعلية وتطبقها موائمات التخزين الحقيقية. يجب ألا يضطر المستهلك إلى معرفة SQL أو بنية PostgreSQL.

### P0 — عمليات SDK الحالية لا تحافظ على الصحة المحاسبية

#### أ. الترحيل المباشر

`PostEntry` يمرر القيد مباشرة إلى Store دون تحقق ظاهر في طبقة المحرك العامة من:

- توازن المدين والدائن.
- صلاحية الحسابات وانتمائها للشركة.
- صلاحية الفترة وحالتها.
- العملة الوظيفية والعملة المعاملة واتساق أسعار الصرف.
- صلاحية حالة القيد وانتقالاته.
- صلاحيات الترحيل والموافقة وMaker-Checker.
- Idempotency ومنع تكرار الترحيل.

قد ينفذ Store معين بعض هذه الضوابط، لكن عقد SPI لا يضمنها، ولا يربطها بمحرك Posting الحالي. لذلك لا يجوز اعتبار هذه الواجهة حاليًا بوابة ترحيل محاسبية موثوقة.

#### ب. العكس ReverseEntry

الدالة الحالية تنسخ القيد الأصلي بالكامل ثم تغيّر معرّف القيد والحالة والتصنيف وتضع `ReversalOfID`. لكنها لا تعكس مبالغ المدين والدائن في السطور، ولا تستخدم `reason`، ولا تظهر عملية ذرية لتغيير حالة الأصل ومنع عكسه أكثر من مرة.

هذا ليس عكسًا محاسبيًا صحيحًا؛ إنه إنشاء نسخة أخرى من القيد بنفس اتجاه المبالغ.

**المطلوب:** تنفيذ العكس عبر خدمة Posting الفعلية ومعاملة ذرية، مع تبديل Debit/Credit في كل سطر، حفظ سبب العكس، ربط الأصل والعكس، والتحقق من عدم عكس القيد مرتين ومن صلاحية الفترة وتاريخ العكس.

#### ج. معالجة الحدث ProcessEvent

الدالة تنشئ JournalEntry جديدًا دون أي `Lines`، ثم ترسله للـ Store. لا تستخدم `Amount` أو `Dimensions` أو `Payload` أو `IdempotencyKey`، ولا تبحث عن قاعدة محاسبية مرتبطة بـ `EventType`.

وبالتالي فإن `HARVEST_CROP` و`POS_SALE` و`SUBSCRIPTION_REVENUE` تؤدي جميعها إلى قيد فارغ تقريبًا، لا إلى قيود تعكس المعنى الاقتصادي لكل حدث.

**المطلوب:** يجب أن يكون مسار الحدث: التحقق من الحدث → تحديد القاعدة المحاسبية → إنشاء سطور القيد → التحقق من التوازن والأبعاد والفترة → ترحيل ذري → تسجيل مفتاح Idempotency والنتيجة. لا ينبغي أن تفسر النواة المجال التشغيلي نفسه؛ بل تستقبل Canonical Accounting Event أو Accounting Command ينتجه Adapter خاص بالنظام الخارجي.

## 4. Bootstrap وOptional Modules

**الموضع:** `pkg/sdk/builder.go`

### الإيجابيات

- `CoreLedgerStore` إلزامي عند Build.
- Reporting وGovernance لهما Store interfaces منفصلة.
- يمكن إضافة StandardModule عبر Option.

### النواقص

1. `Build` لا يتحقق من وجود `ReportingStore` عند تفعيل Reporting، ولا `GovernanceStore` عند تفعيل Governance. بل يعيد Service دائمًا ثم يظهر الخطأ عند أول استدعاء. الأفضل أن تكون القدرة غير مفعّلة وغير متاحة، أو يفشل Build برسالة توضّح الاعتمادية المفقودة.
2. `StandardModule` لا يعلن قائمة `Requires/Provides` أو اعتمادياته المحددة؛ ويُمرر له `CoreLedgerStore` فقط.
3. `RegisterRules` و`RunScheduledJobs` معرفتان بوسائط `interface{}`، ولا يتم استدعاؤهما أثناء Build.
4. تطبيقات الوحدات الأربع في `modules/ias12` و`modules/ifrs15` و`modules/ifrs16` و`modules/ifrs9` مجرد هياكل: `RegisterRules` و`RunScheduledJobs` تعيدان `nil` دون تنفيذ أو تسجيل قواعد فعلية.
5. `NewBuilder` يتجاهل الأخطاء المعادة من Option عبر `_ = opt(b)`. هذا يسمح بإخفاء أخطاء إعداد مستقبلية.
6. لا توجد معالجة واضحة لوحدة nil أو الوحدات المكررة، ولا تحقق من الاعتماديات المتبادلة بين الوحدات.
7. وسيط `ctx` في `Build` غير مستخدم.

**التوصية:** إنشاء Module Registry بعقود typed، يعرّف كل Module اسمًا وإصدارًا وCapabilities وRequiredPorts وDependencies، ثم يفعل الوحدات وفق Graph تحقق من الاعتماديات. مثلًا Reporting لا يُفعّل إلا عند توفير مصدر بيانات التقارير المطلوب. ولا ينبغي أن تحمل النواة اعتماديات معيار IFRS لا يحتاجها كل مستهلك.

## 5. الاختبارات المعمارية الثلاثة

### 5.1 External Module Consumption — غير مثبت حتى الآن

`test/acid/external_consumption_test.go` موجود داخل نفس Module، ويستخدم Fake Store. هذا اختبار لاستخدام الحزم العامة من Package أخرى داخل المستودع، لكنه ليس اختبار مستهلك مستقل في Module خارجي.

كما أن `go.mod` يستخدم:

```go
module accounting_engine
```

وهذا ليس مسار نشر مناسبًا لمكتبة Go يستهلكها مشروع مستقل. ينبغي اعتماد مسار Module رسمي قابل للتنزيل مثل `github.com/<organization>/accounting-engine` بعد تحديد الناشر.

هناك كذلك حزمة جذرية عامة `package accounting_engine` في `engine.go` تكشف حقولًا وأنواعًا من `internal/*`. أما `scripts/check_public_api_purity.sh` فيفحص `pkg/` فقط، وبالتالي لا يغطي هذه الواجهة الجذرية.

**الاختبار المقبول:** إنشاء Fixture في مجلد مستقل له `go.mod` خاص به، لا يكون تابعًا لشجرة الوحدة الأصلية، ثم يستهلك SDK وموائم PostgreSQL من المسار الرسمي فقط. يجب أن يبني ويشغّل سيناريو محاسبيًا حقيقيًا دون استيراد أي `internal/*` أو التعامل مع SQL.

### 5.2 Industry Independence — الاختبار الحالي شكلي

الاختبار يمرر ثلاثة Event Types، ويتحقق من أن ثلاثة قيود وصلت إلى Fake Store. لكنه لا يتحقق من أن الحدث أنتج قيدًا صحيحًا أو متوازنًا أو ذا سطور محاسبية صحيحة؛ بل إن `ProcessEvent` لا يستخدم قيمة الحدث المالية أصلًا.

**الاختبار المقبول:** لكل قطاع، إنشاء Adapter خارجي ينتج Canonical Accounting Event ثم إثبات أن النواة تستقبل العقد المحاسبي الموحد وتنتج قيدًا متوازنًا صحيحًا. تُقارن نتائج الترحيل لا أسماء الأحداث وعدد الاستدعاءات فقط.

أمثلة قطاعات مناسبة:

- التجارة: بيع نقدي وبيع آجل وإرجاع ومخزون وضرائب.
- الزراعة: حصاد أو تغير قيمة أصل بيولوجي، وفق السياسة المحاسبية المختارة.
- الخدمات: فاتورة خدمة ومقابل مقدم/إيراد مؤجل والاعتراف بالإيراد.
- الصناعة: استهلاك مواد وتحويل تكاليف إنتاج ومخزون تام.

تفاصيل العمليات تبقى في Adapters/Business Systems، بينما النواة تتعامل مع الأثر المحاسبي المعياري.

### 5.3 Infrastructure Independence — الاختبار الحالي جزئي

اختبار الاستقلال يستخدم Fake Memory Store خاصًا بالاختبار، وليس `storage/memory.Driver` الفعلي، لأن الأخير لا يطبق SPI الجديدة. لذلك يثبت أن SDK يمكنه التفاعل مع كائن وهمي يحقق واجهة التخزين، لكنه لا يثبت قابلية تبديل موائمات المشروع الحقيقية.

**الاختبار المقبول:** نفس سيناريو المحاسبة ونفس عقد SDK يمران على Memory Adapter حقيقي وPostgreSQL Adapter حقيقي، مع فحص النتائج والتعامل مع الفشل والتزامن وإعادة المحاولة. ويجب ألا يتغير كود المستهلك عند تبديل نوع التخزين.

## 6. جودة العقود العامة قبل تثبيت v1

يجب معالجة النقاط التالية قبل اعتبار `pkg/api/v1` عقدًا مستقرًا:

- `CompanyID`, `AccountID`, `FiscalPeriodID`, `JournalEntryID` معرفة كـ type aliases لـ `uuid.UUID`؛ لذلك لا تحقق تمييزًا نوعيًا فعليًا بين الهويات. يفضّل تعريف أنواع مستقلة مع Constructors/Parse/Marshal مناسبة.
- لا يوجد `FiscalYearID` ضمن الأنواع العامة.
- `FiscalYear.ID` معرف على أنه `CompanyID` ويوجد تعليق `// or ID`، كما أن `FiscalPeriod.FiscalYearID` معرف كـ `CompanyID`. يجب إنشاء نوع FiscalYearID وربطه بشكل صحيح.
- `EntryLine.ID` معرف كـ `AccountID`؛ يجب تخصيص `JournalEntryLineID`.
- `PartnerID` و`CostCenterID` و`ProjectID` و`SegmentID` و`BusinessUnitID` جميعها ممثلة بـ `*CompanyID`. يجب استخدام أنواع نطاقية مناسبة أو عقد معرفات موحد موثق، لا إعادة استخدام CompanyID دلاليًا.
- `TransactionAmount` من نوع `Money` ويحتوي أصلًا على العملة، مع وجود `TransactionCurrency` منفصل؛ يجب فرض الاتساق أو إزالة التكرار.
- يجب توثيق حقول القيود، حالات الانتقال، قواعد صحة السطر، دلالة العملات وأسعار الصرف، وقواعد التواريخ بصورة صريحة.

هذه التعديلات مهمة لأن `v1` تصبح أساس التوافق التي سيبني عليها مستهلكون خارجيون.

## 7. خدمة Microservice ليست جاهزة بعد

**المواضع:** `cmd/accounting-service/*`, `proto/accounting/v1/ledger.proto`, `deployments/Dockerfile`

الخدمة الحالية Scaffold وليست خدمة تشغيلية مكتملة:

- `main.go` ينشئ `memoryCoreStore` يضمّن `storage.CoreLedgerStore` بقيمة nil، ولا يفتح PostgreSQL أو يهيئ موائمًا حقيقيًا.
- قيمة `cfg.Database` لا تستخدم لاختيار Driver.
- `/api/v1/entries` يعيد `entry-stub-001` ثابتًا ولا يستدعي Engine.
- `/api/v1/trial-balance` يعيد `is_balanced: true` وقائمة فارغة ثابتة.
- `/readyz` يعيد READY دائمًا دون التحقق من جاهزية التخزين أو المحرك.
- `/metrics` يعيد Gauge ثابتًا، لا مقاييس تشغيل فعلية.
- `GRPCPort` معرف في Config ويعرضه Docker، لكن `RunServer` لا يبدأ خادم gRPC.
- ملف Proto يعرّف حقولًا أولية جدًا، ولا يمثل بعد عقدًا كافيًا لترحيل قيد متعدد السطور والعملات والأبعاد، ولا تظهر ملفات Go مولدة أو إعداد Build يثبت استخدامها.
- Dockerfile يستخدم `golang:1.22-alpine`، في حين يطلب `go.mod` الإصدار `go 1.26.11`. هذه عدم مطابقة تمنع بناء الصورة بهذا الأساس كما هو.

**القرار:** لا تجعل Microservice شرطًا لإنجاز المنتج. اجعل Go Library هي التوزيعة الأساسية، ثم أضف HTTP/gRPC Service كـ Deployment Adapter عند اكتمال SDK والموائمات. عندها يجب أن يستدعي كل Handler نفس Application Services المستخدمة داخل المكتبة.

## 8. ما لم يتم التحقق منه

تعذر تشغيل `go test ./...` في بيئة المراجعة. الإصدار المحلي هو Go 1.23.2، بينما `go.mod` يطلب Go 1.26.11، ومحاولة الحصول على Toolchain المطلوب لم تنجح بسبب عدم توفر الاتصال بمصدر تنزيل Go.

لذلك هذه مراجعة Static Code / Architecture Review وليست تقريرًا عن نجاح Build أو الاختبارات. لا أعتبر وجود الاختبارات في المستودع دليلًا على نجاحها.

## 9. خطة المعالجة ذات الأولوية

### المرحلة الأولى — توحيد مدخل المنتج

1. اعتماد Module Path رسمي قابل للاستهلاك الخارجي.
2. تحديد `pkg/sdk` كواجهة المنتج الوحيدة.
3. نقل أو إخفاء الواجهة الجذرية الحالية التي تكشف أنواع `internal`، أو تحويلها إلى Facade توافقية تستخدم Public API فقط.
4. توسيع API بالحد الأدنى اللازم لإعداد الشركة ودليل الحسابات والسنوات والفترات المالية قبل الترحيل.
5. مراجعة كل أنواع `api/v1` وتصحيح IDs والحقول الدلالية قبل تثبيت Version 1.

### المرحلة الثانية — ربط SDK بالمحرك الحقيقي

1. وضع Application Services عامة خلف SDK.
2. توصيل Ledger Service بـ `internal/posting.Engine`، وليس بالـ Store مباشرة.
3. توصيل Master Data وValuation وGovernance وSubledgers وReporting عبر Use Cases واضحة.
4. إضافة Mapping/Adapters بين Public DTOs والـ internal domain types.
5. ضمان أن جميع مسارات Posting وReversal تمر عبر نفس الضوابط المحاسبية.

### المرحلة الثالثة — تفعيل موائمات التخزين الحقيقية

1. جعل Postgres Adapter يطبق SPI العامة أو Ports التطبيق المعيارية.
2. جعل Memory Adapter يطبق العقد نفسه.
3. إضافة Compile-time interface assertions لكل Adapter.
4. إضافة اختبارات Contract موحدة تعمل على Memory وPostgreSQL.
5. اختبار فشل المعاملة، الإلغاء، التزامن، إعادة المحاولة، Idempotency، والعكس الذري.

### المرحلة الرابعة — Event Ingestion وModules

1. تحديد Canonical Accounting Event وAccounting Command بوضوح.
2. تصميم Posting Rule Registry typed مع Versioning وتحديد أولوية وتاريخ سريان القواعد.
3. تنفيذ Idempotency على مستوى الشركة/المصدر/المفتاح وبضمان تخزيني ذري.
4. تعريف Module Manifest يتضمن Requires/Provides وإصدارات العقود.
5. وصل وحدات IFRS الفعلية الموجودة في `internal` بالوحدات العامة، وعدم تقديم Modules فارغة على أنها جاهزة.
6. اختبار أن غياب Reporting Store يمنع تفعيل Reporting فقط، لا المحرك الأساسي، وأن أي Module لا يعمل دون اعتمادياته المطلوبة.

### المرحلة الخامسة — الاختبارات وخدمة التشغيل

1. نقل External Consumer Fixture إلى Module مستقل خارج الوحدة.
2. إعادة كتابة Industry Independence لتفحص نتائج القيود المحاسبية لا مجرد عدد الأحداث.
3. إعادة كتابة Infrastructure Independence باستخدام الموائمات الحقيقية.
4. تحديث Dockerfile وCI لنسخة Go المتوافقة مع `go.mod`.
5. جعل HTTP/gRPC Handlers تستدعي SDK الفعلي، وإضافة readiness حقيقية وgraceful shutdown ومهلات HTTP.

## 10. قرار Go Library أم Microservice

أوصي بأن يكون المنتج الأساسي:

**Universal Accounting Engine = Go Library + Public SDK + SPI + Adapters**

ويكون Microservice خيار نشر فوق المكتبة، لا بديلًا عنها.

هذا يمنح الأنظمة التي تعمل داخل عملية Go إمكانية تضمين المحرك مباشرة، ويتيح للأنظمة متعددة اللغات أو المنفصلة تشغيليًا استهلاكه عبر HTTP/gRPC لاحقًا. المهم ألا ينشأ من ذلك منطق محاسبي مختلف بين نمط المكتبة ونمط الخدمة؛ يجب أن يمر الاثنان عبر نفس Application Services.

## 11. الخلاصة

النسخة الجديدة أفضل من السابقة من ناحية اتجاه التصميم وتسمية الحدود، لكنها **لا تحقق بعد اختبارات المنتج الثلاثة بصورة حقيقية**. أكبر مخاطرة هي أن يتم توسيع `pkg/sdk` كتنفيذ ثانٍ مبسط بدل أن يصبح واجهة للمحرك المحاسبي الناضج داخل `internal`.

لا أوصي بإعادة كتابة المحرك الداخلي من الصفر. أوصي بالحفاظ على منطق المحاسبة الحالي، ووضع Application Layer نظيفة حوله، ثم جعل SDK واجهة لهذه الطبقة، وتوصيل موائمات التخزين الحقيقية بها.

**معيار قبول النسخة القادمة:** يجب أن يستطيع مشروع Go جديد، في Module مستقل، إنشاء المحرك باستخدام Public SDK وPostgreSQL Adapter، وتهيئة الشركة ودليل الحسابات والفترة المالية، ثم إنشاء قيد صحيح وترحيله وعكسه وإنتاج ميزان مراجعة؛ دون استيراد `internal/*` أو معرفة SQL أو تفاصيل PostgreSQL، وبنفس السلوك عند استخدام Memory Adapter في اختبارات العقود.
