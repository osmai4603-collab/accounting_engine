# المرحلة الثانية: وحدات السياسات المحاسبية والإعدادات

## Phase 2: Policy & Configuration Units

**الهدف العام للمرحلة:** تجميع منطق السياسات المالية الموزع داخل وحدات سياسات مستقلة ومؤرخة بالإصدارات الفعالة (**Versioned Policy Units**)، تضمن ثبات المعالجات المحاسبية وقابليتها للتدقيق والتفسير التاريخي دون أي تضارب.

---

### المهمة 2.1: وحدة سياسات العملات والتقريب المالي (Currency & Rounding Policy Unit)

* **المشكلة الحالية:**
  سياسات العملات والتقريب موزعة بين حزمة `types` وحزمة `valuation` وحزمة `posting`؛ حيث يتم استخدام قيم ثابتة للدقة (FinancialScale = 4, InternalScale = 12) بدون إمكانية تخصيص سياسة التقريب للعملات التي لا تقبل كسوراً (مثل الين الياباني JPY) أو العملات ذات الثلاث خانات (مثل الدينار الكويتي KWD)، كما تفتقر التقارير لسياسة واضحة تلزم بإصدار القوائم بعملة العرض المعتمدة للشركة.
* **الهدف:**
  إنشاء وحدة متخصصة باسم `CurrencyPolicyUnit` تتولى إدارة قواعد العملات والتقريب على مستوى كل شركة، وتفرض قواعد التعامل مع العملة الوظيفية، وعملة العرض، وسياسات التقريب المصرفي (Banker's Rounding vs Half-Up).
* **السياق الفني والمحاسبي المطلوب:**
  * **المعيار الدولي:** معيار المحاسبة الدولي **IAS 21 (الفقرات 8–14)** بشأن تحديد العملة الوظيفية وعملة العرض، ومواصفة **ISO 4217** للوحدات الصغرى للعملات (Minor Units: 0 لـ JPY، 2 لـ USD/SAR، 3 لـ KWD/BHD).
  * **معايير الحسابات المالية:** مبدأ الحفاظ على الدقة الرياضية الكاملة في الحسابات الوسيطة (Internal Precision 12-digit) وتطبيق قواعد التقريب المعتمدة فقط عند الترحيل النهائي وتوليد القوائم المالية.
* **خطوات التنفيذ المحددة:**
  1. تعريف بنية `CurrencyPolicy` في وحدة مستقلة:

     ```go
     type CurrencyPolicy struct {
         CompanyID            uuid.UUID
         FunctionalCurrency   string
         PresentationCurrency string
         RoundingMethod       financialtypes.RoundingMethod
         ToleranceScale       int
         AllowedCurrencies    []string
         EffectiveDate        time.Time
     }
     ```

  2. إنشاء `CurrencyPolicyUnit` لتوفير واجهات تحقق تفحص القيد قبل ترحيله:
     * هل العملة المستخدمة ضمن العملات المصرح بها للشركة؟
     * هل تم التقريب وفق الوحدات الصغرى للعملة المحددة؟
     * هل فروق التقريب (Rounding Differences) تُرحل تلقائياً إلى حساب تسوية فروق العملة المخصص؟
  3. ربط محركات التقارير بالوحدة لتقديم القوائم تلقائياً بعملة العرض الرسمية للشركة مع إمكانية الترجمة لعملات أخرى عند الطلب الصريح.
* **معايير قبول نفاذ المهمة (Acceptance Criteria):**
  * [ ] كتابة اختبار يثبت التقريب الصحيح لقيد بالين الياباني (بدون أي كسور) وقيد بالدينار الكويتي (3 خانات عشرية) وقيد بالريال السعودي (خانتان عشريتان).
  * [ ] التأكد من معالجة فروق التقريب العشرية في قيد متوازن دون فقدان سنت واحد.

### المهمة 2.2: وحدة سياسات الترحيل والفترات المالية (Posting & Fiscal Policy Unit)

* **المشكلة الحالية:**
  قواعد التحقق من إمكانية الترحيل، وتواريخ القيود السابقة (Back-dating)، والتعديل على المسودات مشتتة بين خدمات `posting` و `masterdata`. لا توجد سياسة موحدة تحدد متى يُسمح بترحيل قيد في فترة سابقة مفتوحة، أو متى يُشترط الحصول على تفويض استثنائي للترحيل بتاريخ سابق.
* **الهدف:**
  إنشاء `PostingPolicyUnit` لمركزة شروط وقواعد قبول وترحيل القيود اليومية والفترات المالية، وتطبيق حدود الرقابة الداخلية بشكل استباقي.
* **السياق الفني والمحاسبي المطلوب:**
  * **المعيار المحاسبي:** معيار المحاسبة الدولي **IAS 10 (الأحداث بعد فترة التقرير)**، ومتطلبات المراجعة الداخلية للفصل بين العمليات الجارية والتعديلات اللاحقة، وقواعد إقفال الفترات (Soft Close vs Hard Close).
* **خطوات التنفيذ المحددة:**
  1. تعريف `PostingPolicy` متضمنة الشروط التالية:
     * الحد الأقصى للأيام المسموح بها لتسجيل قيد بتاريخ سابق (Back-dating threshold).
     * سياسة الترحيل في الفترات المغلقة إدارياً (Soft Closed) واشتراط صلاحية مدير الحسابات.
     * سياسة منع الترحيل القطعي في الفترات المقفلة نهائياً (Hard Closed) بدون أي استثناء.
     * سياسة فرض إسناد مراكز التكلفة والأبعاد التحليلية للحسابات الإيرادية والمصروفية.
  2. دمج الوحدة كخطوة فحص إلزامية في خط ترحيل القيد (`posting.Engine.PrepareForPosting`).
* **معايير قبول نفاذ المهمة (Acceptance Criteria):**
  * [ ] رفض ترحيل أي قيد بتاريخ سابق يتجاوز المهلة المحددة في سياسة الشركة دون الحصول على موافقة استثنائية.
  * [ ] رفض الترحيل في فترة Hard-Closed مهما كانت صلاحيات المستخدم، وإثبات ذلك باختبار تكامل مع قاعدة البيانات.

### المهمة 2.3: تأريخ وتحديد إصدارات السياسات المحاسبية (Versioned & Effective-Dated Policies)

* **المشكلة الحالية:**
  عند تعديل أي إعداد أو سياسة محاسبية داخل النظام (مثل تغيير طريقة الإهلاك، أو تعديل نسبة التقريب، أو تغيير عتبة الموافقة)، قد يتم تطبيق التعديل بأثر فوري يؤثر سلباً على نتائج إعادة احتساب الفترات المالية السابقة، مما يخل بمبدأ الثبات التاريخي للبيانات المالية.
* **الهدف:**
  بناء آلية تأريخ زمني وإصدارات رقمية (`Effective-Dated & Versioned Policies`) لكافة السياسات المحاسبية، بحيث يحمل كل قرار تاريخ بداية نفاذ وتاريخ انتهاء.
* **السياق الفني والمحاسبي المطلوب:**
  * **المعيار الدولي:** معيار المحاسبة الدولي **IAS 8 (السياسات المحاسبية والتغييرات في التقديرات المحاسبية والأخطاء)**؛ حيث يفرق المعيار بين التغيير في السياسة المحاسبية (الذي يتطلب تطبيقاً بأثر رجعي مع إعادة تبويب الفترات المقارنة) وبين التغيير في التقدير المحاسبي (الذي يُطبق بأثر مستقبلي).
* **خطوات التنفيذ المحددة:**
  1. إنشاء نموذج موحد للسياسات المؤرخة:

     ```go
     type EffectivePolicyHeader struct {
         PolicyID      uuid.UUID
         CompanyID     uuid.UUID
         Version       int
         EffectiveFrom time.Time
         EffectiveTo   *time.Time
         CreatedBy     string
         ApprovedBy    string
         CreatedAt     time.Time
     }
     ```

  2. توفير دالة استعلام تاريخية: `GetPolicyAsOf(ctx, companyID, asOfDate time.Time)`.
  3. ربط محرك التحقق ومحرك التقارير بالسياسة التي كانت سارية في تاريخ المعاملة الفعلية وليس تاريخ اليوم.
* **معايير قبول نفاذ المهمة (Acceptance Criteria):**
  * [ ] اختبار يثبت أن استدعاء المحرك لتفسير قيد مسجل في 2024 يعتمد سياسة 2024 حتى بعد صدور سياسة جديدة لعام 2025.
  * [ ] حفظ سجل غير قابل للتعديل (Audit Log) لجميع عمليات إضافة أو تعديل السياسات المحاسبية.
