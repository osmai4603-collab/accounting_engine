# المرحلة `P10` — رفع الدفاتر الفرعية إلى الواجهات العامة ومحاسبة المعاملات بالعملات الأجنبية

- **الهدف:** إتاحة الدفاتر الفرعية الأساسية (الذمم المدينة والدائنة، الأصول الثابتة، والخزينة) للمستهلكين الخارجيين عبر Public SPI و Public API، مع الفصل المعماري الصارم بين عمليات الدفتر الفرعي الإدارية والأحداث المحاسبية المنتجة لقيود GL، والتحقق الوظيفي من معالجة المعاملات بالعملات الأجنبية وإعادة تقييم البنود النقدية.
- **عدد المهام:** 4 مهام (`P10-01` إلى `P10-04`)
- **الاعتماديات:** `P8-01`، و `P8-04`، و `P9-01` (لربط تسويات الفترات والمطابقة)

---

## مبدأ معماري ملزم لمرحلة P10: الفصل بين العمليات والأحداث المحاسبية

> [!IMPORTANT]
> **ليست كل عملية في الدفتر الفرعي تُنتج قيداً في الدفتر الأستاذ العام (GL).**
> يجب الفصل التام بين 5 مستويات لكل دفتر فرعي:
>
> 1. **Subledger Domain Operations:** عمليات وظيفية وإدارية تخص نطاق الدفتر الفرعي نفسه (مثل تسجيل حساب بنكي، تحديث بيانات مورد، استعلام).
> 2. **Accounting Events:** أحداث مالية ناشئة يترتب عليها أثر محاسبي صريح.
> 3. **Journal Draft Generation:** تحويل الحدث المالي إلى مسودة قيد متوازنة تستند إلى حسابات الرقابة (Control Accounts).
> 4. **Posting via Application Layer:** ترحيل القيد رسمياً إلى الدفتر العام.
> 5. **Subledger-to-GL Reconciliation:** مطابقة رصيد الدفتر الفرعي التراكمي مع رصيد حساب الرقابة المقابل.

---

## تفاصيل المهام

### `P10-01` — رفع الذمم المدينة والدائنة (AR/AP) إلى Public SPI

- **المشكلة التي تحلها:** كود الذمم موجود داخلياً في `internal/subledgers/receivable.go` و `payable.go`، ولا يمكن لأي تطبيق خارجي استخدامه كجزء من الـ SDK العام. بالإضافة إلى ذلك، لا يوجد تمييز واضح بين إدارة الفواتير والمطالبات وبين الترحيل المحاسبي لحسابات الرقابة (Accounts Receivable / Accounts Payable Control Accounts).

- **الهدف الذي تحققه:** إتاحة واجهات عامة في `pkg/api/v1/subledger/` و `pkg/spi/subledger/` لإدارة دورة حياة الذمم مع الفصل الصريح بين العمليات الإدارية والأحداث المحاسبية، وضمان مطابقة رصيد الذمم مع حسابات الرقابة.

- **تصنيف عمليات AR/AP والأثر المحاسبي:**

| العملية (Operation) | هل تنتج قيد GL؟ | السبب والتوجيه المحاسبي |
| --------------------- | ----------------- | ------------------------- |
| إنشاء ذمة/فاتورة (Create Invoice/Receivable) | ✅ نعم | اعتراف بالذمة والإيراد/الضريبة عبر Control Account |
| تسجيل دفعة/تحصيل (Record Payment/Collection) | ✅ نعم | تسوية الذمة وتأثير حساب النقدية/البنك |
| شطب ذمة معدومة (Write-Off) | ✅ نعم | إثبات خسائر ديون معدومة وتخفيض الذمة |
| تعديل بيانات العميل/المورد (Update Master) | ❌ لا | عملية إدارية بحتة لا أثر مالي لها |
| استعلام الأرصدة وأعمار الديون (Aging Inquiry) | ❌ لا | استعلام وقراءة بيانات فقط |

- **نطاق المهمة:**
  - `pkg/api/v1/subledger/` — نماذج البيانات العامة: `Receivable`, `Payable`, `Payment`, `AgingBucket`
  - `pkg/spi/subledger/` — واجهات التخزين والعمليات: `ReceivableStore`, `PayableStore`
  - `internal/subledgers/` — تكييف التنفيذ الداخلي لتغذية الواجهات العامة
  - `pkg/sdk/builder.go` — خيار تفعيل `WithSubledgerARAP` كقدرة اختيارية
  - اختبارات استهلاك خارجي ومطابقة مع GL

- **خطوات التنفيذ:**
  1. تصميم الواجهات والأنواع العامة في `pkg/api/v1/subledger/` و `pkg/spi/subledger/`.
  2. تحديد وتوثيق مخطط حسابات الرقابة (Control Accounts Mapping): ربط ذمم العملاء بحساب الرقابة المدين، وذمم الموردين بحساب الرقابة الدائن.
  3. تنفيذ توليد مسودات القيود عند وقوع الأحداث المحاسبية المحددة فقط (إنشاء، سداد، شطب).
  4. منع العمليات الإدارية (مثل الاستعلام والتحديث الوصفي) من استدعاء خط الترحيل أو حجز أي تسلسلات.
  5. بناء وظيفة المطابقة الدورية (Reconciliation Report): التحقق الآلي من أن مجموع أرصدة سجلات الذمم يساوي رصيد حساب الرقابة في ميزان المراجعة.
  6. إتاحة الذمم كقدرة اختيارية للمستهلك عبر الـ Builder.

- **الاعتماديات:** `P8-01`، `P8-04`، و `P9-01`.

- **معايير القبول:**
  - [ ] حزم `pkg/api/v1/subledger/` و `pkg/spi/subledger/` خالية من أي استيراد لـ `internal`.
  - [ ] العمليات الإدارية لا تُنتج قيوداً ولا تؤثر على الدفتر الأستاذ العام.
  - [ ] كل حركة مالية (فاتورة، سداد، شطب) تُنتج قيداً متوازناً عبر حساب الرقابة الصحيح.
  - [ ] نجاح المطابقة التامة بين أرصدة الذمم التفصيلية ورصيد حساب الرقابة في GL.
  - [ ] قدرة المستهلك على تشغيل المحرك بدون تفعيل وحدة الذمم (اختيارية تامة).

### `P10-02` — رفع الأصول الثابتة (Fixed Assets) إلى Public SPI

- **المشكلة التي تحلها:** إدارة الأصول الثابتة وجداول الإهلاك محصورة حالياً في `internal/subledgers/fixed_assets.go`، مما يحرم الأنظمة الخارجية من الاستفادة من احتساب الإهلاك وإعادة التقييم والاستبعاد برمجياً.

- **الهدف الذي تحققه:** إتاحة واجهات عامة لإدارة سجل الأصول الثابتة واحتساب الإهلاك الدوري وإعادة التقييم والاستبعاد، مع ربط الأحداث المحاسبية بحسابات الأصول ومجمع الإهلاك والأرباح/الخسائر الرأسمالية.

- **تصنيف عمليات الأصول الثابتة والأثر المحاسبي:**

| العملية (Operation) | هل تنتج قيد GL؟ | السبب والتوجيه المحاسبي |
| --------------------- | ----------------- | ------------------------- |
| تسجيل أصل جديد (Register Asset) | ❌ لا (أو اختياري) | إذا كان الشراء مُثبت بقيد مستقل؛ أما إذا كان الشراء من خلال العملية فينتج قيد أصل/نقدية |
| تشغيل الإهلاك الدوري (Run Depreciation) | ✅ نعم | إثبات مصروف الإهلاك وإضافته إلى مجمع الإهلاك |
| إعادة تقييم الأصل (Asset Revaluation) | ✅ نعم | تعديل القيمة الدفترية مقابل فائض إعادة التقييم أو الأرباح والخسائر |
| استبعاد/بيع الأصل (Disposal/Scrapping) | ✅ نعم | إلغاء تكلفة الأصل ومجمعه وإثبات ربح أو خسارة الاستبعاد |
| جرد الأصل أو تغيير موقعه (Physical Audit) | ❌ لا | عملية لوجستية وإدارية |

- **نطاق المهمة:**
  - `pkg/api/v1/subledger/` — نماذج: `FixedAsset`, `DepreciationSchedule`, `AssetDisposal`
  - `pkg/spi/subledger/` — واجهات: `FixedAssetStore`, `DepreciationCalculator`
  - `internal/subledgers/fixed_assets.go`, `asset_schedule.go`
  - اختبارات دورة حياة الأصل الكاملة

- **خطوات التنفيذ:**
  1. صياغة الأنواع العامة وإتاحة طرق الإهلاك الشائعة (القسط الثابت، القسط المتناقص).
  2. تصميم توليد قيد الإهلاك الدوري وتكامله كقيد تسوية (`EntryClassAdjusting`) مرتبط بـ `P9-03`.
  3. تنفيذ قيود إعادة التقييم (Revaluation Surplus / Deficit) وفق المتطلبات المحاسبية.
  4. تنفيذ قيود الاستبعاد (Disposal) مع إثبات المقبوضات وتصفية مجمع الإهلاك وإثبات الناتج الرأسمالي.
  5. التأكد من أن التحديثات الوصفية ومواقع الأصول لا تثير أي قيود محاسبية.

- **الاعتماديات:** `P8-01`، `P8-04`، و `P9-01`.

- **معايير القبول:**
  - [ ] الواجهات العامة للأصول معرّفة بالكامل في الـ Public API/SPI.
  - [ ] الإهلاك الدوري يُنتج قيد تسوية دقيق الحسابات ومرتبط بحساب الرقابة ومجمع الإهلاك.
  - [ ] الاستبعاد يحسب الربح أو الخسارة الرأسمالية بدقة وينتج القيد الصحيح.
  - [ ] العمليات غير المالية لا تؤثر على الدفتر الأستاذ.
  - [ ] اختبار دورة حياة أصل كاملة من الاستحواذ إلى الإهلاك وإعادة التقييم والاستبعاد.

### `P10-03` — رفع الخزينة (Treasury) إلى Public SPI وتحديد نطاق المطابقة البنكية

- **المشكلة التي تحلها:** إدارة الحسابات البنكية ومطابقتها وعمليات الخزينة داخلية في `internal/subledgers/treasury.go`، مع غياب التمييز بين قراءة كشوف الحسابات (Bank Statements) والعمليات المالية المنشئة لقيود.

- **الهدف الذي تحققه:** إتاحة واجهات إدارة الخزينة العامة، مع دعم عمليات التحويل والمطابقة البنكية، وتأكيد أن استيراد كشف الحساب وعملية المطابقة ذاتها لا تولد قيوداً إلا عند تسوية فروقات معتمدة.

- **تصنيف عمليات الخزينة والأثر المحاسبي:**

| العملية (Operation) | هل تنتج قيد GL؟ | السبب والتوجيه المحاسبي |
| --------------------- | ----------------- | ------------------------- |
| تسجيل/تعديل حساب بنكي (Register Bank) | ❌ لا | تعريف إداري في دليل الحسابات/البنوك |
| إيداع / سحب مباشر (Direct Deposit/Withdrawal) | ✅ نعم | حركة نقدية تؤثر على حساب البنك وحساب الإيراد/المصروف |
| تحويل بين حسابات بنكية (Bank Transfer) | ✅ نعم | حركة متوازنة بين حسابين بنكيين (أو عبر وسيط تحويل) |
| استيراد كشف الحساب البنكي (Import Statement) | ❌ لا | تغذية بيانات خارجية للتدقيق فقط |
| إجراء المطابقة البنكية (Reconciliation) | ❌ لا | مطابقة سجلات لا تولد قيداً بذاتها إلا إذا تم اعتماد قيد تسوية للفروقات |

- **نطاق المهمة:**
  - `pkg/api/v1/subledger/` — نماذج: `BankAccount`, `TreasuryTransaction`, `ReconciliationReport`
  - `pkg/spi/subledger/` — واجهات: `TreasuryStore`
  - parsers صيغ كشوف الحسابات (CAMT.053 / MT940) تبقى داخلية والمستهلك يتعامل مع بيانات مهيكلة
  - اختبارات المطابقة والتحويلات

- **خطوات التنفيذ:**
  1. صياغة الأنواع العامة لإدارة الحسابات البنكية والتحويلات.
  2. تصميم وتنفيذ أحداث التحويل بين البنوك لإنتاج قيود GL متوازنة عبر Application Layer.
  3. تنفيذ منطق المطابقة البنكية (Matching Engine) لمقارنة حركات البنك مع حركات الدفتر وتقديم تقرير الفروقات.
  4. التأكد الصارم من أن استيراد الكشوف ومطابقتها لا يولّد أي قيود تلقائية دون اعتماد صريح لقيد تسوية.

- **الاعتماديات:** `P8-01`، `P8-04`، و `P9-01`.

- **معايير القبول:**
  - [ ] الأنواع متاحة عبر Public API ومستقلة عن التفاصيل الداخلية.
  - [ ] التحويلات النقدية تُنتج قيوداً متوازنة وسليمة في GL.
  - [ ] استيراد كشوف الحسابات والمطابقة لا يولدان أي قيود محاسبية بصورة غير مقصودة.
  - [ ] إنتاج تقرير مطابقة بنكية يوضح المبالغ المعلقة في الدفاتر والمبالغ المعلقة لدى البنك.

### `P10-04` — محاسبة المعاملات بالعملات الأجنبية وإعادة قياس البنود النقدية (FX Transactions & Monetary Remeasurement)

- **المشكلة التي تحلها والتوضيح الدلالي:** تمت الإشارة سابقاً إلى هذا النطاق باسم "IAS 21"، وهو مسمى غير دقيق يوحي بامتثال كامل لمعيار أثر التغيرات في أسعار صرف العملات الأجنبية. المعيار الكامل يشمل موضوعات معقدة خارج نطاق المحرك الحالي مثل ترجمة القوائم المالية للعمليات الأجنبية (Translation of Foreign Operations) وتوحيد القوائم وتحديد العملة الوظيفية للمجموعات. النطاق الحقيقي للمحرك هو **محاسبة المعاملات الفردية بالعملات الأجنبية وإعادة قياس البنود النقدية في نهاية الفترات**.

- **الهدف الذي تحققه:** التحقق الوظيفي والرياضي الشامل من:
  1. إثبات المعاملات الأولية بالعملات الأجنبية بالسعر الفوري (Spot Rate).
  2. احتساب أرباح وخسائر الصرف المحققة (Realized FX Gains/Losses) عند تسوية المعاملات بسعر مختلف عن تاريخ الإثبات.
  3. احتساب أرباح وخسائر الصرف غير المحققة (Unrealized FX Gains/Losses) الناتجة عن إعادة قياس البنود النقدية (Monetary Items) في نهاية الفترات المالية بالسعر الختامي (Closing Rate).
  4. ترحيل الفروقات المحتسبة بدقة إلى حسابات الأرباح والخسائر المعتمدة.

- **نطاق المهمة:**
  - `internal/valuation/revaluation.go` — مراجعة وتدقيق محرك إعادة التقييم
  - `docs/compliance/ias21_scope_clarification.md` — توثيق رسمي للنطاق والاستثناءات
  - بناء وتوثيق Golden Scenarios للأرباح والخسائر المحققة وغير المحققة
  - **استثناء صريح ومؤكد:** لا يشمل ترجمة القوائم المالية لشركات تابعة أجنبية (Foreign Operation Translation) أو مجمع احتياطي ترجمة العملات الأجنبية (FCTR) في حقوق الملكية.

- **خطوات التنفيذ:**
  1. صياغة وثيقة توضيح النطاق: تسمية الوحدة بدقة "Foreign Currency Transaction Accounting & Monetary Item Remeasurement" وحصر الاستثناءات.
  2. تدقيق آلية تمييز البنود النقدية (Monetary Items: نقدية، بنوك، عملاء، موردين) عن البنود غير النقدية (Non-monetary Items: أصول ثابتة، مخزون) التي لا يُعاد قياسها بسعر الإقفال.
  3. سيناريو الأرباح/الخسائر المحققة: إثبات فاتورة بعملة أجنبية ⟵ سداد الفاتورة لاحقاً بسعر صرف مختلف ⟵ توليد قيد تسوية يحمل فرق الصرف المحقق في قائمة الدخل.
  4. سيناريو الأرباح/الخسائر غير المحققة: بقاء رصيد نقدي أو ذمة بعملة أجنبية في نهاية الفترة ⟵ إعادة التقييم بالسعر الختامي ⟵ توليد قيد تسوية دوري لفرق الصرف غير المحقق.
  5. التأكد من حفظ أسعار الصرف التاريخية المستخدمة ومراجعها لضمان قابلية المراجعة والتدقيق.

- **الاعتماديات:** `P8-01`، `P8-04`، و `P9-01`.

- **معايير القبول:**
  - [ ] توثيق مسمى النطاق بوضوح وحصر استثناءات معيار IAS 21 في وثيقة الامتثال.
  - [ ] التمييز الصارم بين البنود النقدية التي تُعاد تقييمها والبنود غير النقدية.
  - [ ] احتساب سليم للأرباح والخسائر المحققة عند التسوية وترحيلها لحسابات FX Gain/Loss.
  - [ ] احتساب سليم للأرباح والخسائر غير المحققة عند الإقفال وترحيلها كقيود تسوية.
  - [ ] اكتمال Golden Scenarios محاسبية مراجعة تثبت سلامة الحسابات والأرصدة.

## معايير اعتماد المرحلة `P10`

| المعيار | الدليل المطلوب |
| --------- | --------------- |
| الفصل التام بين العمليات الإدارية والأحداث المحاسبية | اختبارات تثبت عدم توليد قيود للعمليات الإدارية |
| AR/AP متاحة خارجياً وتتطابق مع GL | اختبار استهلاك خارجي + تطابق تفاصيل الذمم مع Control Account |
| Fixed Assets متاحة خارجياً | اختبار دورة حياة أصل كاملة مع قيود الإهلاك والاستبعاد |
| Treasury متاحة خارجياً مع مطابقة بنكية | اختبار تحويل بنكي سليم + تقرير مطابقة بنكية بدون قيود عشوائية |
| نطاق العملات الأجنبية محدد وموثق | وثيقة IAS 21 Scope Clarification + Golden Scenarios لـ FX |
| جميع الدفاتر الفرعية اختيارية | قدرة تشغيل المحرك بكفاءة دون تفعيل أي دفتر فرعي |
