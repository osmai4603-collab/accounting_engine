# المرحلة `P10` — رفع الدفاتر الفرعية إلى الواجهات العامة وإكمال IAS 21

- **الهدف:** جعل الدفاتر الفرعية الأساسية (ذمم مدينة/دائنة، أصول ثابتة، خزينة) متاحة للمستهلك الخارجي عبر public SPI، والتحقق من اكتمال امتثال IAS 21 لأرباح/خسائر الصرف
- **عدد المهام:** 4
- **الاعتماديات:** `P8-01`، `P9-01`
- **الحالة الحالية للميزات:**
  - جميع الدفاتر الفرعية: **مكتملة جزئياً** — كود موجود في `internal/subledgers/` لكن غير متاح خارجياً
  - IAS 21: **تحتاج تحقق فعلي** — `internal/valuation/revaluation.go` موجود

---

## تفاصيل المهام

### `P10-01` — رفع الذمم المدينة والدائنة (AR/AP) إلى Public SPI

- **المشكلة التي تحلها:** `internal/subledgers/receivable.go` و `internal/subledgers/payable.go` موجودان مع وظائف لإدارة الذمم، لكنهما داخل `internal/` — لا يستطيع مستهلك خارجي استخدامهما. هذا يعني أن المحرك لا يقدّم إدارة ذمم كميزة، رغم وجود التنفيذ.

- **الهدف الذي تحققه:** واجهات عامة في `pkg/spi/` أو `pkg/api/v1/` تكشف عمليات الذمم الأساسية: إنشاء ذمة، تسجيل دفعة/تحصيل، مطابقة مع GL، استعلام عن الأرصدة.

- **نطاق المهمة:**
  - `pkg/api/v1/subledger/` (جديد) — أنواع الذمم العامة
  - `pkg/spi/subledger/` (جديد) — واجهات التخزين والعمليات
  - `internal/subledgers/receivable.go`, `payable.go` — يبقى التنفيذ داخلياً
  - `pkg/sdk/builder.go` — تسجيل SubledgerService كـ Capability اختيارية
  - اختبارات الاستهلاك الخارجي
  - **لا تشمل:** نظام فوترة أو مبيعات أو مشتريات كاملة

- **خطوات التنفيذ:**
  1. حصر وتقييم الوظائف الموجودة في `receivable.go` و `payable.go` — تحديد ما هو مكتمل محاسبياً وما هو شكلي.
  2. تعريف أنواع عامة: `Receivable`, `Payable`, `Payment`, `ReceivableStatus`, `PayableStatus` في `pkg/api/v1/subledger/`.
  3. تعريف واجهات SPI: `ReceivableStore`, `PayableStore` مع عمليات CRUD والاستعلام.
  4. تعريف Application Commands: `CreateReceivableCommand`, `RecordPaymentCommand`, `WriteOffCommand`.
  5. ربط كل عملية subledger بأثر GL عبر Control Account — تعريف `ControlAccountMapping`.
  6. جعل Subledger Capability اختيارية في Builder: `WithSubledger(SubledgerService)`.
  7. التأكد من أن كل حركة فرعية تنتج قيد GL قابل للتتبع والمطابقة.
  8. اختبار من مستهلك خارجي: إنشاء ذمة، تسجيل دفعة، مطابقة مع GL.

- **الاعتماديات:** `P8-01`، `P9-01`.

- **معايير القبول:**
  - [ ] الأنواع العامة في `pkg/api/v1/subledger/` قابلة للاستيراد من مشروع خارجي
  - [ ] المستهلك لا يحتاج `internal/` لاستخدام الذمم
  - [ ] كل حركة ذمة تنتج قيد GL عبر Control Account
  - [ ] مطابقة Subledger مع GL: الرصيد التفصيلي يساوي رصيد حساب الرقابة
  - [ ] Subledger اختياري — المحرك يعمل بدونه
  - [ ] اختبار استهلاك خارجي ناجح
  - [ ] لا تسريب لـ `internal/` في الواجهات العامة

- **ملاحظة التوازي:** يمكن تنفيذها بالتوازي مع `P10-02` و`P10-03` و`P10-04`. كل subledger في ملفاته الخاصة. يتشاركون في `pkg/api/v1/subledger/` — يجب تنسيق إضافة الأنواع.

### `P10-02` — رفع الأصول الثابتة (Fixed Assets) إلى Public SPI

- **المشكلة التي تحلها:** `internal/subledgers/fixed_assets.go`, `asset_schedule.go`, `asset_revaluation.go` موجودة لكن في `internal/`. وظائف الإهلاك وجداول الأصول وإعادة التقييم غير متاحة للمستهلك الخارجي.

- **الهدف الذي تحققه:** واجهات عامة لإدارة الأصول: تسجيل أصل، حساب الإهلاك، إعادة التقييم، الاستبعاد — مع أثر GL تلقائي.

- **نطاق المهمة:**
  - `pkg/api/v1/subledger/` — أنواع الأصول العامة
  - `pkg/spi/subledger/` — واجهات التخزين
  - `internal/subledgers/fixed_assets.go`, `asset_schedule.go`, `asset_revaluation.go`
  - `pkg/sdk/builder.go` — تسجيل FixedAssetService
  - **لا تشمل:** إدارة مخزون أو أصول غير ملموسة

- **خطوات التنفيذ:**
  1. تقييم وظائف `fixed_assets.go` و `asset_schedule.go` و `asset_revaluation.go` — تحديد الاكتمال المحاسبي.
  2. تعريف أنواع: `FixedAsset`, `DepreciationSchedule`, `DepreciationMethod`, `AssetDisposal`, `AssetRevaluation`.
  3. تعريف واجهات: `FixedAssetStore`, `DepreciationStore`.
  4. تعريف Commands: `RegisterAssetCommand`, `CalculateDepreciationCommand`, `RevalueAssetCommand`, `DisposeAssetCommand`.
  5. ربط الإهلاك الدوري بإقفال الفترة (P9-01) كقيد تسوية.
  6. ربط Disposal بقيد GL يتضمن ربح/خسارة الاستبعاد.
  7. جعل الأصول Capability اختيارية.
  8. اختبار دورة حياة أصل: تسجيل → إهلاك لعدة فترات → إعادة تقييم → استبعاد.

- **الاعتماديات:** `P8-01`، `P9-01`.

- **معايير القبول:**
  - [ ] أنواع الأصول الثابتة قابلة للاستيراد خارجياً
  - [ ] جدول إهلاك يُنتج قيود GL بالمبالغ الصحيحة
  - [ ] إعادة التقييم تُنتج قيد GL مع فائض/عجز إعادة التقييم
  - [ ] الاستبعاد يُنتج قيد GL مع ربح/خسارة
  - [ ] مطابقة subledger الأصول مع GL (Control Account)
  - [ ] مراجعة محاسبية لطرق الإهلاك المدعومة
  - [ ] Capability اختيارية

### `P10-03` — رفع الخزينة (Treasury) إلى Public SPI

- **المشكلة التي تحلها:** `internal/subledgers/treasury.go` موجود مع إدارة الحسابات البنكية وعمليات الخزينة، لكنه داخلي.

- **الهدف الذي تحققه:** واجهات عامة لعمليات الخزينة الأساسية: تسجيل حساب بنكي، تسجيل إيداع/سحب، تحويل بين حسابات، مطابقة بنكية.

- **نطاق المهمة:**
  - `pkg/api/v1/subledger/` — أنواع الخزينة
  - `pkg/spi/subledger/` — واجهات
  - `internal/subledgers/treasury.go`
  - parsers CAMT.053 / MT940 (تبقى في `internal/` — المستهلك يرى النتيجة فقط)
  - **لا تشمل:** إدارة استثمارات أو أدوات مالية معقدة

- **خطوات التنفيذ:**
  1. تقييم وظائف `treasury.go` — تحديد الاكتمال.
  2. تعريف أنواع: `BankAccount`, `BankTransaction`, `BankReconciliation`, `TransferRequest`.
  3. تعريف واجهات: `TreasuryStore`, `BankReconciliationStore`.
  4. تعريف Commands: `RegisterBankAccountCommand`, `RecordBankTransactionCommand`, `ReconcileBankCommand`, `TransferFundsCommand`.
  5. ربط كل عملية بقيد GL.
  6. تقديم نتائج المطابقة البنكية (الكشف مقابل GL) كتقرير.
  7. إبقاء parsers (CAMT.053, MT940) داخلية — المستهلك يمرر بيانات مهيكلة.
  8. اختبار: تسجيل حساب بنكي، تسجيل عمليات، تحويل، مطابقة.

- **الاعتماديات:** `P8-01`، `P9-01`.

- **معايير القبول:**
  - [ ] أنواع الخزينة قابلة للاستيراد خارجياً
  - [ ] كل عملية خزينة تنتج قيد GL
  - [ ] التحويل بين حسابات ينتج قيداً متوازناً
  - [ ] المطابقة البنكية تكشف الفروقات بين الكشف والسجلات
  - [ ] Capability اختيارية
  - [ ] المستهلك لا يحتاج معرفة CAMT.053/MT940

### `P10-04` — التحقق من اكتمال IAS 21 وأرباح/خسائر الصرف

- **المشكلة التي تحلها:** تقرير التحليل يشير إلى أن أرباح/خسائر الصرف المحققة وغير المحققة **تحتاج تحقق فعلي**. يوجد `internal/valuation/revaluation.go` وIAS 21 Compliance Matrix، لكن يجب التأكد من أن:
  - أرباح/خسائر الصرف المحققة تُحسب عند التسوية (settlement)
  - أرباح/خسائر الصرف غير المحققة تُحسب عند إعادة التقييم الدوري (revaluation at period-end)
  - النتائج تُرحّل إلى حسابات صحيحة عبر Application Layer

- **الهدف الذي تحققه:** تحقق وظيفي يُثبت أن IAS 21 ضمن النطاق المعلن يعمل end-to-end مع Golden Scenarios.

- **نطاق المهمة:**
  - `internal/valuation/revaluation.go` — مراجعة وتكملة
  - `internal/valuation/` — منطق FX gains/losses
  - `pkg/api/v1/types/` — أنواع العملات إذا لزمت
  - Golden Scenarios
  - **لا تشمل:** Consolidation أو ترجمة عمليات أجنبية كاملة

- **خطوات التنفيذ:**
  1. مراجعة `revaluation.go` و Compliance Matrix الموجودة.
  2. بناء Golden Scenario لأرباح/خسائر محققة: شراء بعملة أجنبية → سداد بسعر صرف مختلف → حساب الربح/الخسارة.
  3. بناء Golden Scenario لأرباح/خسائر غير محققة: ذمة مفتوحة بعملة أجنبية → إعادة تقييم بسعر نهاية الفترة.
  4. التحقق من أن القيود المولّدة تُرحّل إلى حسابات الأرباح/الخسائر الصحيحة.
  5. التحقق من حفظ سعر الصرف التاريخي لإعادة إنتاج النتائج.
  6. تحديث Compliance Matrix بنتائج التحقق.
  7. مراجعة محاسبية مستقلة للسيناريوهات.

- **الاعتماديات:** `P8-01`، `P9-01`.

- **معايير القبول:**
  - [ ] أرباح/خسائر صرف محققة تُحسب صحيحاً عند التسوية
  - [ ] أرباح/خسائر صرف غير محققة تُحسب عند إعادة التقييم الدوري
  - [ ] القيود تُرحّل إلى حسابات FX Gain/Loss الصحيحة
  - [ ] سعر الصرف التاريخي محفوظ لإعادة الإنتاج
  - [ ] Golden Scenarios مراجعة محاسبياً
  - [ ] Compliance Matrix محدّثة بنتائج التحقق الفعلي
  - [ ] الحالات غير المدعومة موثقة صراحةً
