# حدود المنتج — Accounting Engine

- **النطاق:** واجهات المنتج العامة في المستودع الحالي؛ ليس بيان إصدار منشور
- **تاريخ التحديد:** 2026-11-13
- **الغرض:** تحديد ما يقدمه المحرك وما يبقى مسؤولية النظام المستهلك، لمنع تحول النواة إلى ERP قطاعي أو كشف تفاصيل التنفيذ.

## 1. تعريف المنتج

Accounting Engine هو محرك خدمات محاسبية قابل للدمج داخل أنظمة أعمال مختلفة. يستقبل أوامر محاسبية موحدة أو أحداثًا محولة بواسطة Industry Adapter، ويطبق قواعد المحاسبة الأساسية وسياسات الترحيل، ويحفظ القيود وآثارها من خلال Persistence Ports.

المحرك ليس نظام ERP كاملًا، ولا يملك دورة التشغيل التجارية أو الزراعية أو الصناعية التي أنتجت الحدث الاقتصادي.

## 2. تصنيف القدرات

| القدرة | التصنيف المستهدف | ما يقدمه المحرك | ما لا يفترض أن يملكه |
| --- | --- | --- | --- |
| Journal Entry / Double Entry Validation | `core-required` | نماذج القيود والتحقق من التوازن والعملة الوظيفية وصحة السطور | مستند البيع أو الإنتاج الأصلي |
| Posting / Reversal | `core-required` | تطبيق دورة الترحيل والعكس والقيود المحاسبية والتدقيق | واجهة المستخدم أو موافقات الموارد البشرية |
| Chart of Accounts / Journals / Fiscal Periods | `core-required` | الحد الأدنى من البيانات المحاسبية الرئيسية اللازمة للترحيل | إدارة المؤسسة التشغيلية الكاملة |
| Persistence Ports / Unit of Work | `core-required` | عقود محايدة للتخزين وحدود المعاملة | معرفة SQL أو مخطط PostgreSQL لدى المستهلك |
| Audit Evidence | `core-required` للعمليات المالية | حفظ أثر من نفذ العملية وسببها ووقتها ومرجعها | مزود هوية المستخدم النهائي بالضرورة |
| Event Integration | `optional` | استقبال حدث محاسبي معياري بعد تحويله إلى عقد المحرك | فهم مخطط ERP الخاص بكل قطاع |
| Reporting | `optional` | تقارير مالية عندما تتوفر مصادر البيانات والعقود اللازمة | تقارير تشغيلية للمخزون أو الإنتاج |
| Governance / Approval | `optional` | بوابات موافقات وفصل واجبات عند تفعيلها | إدارة المستخدمين والمصادقة الشاملة للنظام المضيف |
| Reconciliation | `optional` | قدرات مطابقة عند توافر بيانات الطرف المقابل والمصادر اللازمة | الاتصال البنكي أو إدارة كشوف البنك ما لم يوفّر Adapter ذلك |
| Consolidation | `optional` | توحيد مالي عند توفير هيكل الكيانات والملكية والعملات والسياسات | إدارة الشركات القانونية والتشغيلية للنظام المضيف |
| IFRS / IAS Modules | `optional` | معالجة محددة النطاق لكل معيار وإصدار وتاريخ سريان | ادعاء امتثال شامل دون تحليل معيار ومتطلبات ونطاق |
| Industry Adapters | `host-owned` أو حزم تكامل منفصلة | عقود وأمثلة مرجعية لتحويل أحداث القطاع إلى أوامر محاسبية | منطق التشغيل الخاص بالتجارة والزراعة والصناعة والخدمات داخل Core |
| Authentication / Identity Provider | `host-owned` مع تكامل آمن | استلام Actor/Principal موثوق وسياق تفويض موثق | تخزين كلمات المرور أو افتراض هوية من حقول الطلب |
| HTTP / gRPC Transport | `optional` | واجهات نقل عند اختيار نشر المحرك كخدمة | فرض استخدام النقل على مستهلك المكتبة |
| Database Schema / PostgreSQL SQL | `host-hidden` | Adapter PostgreSQL داخلي أو قابل للاختيار | إجبار النظام الخارجي على كتابة SQL المحرك أو معرفة جداولها |
| Inventory / Sales / Payroll / Production | `host-owned` | استقبال أثرها المحاسبي عبر Adapter | امتلاك دورة حياة المستندات التشغيلية |

## 3. الحد الأدنى للإصدار المنتج الأول

1. Public SDK واحد ومستقر، لا يعتمد على أنواع `internal`.
2. Public SPI كافٍ لتوصيل Persistence Adapter خارجي.
3. Application Layer واحدة لكل عمليات إنشاء القيود والتحقق والترحيل والعكس والأحداث.
4. Master Data محاسبية كافية ومحددة بعقود عامة.
5. Posting وReversal وAudit وIdempotency بحدود ذرية موثقة.
6. موائم PostgreSQL وموائم Memory للاختبار، مع عدم اختيار Memory تلقائيًا في الإنتاج.
7. مثال مستهلك خارجي مستقل وAdapter خارجي يثبتان عدم تسرب تفاصيل التخزين.
8. تقارير أساسية لا تُفعّل إلا عند توافر Reporting Capability ومصادرها.
9. أمن الخدمة: إما مصادقة/تفويض صريحان داخل transport أو عقد موثق ومثبت لطبقة مضيفة موثوقة، مع عدم الثقة في `company_id` المرسل وحده.
10. توثيق دقيق لنطاق أي وحدة معيارية، دون ادعاء الامتثال الكامل لمعيار لم يكتمل.

## 4. ميزات مجمدة حتى إغلاق بوابات المنتج الأساسية

- إضافة Industry Adapters جديدة أو توسيع قوالب القطاعات.
- إضافة وحدات IFRS/IAS جديدة أو توسيع نطاق ادعاء الامتثال.
- إضافة تقارير مالية متقدمة جديدة.
- إضافة transports أو بروتوكولات جديدة.
- توسيع Consolidation أو Subledgers قبل إثبات العقود والتكافؤ.

يسمح فقط بإصلاح عيب يمنع مهمة معتمدة أو يهدد سلامة البيانات، مع توثيق أثره.

## 5. معايير الاستقلال

### Industry Independence

يحوّل كل نظام قطاعي بياناته إلى Canonical Accounting Command من خلال Adapter منفصل؛ ولا يتطلب تعديل Core عند إضافة قطاع جديد ما دامت الدلالة المحاسبية ضمن العقود القائمة.

### Infrastructure Independence

تستخدم Application Layer Ports عامة؛ ولا يستورد المستهلك `pgx` ولا يعرف SQL أو جداول المحرك. ويثبت ذلك Adapter خارجي مستقل واختبارات تكافؤ دلالي.

### External Consumption

يستطيع مشروع Go مستقل استيراد SDK وSPI من مسار Module منشور، وبناء Adapter وتشغيل دورة محاسبية فعلية دون `internal` imports أو استدعاءات SQL خاصة بالمحرك.

## 6. مراجعة النطاق مقابل القطاعات

المراجعة تثبت أن Core لا يحتوي مفهومًا قطاعيًا، وأن كل قطاع يصل إلى المحرك عبر Canonical Accounting Command فقط.

| القطاع | ما يملكه النظام المضيف | ما يستقبله المحرك | دليل على عدم تسرب القطاع إلى Core |
| --- | --- | --- | --- |
| التجارة | أمر البيع، الفاتورة، المخزون، المرتجعات، تسوية الموردين | قيد مزدوج بحسابات الذمم/الإيراد/المخزون/تكلفة المبيعات ومرجع المستند ومفتاح التكرار | Core لا يعرف `SalesOrder` أو `Invoice`; التحويل يتم في Adapter/Host |
| الزراعة | دورة المحصول، الحصاد، المخزون الزراعي، الإعانات | قيد بحسابات الأصول البيولوجية/المخزون/الإيراد حسب السياسة المحاسبية التي يحددها المضيف | لا يوجد نوع محصول أو موسم داخل العقود العامة |
| الصناعة | أمر الإنتاج، المواد، العمالة، الإنتاج التام، الانحرافات | قيد تحويل تكلفة/مخزون/انحرافات عبر أوامر محاسبية | لا يوجد `WorkOrder` أو `BOM` في Core |
| الخدمات | عقد الخدمة، ساعات العمل، الفوترة، الاعتراف بالإيراد | قيد إيراد/ذمم/مقدم/تكلفة خدمة عبر أمر أو حدث محاسبي | لا يوجد مفهوم مشروع/خدمة إلزامي في Core |

النتيجة: إضافة قطاع جديد لا تتطلب تعديل `internal/posting` أو `pkg/spi/storage`؛ تتطلب فقط Adapter يحول وقائع القطاع إلى `CreateDraftCommand`/`PostEntryCommand` (P2) مع Master Data محاسبية حقيقية.

## 7. قرارات لم تُحسم بعد

هذه الوثيقة تحدد الحدود المستهدفة، لكنها لا تحسم بديلًا تقنيًا نهائيًا في القرارات التي تتطلب baseline وADRs:

- اسم ومسار Go Module النهائي وقرار النشر العام.
- شكل Transaction Runner / Unit of Work وضماناته لكل Adapter.
- حدود المصادقة والتفويض بين المحرك والنظام المضيف.
- قائمة الإصدارات والنطاق التفصيلي لكل معيار محاسبي.
- استراتيجية توافق Root API الحالي مع SDK الجديد.
