# ADR-0006 — Module Boundaries for ERP Expansion

- **الحالة:** معتمد
- **التاريخ:** 2026-11-12
- **المراجعة:** 2026-11-12
- **المالك:** `ARCH` + `LEDGER` + `SME`
- **الفجوات المرتبطة:** `GAP-ERP-01` … `GAP-ERP-10`
- **المهام المرتبطة:** `P5-T1` … `P5-T12`

## السياق

المرحلة 5 تضيف وحدات ERP (مخزون، مشتريات، مبيعات، رواتب، ضرائب، موازنات، مشاريع، تكاليف). الخطر أن تُبنى هذه الوحدات داخل `internal/posting` أو `engine.go` مباشرةً، فتصبح النواة المحاسبية معتمدة على تفاصيل تجارية وتفقد قابليتها للاختبار والتطور. كما أن كل وحدة تحتاج كيانات وترحيلات وقيوداً خاصة، لكن يجب ألا تكسر ضمانات القيد المزدوج والذرّية.

## القرار

1. **كل وحدة ERP حزمة مستقلة** تحت `internal/<module>` (مثل `internal/inventory`, `internal/payroll`)، ولها:
   - أنواع مجال (Domain types) لا تعتمد على `posting` في تعريفها الأساسي،
   - منافذ (`<Module>Repository`, `<Module>Service`) معرفة داخل الوحدة،
   - محول تخزين مستقل (`storage/postgres/<module>.go`) وهجرات خاصة،
   - اختبارات وحدة + عقد تخزين + تكامل.
2. **التكامل مع النواة عبر منفذ واحد:** الوحدة تُنشئ `posting.JournalEntry` عبر دالة بناء صريحة، وتمرره إلى `PostingStoragePort` أو `Engine` القائم. لا تكتب الوحدة في `account_moves` مباشرةً.
3. **المرفقات (Attachments):** أي أثر جانبي (تحديث مخزون، استحقاق راتب) يُنفَّذ عبر `posting.LedgerAttachment` ضمن نفس معاملة الترحيل. لا يوجد «ترحيل ثم تحديث» منفصل.
4. **حدود الاستيراد:**
   - لا تستورد وحدة ERP داخل `internal/posting` أو `engine.go`.
   - لا تستورد وحدتان ERP إحداهما الأخرى مباشرةً؛ التنسيق عبر `internal/contracts` أو أحداث صريحة.
   - `engine.go` يعرف الوحدات فقط عبر واجهات تهيئة اختيارية.
5. **الحسابات الضابطة:** لكل وحدة حساب ضابط (Control Account) مستقل، ولا تتشارك الوحدات حساباً ضابطاً دون توثيق في مخطط الحسابات.
6. **الترحيلات:** لكل وحدة هجراتها الخاصة بنفس سياسة ADR-0005، مع مفاتيح أجنبية مركبة `(company_id, ...)`.
7. **الأعلام (Feature flags):** كل وحدة تُفعَّل بعلم مستقل، وتعطيلها لا يفسد البيانات المرحّلة.
8. **الإفصاح:** كل وحدة توفر واجهة قراءة للإفصاحات الخاصة بها؛ لا تُحقن منطق الإفصاح داخل `internal/reporting` مباشرةً.

## البدائل المرفوضة

| البديل | سبب الرفض |
| --- | --- |
| إضافة أنواع ERP إلى `internal/posting` | توسّع النواة وتزيد اقترانها بالمجال التجاري |
| كتابة قيود ERP مباشرة في الجداول | تتجاوز البصمة والاعتماد والذرّية والتدقيق |
| حزمة ERP واحدة ضخمة | تمنع التطور المستقل والاختبار المعزول |
| مشاركة الحسابات الضابطة بين الوحدات | تخلط الأرصدة وتصعّب التسوية |
| هجرات مركزية لكل الوحدات | تبطئ النشر وتخلق تعارضات ترحيل |

## النتائج

- المرحلة 5 تصبح إضافات معزولة قابلة للاختبار، لا تعديلاً في نواة الترحيل.
- تحتاج كل وحدة إلى عقد تخزين واختبارات مرفقات.
- تزداد الحاجة إلى مراجعة معمارية لكل وحدة قبل التنفيذ.

## المخاطر

| المخاطرة | التخفيف |
| --- | --- |
| تكرار منطق الترحيل في كل وحدة | مكتبة بناء قيود مشتركة + مراجعة `ARCH` |
| تعارض أسماء جداول/هجرات | بادئة وحدة + أرقام إصدار موحدة |
| إفصاحات غير متسقة | عقد إفصاح موحد في `internal/reporting/taxonomy` |
| تعطيل وحدة يترك بيانات يتيمة | علم تشغيل + قراءة فقط عند التعطيل + خطة أرشفة |
