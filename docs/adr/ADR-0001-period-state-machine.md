# ADR-0001 — Period State Machine

- **الحالة:** معتمد
- **التاريخ:** 2026-11-12
- **المراجعة:** 2026-11-12
- **المالك:** `ARCH` + `LEDGER` + `DBA`
- **الفجوات المرتبطة:** `GAP-GOV-01`, `GAP-GOV-02`, `GAP-CLS-02`, `GAP-CLS-04`
- **المهام المرتبطة:** `P1-T1`, `P2-T3`, `P2-T4`

## السياق

حالة الفترة المالية تُقرأ وتُكتب حالياً في أكثر من طبقة. يتحقق `internal/masterdata` من الانتقالات في بعض المسارات، بينما ينفّذ `storage/postgres/masterdata.go::UpdatePeriodState` تحديثاً مباشراً لا يمر عبر `ValidatePeriodTransition`. لذلك يمكن لفترة `hard_closed` أن تعود `open` دون صلاحية أو سبب أو أثر تدقيقي. كما أن الاختيار بين الفترتين 13 و14 يعتمد على التاريخ، وتاريخهما متطابق.

## القرار

1. الحالات المسموحة هي فقط:
   - `open → soft_closed`
   - `soft_closed → hard_closed`
2. لا يُسمح بأي انتقال مباشر من `hard_closed` إلى `open` أو `soft_closed` عبر أي API أو استعلام عادي. **`hard_closed` نهائية.**
3. إعادة فتح سنة مقفلة نهائياً ليست انتقال حالة؛ تتطلب إجراءً استثنائياً موثقاً:
   - قرار مزدوج (`LEDGER` + `SME`/المدير المالي)،
   - سبب مكتوب ومرجع مستند،
   - سجل تدقيق غير قابل للتعديل،
   - وأداة إدارية منفصلة تُنشئ فترة/سنة تصحيحية بدلاً من كسر القفل.
4. التحقق من الانتقال والكتابة يحدثان داخل معاملة واحدة مع `SELECT ... FOR UPDATE` على صف الفترة. لا يُقبل «قراءة ثم كتابة» خارج القفل.
5. اختيار الفترتين 13 و14 يكون **بالرقم** (`period_number`)، لا بالتاريخ. أي واجهة تعتمد على التاريخ يجب أن تستبعد الفترتين 13 و14 صراحةً أو تطلب الرقم.
6. كل محاولة انتقال مرفوضة تُسجَّل بـ`company_id`, `period_id`, `from`, `to`, `actor`, `reason`, `trace_id`.

## البدائل المرفوضة

| البديل | سبب الرفض |
| --- | --- |
| السماح بـ`hard_closed → open` للمدير المالي | يهدم ضمان عدم تعديل قيود سنة مقفلة، ويجعل الأدلة المالية قابلة للتغيير بعد النشر |
| `hard_closed → soft_closed` ثم تعديل | نفس المشكلة مع خطوة إضافية |
| التحقق في طبقة الخدمة فقط | يمكن تجاوزه باستدعاء التخزين المباشر، وهو ما حدث فعلاً |
| إعادة الفتح عبر Cron/مهمة مجدولة | تفقد الفاعل والسبب وتخلط بين التشغيل والقرار المحاسبي |
| اختيار الفترة 13/14 بالتاريخ | تاريخهما متطابق، فالاختيار غير حتمي |

## النتائج

- كل كتابة لحالة الفترة تمر عبر مسار واحد قابل للاختبار.
- تصبح محاولة إعادة الفتح فشلاً صريحاً (`PERIOD_TRANSITION_INVALID`) لا سلوكاً صامتاً.
- تحتاج الأدوات الإدارية إلى مسار تصحيحي منفصل ومصرح.
- تحتاج اختبارات PostgreSQL إلى تغطية `FOR UPDATE` وانتقالات الفترتين 13/14.

## المخاطر

| المخاطرة | التخفيف |
| --- | --- |
| كسر سيناريو إقفال قائم يعتمد على إعادة الفتح | توفير إجراء تصحيحي موثق قبل النشر، واختبار ترحيل للبيانات القائمة |
| أقفال أطول على صف الفترة | قصر المعاملة، فهارس مناسبة، وقياس زمن الإقفال |
| اعتماد واجهات قديمة على التاريخ | تدقيق نقاط الاستدعاء وإضافة اختبارات للفترتين 13/14 |
