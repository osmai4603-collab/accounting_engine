# ADR-0005 — Storage Parity & Migrations

- **الحالة:** معتمد
- **التاريخ:** 2026-11-12
- **المراجعة:** 2026-11-12
- **المالك:** `ARCH` + `DBA` + `QA`
- **الفجوات المرتبطة:** `GAP-PST-06`, `GAP-AST-02`, `GAP-OPS-07`
- **المهام المرتبطة:** `P0-T8`, `P1-T6`, `P1-T9`, `P4-T6`

## السياق

المحرك يدعم ثلاثة تنفيذات للتخزين: `storage/memory`، `storage/postgres`، وmocks في الاختبارات. بعض الضمانات (الذرّية، الأقفال، منع التكرار المتزامن) موجودة في PostgreSQL فقط، بينما Memory يقدم ضمانات أضعف. هذا يسمح لاختبارات خضراء على Memory بفجوة حقيقية في الإنتاج. كذلك لا توجد سياسة مكتوبة للهجرات الخطرة، وبعض الهجرات تحتوي تغييرات نوع غير متوافقة.

## القرار

### تكافؤ التخزين

1. **العقد هو السلوك، لا الواجهة.** كل عملية لها عقد موثق (ذرّية، أخطاء متوقعة، ترتيب أقفال، آثار جانبية) في `storage` contract tests.
2. كل تنفيذ (`memory`, `mock`, `postgres`) يجب أن يجتاز نفس `storage contract tests`.
3. إذا لم يستطع تنفيذ ما تقديم ضمان (مثل أقفال الصفوف)، يجب أن **يرفض العملية صراحةً** بدلاً من محاكاة نجاح مضلل.
4. اختبارات التزامن (`-race`, goroutines) تُشغَّل على Memory وPostgreSQL معاً.
5. أي اختلاف سلوكي مكتشف يُسجَّل كفجوة `GAP-*` ولا يُترك كـ«فرق تنفيذ مقبول».

### الهجرات

1. **Expand/Contract إلزامي:**
   - Expand: إضافة عمود/جدول/فهرس متوافق مع الإصدار القديم.
   - Backfill: تعبئة بيانات في خطوة منفصلة قابلة للاستئناف.
   - Switch: تبديل القراءة/الكتابة إلى الشكل الجديد.
   - Contract: إزالة الشكل القديم في إصدار لاحق فقط.
2. لا يُسمح في نفس الإصدار بـ:
   - `DROP COLUMN` أو `DROP TABLE` قبل Contract،
   - `ALTER COLUMN ... TYPE` غير المتوافق،
   - `NOT NULL` جديد على بيانات قائمة دون default/backfill،
   - `DELETE FROM` أو `TRUNCATE` على بيانات مالية.
3. كل هجرة أمامية يجب أن يكون لها `.down.sql` غير فارغ، واختبار ترقية من الإصدار السابق.
4. `storage/postgres/migrations_guard_test.go` يرفض الأنماط الخطرة تلقائياً. الاستثناءات القديمة مسجلة بأسبابها في `docs/migration_policy.md`.
5. فحص checksum يمنع تعديل هجرة مطبقة. أي تصحيح يتم بهجرة جديدة.
6. النسخ الاحتياطي قبل الهجرة والتراجع موثقان في `docs/migration_policy.md`.

## البدائل المرفوضة

| البديل | سبب الرفض |
| --- | --- |
| اعتبار Memory «تقريباً» مثل PostgreSQL | يخفي سباقات التزامن ويجعل الاختبار الأخضر غير ممثل للإنتاج |
| Squash الهجرات لتسريع النشر | يفقد تاريخ الترقية ويجعل rollback مستحيلاً |
| حذف الأعمدة مباشرة مع النشر | يكسر الإصدار السابق أثناء rollout |
| الاعتماد على مراجعة بشرية فقط للهجرات | لا تمنع خطأً متكرراً؛ الفحص الآلي إلزامي |
| Down migration اختياري | يمنع التراجع عند فشل الإنتاج |

## النتائج

- تكلفة إضافية في كل تغيير تخزين، لكن سلوك الإنتاج يصبح قابلاً للإثبات.
- CI يشغّل حارس الهجرات واختبار الترقية، ويمنع الدمج عند الفشل.
- تحتاج الفرق إلى كتابة Backfill قابل للاستئناف في المهام الكبيرة.

## المخاطر

| المخاطرة | التخفيف |
| --- | --- |
| تباطؤ التطوير بسبب Expand/Contract | قوالب جاهزة وأمثلة في `docs/migration_policy.md` |
| نسيان down migration | فحص آلي في `go test` |
| فشل backfill الجزئي | معالجة idempotent + checkpoint + مراقبة |
| اختلاف Memory رغم العقد | contract tests مشتركة في CI |
