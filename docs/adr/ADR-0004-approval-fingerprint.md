# ADR-0004 — Approval Fingerprint

- **الحالة:** معتمد
- **التاريخ:** 2026-11-12
- **المراجعة:** 2026-11-12
- **المالك:** `ARCH` + `LEDGER` + `SME`
- **الفجوات المرتبطة:** `GAP-PST-02`, `GAP-PST-03`
- **المهام المرتبطة:** `P1-T3`, `P1-T4`

## السياق

بصمة الاعتماد هي الفاصل بين «ما وافق عليه المعتمِد» و«ما يُرحَّل فعلاً». حالياً:

- `DraftContentMatches` لا يقارن `PeriodID`, `TargetPeriodNumber`, `AdjustmentAuthorized`, `OriginalEntryID`.
- `EntryContentHash` لا يغطي `SourceEventID`.

لذلك يمكن تغيير الفترة أو ربط القيد بحدث اقتصادي آخر بعد الاعتماد دون إبطال البصمة.

## القرار

1. تُحسب البصمة على تمثيل قانوني (canonical) ثابت الترتيب، وتشمل **كل حقل مؤثر محاسبياً**:
   - هوية الشركة والدفتر (`CompanyID`, `JournalID`).
   - التاريخ الفعلي (`EntryDate`/`Date`) والفترة (`PeriodID`, `TargetPeriodNumber`).
   - التصنيف (`Classification`) والمرجع (`Reference`, `DocumentReference`).
   - الارتباط الاقتصادي (`SourceEventID`, `OriginalEntryID`).
   - تفويض التعديل (`AdjustmentAuthorized`).
   - العملة، نوع سعر الصرف، وأي مبلغ وظيفي/معاملاتي.
   - كل سطر: `ID`, `AccountID`, `Debit`, `Credit`, `AmountCurrency`, `FunctionalDebit`, `FunctionalCredit`, `ExchangeRate`, `CostCenterID`, الأبعاد المالية، وبيانات الطرف/المستند المؤثرة.
   - هوية المرفقات وربطها بالقيد عند وجودها.
2. **لا تدخل** في البصمة الحقول التشغيلية: `Status`, `SequenceNumber`, `CreatedAt`, `UpdatedAt`, `ReversedEntryID`؛ فهي تتحرك ضمن انتقالات يتحكم بها المحرك، لا ضمن محتوى الاعتماد.
3. `DraftContentMatches` و`EntryContentHash` يستخدمان نفس دالة التمثيل القانوني ونفس قائمة الحقول. أي اختلاف بينهما يعتبر عيباً.
4. عند تغيّر أي حقل مؤثر بعد الاعتماد:
   - تُبطل البصمة،
   - يُرفض الترحيل بـ`APPROVAL_REQUIRED` أو `ENTRY_IMMUTABLE`،
   - ويُطلب اعتماد جديد.
5. تُحفظ نسخة البصمة المعتمدة ونسخة البصمة الحالية عند الرفض للتدقيق.

## البدائل المرفوضة

| البديل | سبب الرفض |
| --- | --- |
| الاعتماد على مقارنة JSON كاملة | حساسة لترتيب الحقول/الفروق الشكلية وتشمل حقولاً تشغيلية |
| إدخال `Status` و`UpdatedAt` في البصمة | كل تحديث تشغيلي يبطل اعتماداً سليماً |
| إبقاء `SourceEventID` خارج البصمة | يسمح بإعادة ربط القيد بحدث اقتصادي مختلف بعد الاعتماد |
| مقارنة الحقول في طبقة الخدمة فقط | يمكن تجاوزها من مسار التخزين المباشر |
| تجزئة كل الحقول بلا توثيق | لا يمكن مراجعة التغطية أو اكتشاف حقل جديد منسي |

## النتائج

- كل حقل جديد في `JournalEntry` أو `JournalEntryLine` يتطلب تحديث قائمة الحقول واختبار بصمة.
- تزداد صعوبة إعادة استخدام مسودة معتمدة لغرض آخر، وهذا مقصود.
- تحتاج اختبارات توافق بين Memory وPostgreSQL على نفس البصمة.

## المخاطر

| المخاطرة | التخفيف |
| --- | --- |
| نسيان حقل جديد | قائمة حقول مركزية + اختبار انعكاسي (reflection) يراجع الحقول |
| إبطال اعتمادات مشروعة بعد ترقية | إصدار بصمة `version` وترحيل تدريجي |
| بطء الحساب | تمثيل قانوني خفيف وتخزين البصمة لا إعادة حسابها في كل قراءة |
