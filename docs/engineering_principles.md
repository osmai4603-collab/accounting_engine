# 🧱 المبادئ الهندسية لبناء المحركات البرمجية

تكمل هذه الوثيقة [الدليل الهندسي لبناء المحركات البرمجية](./software_engines.md)، وتعرض مبادئ التصميم التي تساعد على بناء الهيكل الداخلي للمحرك.

المعايير الرسمية تحدد أطر الجودة ودورة الحياة والقياس، أما المبادئ التالية فليست كلها معايير إلزامية؛ إنها ممارسات هندسية ينبغي تطبيقها بما يتناسب مع طبيعة المحرك ومخاطره.

## 1. Separation of Concerns

فصل المسؤوليات.

يجب ألا يتحول المحرك إلى مكوّن يعرف كل شيء عن النظام.

مثلاً، في محرك محاسبي:

| المسؤولية             | مكانها المقترح            |
| --------------------- | ------------------------- |
| القواعد المحاسبية     | Accounting Core           |
| استقبال HTTP          | HTTP Adapter              |
| تخزين البيانات        | Persistence Adapter       |
| إرسال الإشعارات       | Notification Adapter      |
| إدارة إعدادات التطبيق | Application Configuration |

الهدف هو ألا تعتمد القواعد المحاسبية مباشرة على تفاصيل HTTP أو PostgreSQL.

## 2. Single Responsibility Principle (SRP)

كل مكوّن يجب أن تكون له مسؤولية واضحة وسبب محدد للتغيير.

مثلاً:

- Journal Validator يتحقق من صحة القيد.
- Posting Engine ينفذ عملية الترحيل.
- Balance Calculator يحسب الأرصدة.

لا تجمع جميع هذه المسؤوليات في كلاس أو Struct واحد ضخم.

## 3. Dependency Inversion Principle (DIP)

يجب أن تعتمد القواعد الأساسية على تجريدات مناسبة، وليس على تفاصيل التنفيذ.

مثلاً:

```text
type JournalRepository interface {
    Save(ctx context.Context, journal Journal) error
    FindByID(ctx context.Context, id string) (Journal, error)
}
```

المحرك يتعامل مع الواجهة، ولا يحتاج إلى معرفة هل التخزين PostgreSQL أو غيره.

## 4. Encapsulation

إخفاء التفاصيل الداخلية.

يجب ألا تسمح للمكونات الخارجية بتغيير حالة المحرك بطريقة تتجاوز قواعده.

مثلاً، لا تسمح للتطبيق بتغيير حالة قيد محاسبي مباشرة إلى Posted دون المرور بعملية التحقق والترحيل المعتمدة.

## 5. High Cohesion / Low Coupling

- High Cohesion: المكونات التي تعمل معاً يجب أن تكون مسؤولة عن مجال مترابط.
- Low Coupling: تقليل الاعتماد المتبادل بين المكونات.

هذا مهم جداً عند تقسيم المحرك إلى Features أو Subsystems.

## 6. Determinism

قابلية التنبؤ بالنتائج.

إذا كانت العملية لا تعتمد على الوقت أو الحالة الخارجية، فيجب أن تعطي المدخلات نفسها النتائج نفسها.

وهذا مهم خصوصاً في:

- المحركات المحاسبية.
- محركات الضرائب.
- محركات الحسابات المالية.
- محركات القواعد.

## 7. Explicit State Management

إدارة الحالات بشكل صريح.

مثلاً، لا تجعل عملية الترحيل مجرد تغيير عشوائي لحقل `status`.

بل عرّف حالات مسموحة وانتقالات بينها:

Journal Lifecycle

Draft

Validated

Posted

كل انتقال يجب أن يخضع لقواعد محددة، وليس لتغيير مباشر للحالة.

## 8. Fail Fast and Explicit Error Handling

اكتشف الأخطاء مبكراً، وأعد أخطاء واضحة يمكن للمكونات المستهلكة التعامل معها.

لا تخفِ الأخطاء ولا تستخدم قيماً افتراضية غير صحيحة لتجاوزها.

## 9. Idempotency

قابلية إعادة تنفيذ الطلب دون تكرار الأثر.

هذه الخاصية مهمة عندما يعيد العميل إرسال الطلب بسبب انقطاع الاتصال.

مثلاً، إعادة إرسال طلب ترحيل عملية محاسبية لا ينبغي أن تنتج قيداً مرحلاً إضافياً.

## 10. Observability

يجب أن يكون المحرك قابلاً للمراقبة والتحليل.

يشمل ذلك:

- Structured Logging.
- Metrics.
- Distributed Tracing عند الحاجة.
- Error Tracking.
- Audit Trails عندما يتطلب المجال ذلك.

هذه المبادئ مجتمعة تعطيك أساساً هندسياً قوياً، لكن تطبيق كل مبدأ يجب أن يتناسب مع طبيعة المحرك ومخاطره.
