# المرحلة الرابعة: وحدات الدفاتر المساعدة ودورة الأحداث الاقتصادية

## Phase 4: Subledgers & Economic Events Lifecycle Units

**الهدف العام للمرحلة:** بناء بنية معيارية متكاملة للتعامل مع الأحداث الاقتصادية الخارجية بضمانات عدم التكرار (Idempotency)، وتطوير الدفاتر المساعدة للذمم، والأصول الثابتة، والخزينة، لتشكل جسراً آمناً بين أنظمة التشغيل (ERP, CRM, Billing) ودفتر الأستاذ العام.

---

### المهمة 4.1: وحدة إدارة دورة حياة الأحداث الاقتصادية (Economic Event Lifecycle Unit)

* **المشكلة الحالية:**
  المشروع يحتوي على نواة جيدة لجسر الأحداث (`internal/subledgers/event_bridge.go`)، لكنها تفتقر إلى إدارة دورة حياة الحدث الاقتصادية الكاملة؛ حيث لا توجد آلية متكاملة لضمان عدم تكرار المعالجة (Idempotency Key Enforcement)، أو إعادة تشغيل الأحداث الفاشلة (Event Replay)، أو التعامل مع الأحداث المعطوبة (Dead Letter Queue)، أو توثيق وتتبع الحدث بمستند المصدر الأصلي.
* **الهدف:**
  تطوير `EconomicEventLifecycleUnit` لتحويل الأحداث الاقتصادية الخام إلى قيود محاسبية مسودة أو مرحلة بضمان المعالجة الدقيقة لمرة واحدة فقط (**Exactly-Once Processing Guarantee**).
* **السياق الفني والمحاسبي المطلوب:**
  * **المعيار الهندسي:** معمارية النظم المالية الموزعة المعتمدة على الأحداث (Event-Driven Architecture)، وقواعد الـ Idempotency في أنظمة المدفوعات والفوترة العالمية (مثل أنظمة SWIFT و Stripe).
  * **المعيار الرقابي:** مبدأ التتبع الكامل من القيد المحاسبي إلى الحدث الاقتصادي والمستند التجاري المعزز له.
* **خطوات التنفيذ المحددة:**
  1. تعريف نموذج متكامل للحدث الاقتصادي:

     ```go
     type EconomicEvent struct {
         EventID         uuid.UUID
         CompanyID       uuid.UUID
         SourceSystem    string
         ExternalID      string
         IdempotencyKey  string
         EventType       string
         EventVersion    int
         PayloadJSON     []byte
         Status          EventStatus // Received, Processed, Rejected, DeadLetter
         GeneratedEntryID *uuid.UUID
         ErrorMessage    string
         CreatedAt       time.Time
         ProcessedAt     *time.Time
     }
     ```

  2. فرض قيد فريد في قاعدة البيانات على `(company_id, source_system, idempotency_key)` لمنع تكرار استقبال أو معالجة نفس المعاملة مرتين.
  3. ربط القيد المحاسبي المولد بمعرف الحدث في جدول `account_moves` عبر حقل `source_event_id`.
  4. توفير واجهة لإعادة معالجة الأحداث الفاشلة بعد تصحيح شجرة الحسابات أو قواعد الترجمة.
* **معايير قبول نفاذ المهمة (Acceptance Criteria):**
  * [ ] اختبار إرسال نفس الحدث الاقتصادي 5 مرات بالتوازي، والتأكد من توليد قيد محاسبي واحد فقط ونجاح بقية الاستدعاءات بإرجاع القيد ذاته بدون تكرار.
  * [ ] تتبع القيد المحاسبي والرجوع بنجاح إلى الحمولة الأصلية للحدث الاقتصادي (Payload JSON).

### المهمة 4.2: تطوير وحدات الذمم المدينة والدائنة (AR & AP Subledger Units)

* **المشكلة الحالية:**
  وحدات الذمم الحالية توفر وظائف التسوية الأساسية ومصفوفة التقادم، لكنها تحتاج إلى تطوير دورة المطابقة المتقدمة متعددة العملات (Cross-Currency Matching)، وإدارة شروط الائتمان والدفع، ومعالجة إشعارات الخصم والإضافة، وإدارة الديون المتنازع عليها، وربط شطب الديون (Write-offs) بسير موافقات مالي صارم.
* **الهدف:**
  تطوير وحدتي `ReceivablesUnit` و `PayablesUnit` لتوفير إدارة نقدية وتشغيلية متقدمة لحسابات الموردين والعملاء.
* **السياق الفني والمحاسبي المطلوب:**
  * **المعايير المحاسبية:** معيار المحاسبة الدولي **IFRS 9** (إدارة التعثر وشطب الديون الرديئة)، ومبادئ إدارة رأس المال العامل (Working Capital Management).
* **خطوات التنفيذ المحددة:**
  1. إضافة ميزة المطابقة متعددة العملات مع توليد قيد فروق العملة المحققة (Realized FX Gain/Loss) آلياً عند اختلاف سعر الصرف بين تاريخ إصدار الفاتورة وتاريخ السداد.
  2. بناء سير موافقات إلزامي لعمليات شطب الديون (Debt Write-off) يمنع شطب أي رصيد مدين دون موافقة المدير المالي المعتمدة.
  3. دعم تقارير أعمار الديون التفصيلية بمستويات تحليلية حسب العميل والفرع ومركز التكلفة.
* **معايير قبول نفاذ المهمة (Acceptance Criteria):**
  * [ ] مطابقة فاتورة مبيعات بالدولار مسجلة بسعر 3.75 مع دفعة بنكية بالريال مسجلة بسعر 3.76، والتأكد من توليد قيد فروق صرف العملة المحقق تلقائياً وتصفير الخط المفتوح.
  * [ ] رفض أي عملية شطب ذمة مدينة بدون وجود موافقة رقمية صالحة من سلطة الاعتماد.

### المهمة 4.3: استكمال وتطوير وحدة الخزينة والبنوك (Treasury & Cash Management Unit)

* **المشكلة الحالية:**
  حزمة `internal/subledgers/treasury.go` تحتوي على قراءة كشوف البنوك والمطابقة الأساسية، لكنها تفتقر إلى بطاقة تعريف الحساب البنكي المؤسسية، والتحويلات البينية بين الحسابات البنكية (Inter-bank Transfers)، وحسابات النقدية في الطريق (Cash in Transit / Clearing Accounts)، وإدارة الاستثناءات في كشوف الحسابات المستوردة.
* **الهدف:**
  بناء وحدة `TreasuryUnit` لإدارة العمليات المصرفية والنقدية للشركة بدقة، وتأمين عمليات التحويل والتسوية البنكية الآلية.
* **السياق الفني والمحاسبي المطلوب:**
  * **المعايير الدولية:** معيار المحاسبة الدولي **IAS 7 (قائمة التدفقات النقدية)**، ومواصفات رسائل سويفت البنكية **MT940** و **CAMT.053 (ISO 20022)**.
* **خطوات التنفيذ المحددة:**
  1. إنشاء نموذج بطاقة الحساب البنكي:

     ```go
     type BankAccount struct {
         ID                uuid.UUID
         CompanyID         uuid.UUID
         BankName          string
         IBAN              string
         Currency          string
         GLAccountID       uuid.UUID // حساب الأستاذ العام المقابل
         ClearingAccountID uuid.UUID // حساب وسيط للتحويلات النقدية المعلقة
     }
     ```

  2. إنشاء دورة التحويل بين البنوك: توليد قيد من البنك المرسل إلى حساب النقدية بالطريق، ثم قيد الإيداع في البنك المستقبل عند تأكيد التسوية البنكية.
  3. تطوير محرك المطابقة البنكية الذكي (Smart Matching Engine) للربط الآلي بين حركات البنك والقيود الداخلية بناءً على التاريخ، والمبلغ، ورقم المرجع.
* **معايير قبول نفاذ المهمة (Acceptance Criteria):**
  * [ ] اختبار دورة تحويل بين حسابين بنكيين بنجاح عبر حساب وسيط وإثبات اتزان أرصدة دفتر الأستاذ.
  * [ ] استيراد كشف بنكي بصيغة CAMT.053 ومطابقة 95% من الحركات آلياً وعزل الحركات المعلقة في تقرير تسوية مستقل.

### المهمة 4.4: توسيع وحدة الأصول الثابتة وإهلاك المكونات (Fixed Assets Component Accounting Unit)

* **المشكلة الحالية:**
  وحدة الأصول الثابتة الحالية تطبق الإهلاك والانخفاض الأساسي، لكنها تفتقر إلى محاسبة أجزاء ومكونات الأصل المنفصلة (Component Accounting)، وإدارة الأصول الرأسمالية قيد التنفيذ (Capital Work in Progress / CWIP)، والمراجعة الدورية السنوية للعمر الإنتاجي والقيمة التخريدية المتبقية.
* **الهدف:**
  ترقية `FixedAssetsUnit` لدعم محاسبة المكونات المستقلة والتحويل من مشاريع قيد التنفيذ إلى أصول مشغلة وفق المعايير الدولية.
* **السياق الفني والمحاسبي المطلوب:**
  * **المعايير الدولية:** معيار المحاسبة الدولي **IAS 16 (العقارات والآلات والمعدات - الفقرات 43–47 الخاصة بإهلاك الأجزاء الهامة بشكل منفصل)**، ومعيار **IAS 36 (انخفاض قيمة الأصول)**.
* **خطوات التنفيذ المحددة:**
  1. تحديث بنية الأصل الثابت لدعم شجرة المكونات:

     ```go
     type AssetComponent struct {
         ID           uuid.UUID
         ParentAssetID uuid.UUID
         Name         string
         Cost         decimal.Decimal
         UsefulLife   int // بالأشهر
         Method       DepreciationMethod
         SalvageValue decimal.Decimal
     }
     ```

  2. حساب وتوليد قيود إهلاك مستقلة لكل جزء من أجزاء الأصل (مثل هيكل الطائرة مقابل محركاتها).
  3. دورة تحويل الأصول قيد التنفيذ (CWIP Capitalization): تحويل التكاليف المتراكمة في حساب المشروعات قيد التنفيذ إلى حساب الأصل الثابت النهائي بمجرد أن يصبح الأصل جاهزاً للاستخدام.
* **معايير قبول نفاذ المهمة (Acceptance Criteria):**
  * [ ] إهلاك أصل مركب (مثل مبنى مكون من هيكل ومصاعد وتكييف) بنسب إهلاك مختلفة لكل مكون بنجاح تام.
  * [ ] اختبار رسملة مشروع قيد التنفيذ وتوليد القيود المحاسبية التراكمية وترحيلها بنجاح.
