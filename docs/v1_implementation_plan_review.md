# مراجعة الخطة التنفيذية `v1` ومقارنتها بتحليل الفجوات

**تاريخ المراجعة:** 2026-11-13  
**الخطة المراجعة:** [`docs/v1_implementation_plan.md`](./v1_implementation_plan.md)  
**التحليل المرجعي:** [`docs/engine3_review_vs_v1_verification.md`](./engine3_review_vs_v1_verification.md)  
**أساس التقييم:** `HEAD a58ebe6`، مع الإشارة إلى الفجوات الإضافية التي كشفها تحليل `engine3`.

---

## 1. الحكم العام

الخطة **قوية جداً كإطار تنفيذي**، وأفضل من مجرد قائمة مهام: لديها مراحل، بوابات، اعتماديات، معايير قبول، وسياسة واضحة لمنع `Skip` وتجاوز الاختبارات. وهي تغطي معظم ما ورد في تقرير التحقق، خصوصاً:

- تثبيت خط الأساس وتصنيف اختبارات `gapred`.
- توفير Master Data عام.
- فرض مسار Posting وإزالة `fallback`.
- Idempotency ذرية.
- مستهلك خارجي مستقل.
- اختبارات تبديل Memory/PostgreSQL.
- gRPC وreadiness وDocker/CI.

لكن الخطة **مبنية على تقرير التحقق وحده**، ولذلك ورثت بعض الفجوات التي لم يغطها ذلك التقرير. النتيجة:

> **الخطة جاهزة كإطار عمل، لكنها غير مكتملة كخطة إغلاق `v1` كما هي.**  
> تحتاج إلى دمج خمس فجوات حرجة قبل بدء المرحلة 1، وإلا فإن بوابتي `P3-02` و`G5-01` ستفشلان أو ستمرّان بشكل مضلل.

## 2. نقاط القوة

1. **فصل المراحل والبوابات واضح:** لا تنتقل مرحلة قبل إثبات سابقتها.
2. **`F0-01` ممتازة:** تصنّف فشل `gapred` إلى فشل منتج/فشل إعداد/غير قابل للتكرار، وهذا يعالج مباشرة ملاحظة أن بعض الاختبارات لا تصل إلى `assertion`.
3. **الاعتماديات موثقة:** جدول الاعتماديات يمنع البدء على عقود غير مستقرة.
4. **`C1-02` تعالج جوهر المشكلة:** حدود المعاملة وIdempotency وApproval/Policy Ports، لا مجرد تحسين شكلي.
5. **`W2-01` شاملة:** إزالة `fallback`، وربط السياسة والاعتماد والأبعاد والمراقبة، وفصل Maker/Checker، وحفظ سبب العكس.
6. **`W2-02` تفرض اختبارات PostgreSQL حقيقية:** تزامن، تعارض حمولة، فشل بين المراحل، وإعادة تشغيل.
7. **`P3-01` و`P3-02` تمنعان الغش المعماري:** `go.mod` مستقل، فحص imports، ومنع `SaveDraftContext`/`PostAtomicContext` المباشرين في اختبار التبديل.
8. **`P3-03` تطلب أثراً محاسبياً فعلياً:** حسابات ومبالغ وعملة وتوازن، لا عدد سطور.
9. **`S4-02` صادقة:** تعترف بعدم وجود تكامل هوية معتمد ولا تعتبر endpoints المحمية مستوفاة.
10. **`G5-01` بوابة اعتماد حقيقية:** لا تقبل «بناء ناجح» بديلاً عن الأدلة السلوكية.

## 4. الفجوات الحرجة في الخطة

### G1 — لا توجد مهمة لإنشاء `Journal` في PostgreSQL (الأخطر)

`C1-01` تحدد النطاق بـ «على الأقل إنشاء/قراءة الشركة والحساب والسنة المالية والفترة»، ولا تذكر `Journal`. بينما:

- `toInternalEntry` يشتق `JournalID` من `(company, SourceModule)`.
- `PostAndSequenceContext` ينفذ `SELECT current_sequence FROM journals ... FOR UPDATE`.
- عولج غياب واجهة الإنشاء/القراءة العامة بعقد `CreateJournal` و`GetJournalByCode` في SPI، مع محولي Memory وPostgreSQL واختبارات عقد مشتركة. يظل ربط `JournalCode` بحلّ `JournalID` أثناء الترحيل خارج هذا التنفيذ المحدود.
- اختبارات PostgreSQL الحالية تُدخل `journals` بـ SQL مباشر.

**الأثر:** `P3-02` (تبديل Memory/PostgreSQL) سيفشل عند أول ترحيل PostgreSQL، و`G5-01` لن يجتاز الشرط `#7`. وحتى `P3-01` قد يمر على Memory فقط، فيعطي ثقة زائفة.

**الإصلاح المقترح:** توسيع `C1-01` أو إضافة `C1-06`:

- `CreateJournal/GetJournalByCode` بعقود عامة.
- قاعدة تفرد `(company_id, code)`.
- حل `JournalID` من `JournalCode` المعتمد، لا من Hash لـ `SourceModule`.
- معيار قبول: ترحيل PostgreSQL عبر SDK بعد تهيئة عامة فقط، دون SQL.

### G2 — `W2-03` لا تغطي كل اختبارات `gapred` الحمراء

`W2-03` تحدد `GAP-PST-01..06` و`GAP-GOV-01/03` فقط. لكن التشغيل الفعلي يُظهر فشلاً أيضاً في:

- `internal/ias12`: `GAP-STD-01/02`.
- `internal/subledgers`: `GAP-AST-01`.
- `storage/memory`: `GAP-AST-02`.
- `internal/reporting`: فشل بناء اختبارات `gapred` (رموز مفقودة).

**الأثر:** `P3-05` تضيف `gapred` إلى CI، و`G5-01` تطلب «لا اختبارات فجوات حمراء». ستظل هذه الحزم حمراء، فتفشل البوابة أو تُخفَّض بصمت.

**الإصلاح المقترح:** توسيع `W2-03` أو إضافة `W2-05`:

- `GAP-STD-01/02`.
- `GAP-AST-01/02`.
- إصلاح بناء `internal/reporting/gapred_test.go` أولاً، ثم تصنيف أي فشل متبقٍ.

### G3 — لا توجد مهمة لإصلاح Memory Balance Sheet

`GetBalanceSheet` في Memory يتجاهل خطأ `GetIncomeStatement`:

```go
is, err := d.GetIncomeStatement(...)
if err == nil && !is.NetIncome.Amount().IsZero() { ... }
```

**الأثر:** تقرير مالي ناقص يُعاد بنجاح. هذا يخالف روح الشرط `#4`، وقد يمر `P3-02` إذا كان الخطأ نادراً أو غير مغطى.

**الإصلاح المقترح:** إضافة معيار قبول صريح في `C1-01` أو مهمة مستقلة:

- `GetBalanceSheet` يرجع الخطأ مباشرة.
- اختبار يثبت عدم إسقاط خطأ قائمة الدخل.
- توثيق سياسة تحويل العملات في تقارير Memory، أو رفض العملة غير المدعومة صراحة.

### G4 — `W2-04` لا تذكر `JournalCode` ولا ربط `LedgerID` بدفتر فعلي

`PublicEventAccountMapping.JournalCode` موجود في العقد وفي SQL، لكنه لا ينتقل إلى `PostingRule`. `W2-04` تذكر `Payload/Dimensions` فقط.

**الأثر:** اختيار Mapping مختلف حسب `LedgerID` قد لا ينتج دفتراً مختلفاً، ويبقى `JournalID` مشتقاً من `SourceModule`.

**الإصلاح المقترح:** إضافة إلى `W2-04`:

- تمرير `JournalCode` إلى `PostingRule` ثم إلى `JournalID`.
- رفض `LedgerID` غير المعروف أو `JournalCode` غير الموجود.
- اختبار يثبت أن `LedgerID` مختلفاً ينتج `JournalID` مختلفاً.

### G5 — لا توجد مهمة لكسر تبعية `storage -> pkg/sdk`

`P3-04` تعالج استيراد `internal/*` من الحزم العامة، لكنها لا تعالج اعتماد:

- `storage/postgres/public_events.go`
- `storage/memory/public_events.go`

على `pkg/sdk`.

**الأثر:** اتجاه الاعتماد معكوس: Adapter يعتمد على طبقة التطبيق. هذا يعيق استبدال SDK أو استخدام العقود من مشروع آخر.

**الإصلاح المقترح:** إضافة إلى `C1-02` أو `P3-04`:

- نقل `PublicEventIngestion` و`PublicEventAccountMapping` وواجهاتهما إلى `pkg/spi/events`.
- منع `storage/*` من استيراد `pkg/sdk` كمعيار قبول.

### G6 — `W2-02` لا تنص صراحة على سلوك الفشل

الخطة تغطي الحجز والذرية والاسترداد، لكنها لا تنص صراحة على:

- إرجاع خطأ `Complete` إلى المستدعي بعد نجاح الترحيل.
- حفظ `reason` في `FailPublicEventIngestion`.
- سياسة إعادة محاولة المفتاح `failed`.
- lease/owner/attempt count للحالة `processing`.

**الإصلاح المقترح:** إضافة معايير قبول صريحة إلى `W2-02`، لا الاكتفاء بعبارة «State Machine قابلة للاستئناف».

## 5. مخاطر الترتيب والتوازي

1. **المسار الحرج طويل:**
   `F0-01 → C1-01/C1-02/C1-03 → C1-04 → W2-01 → W2-02/W2-03 → P3-02 → G5-01`.

   هذا مقبول منطقياً، لكنه يجعل `C1-02` نقطة اختناق لكل شيء تقريباً.

2. **`C1-02` واسعة جداً:** تجمع Transaction Manager وIdempotency Repository وApproval/Policy Ports. يُفضّل تقسيمها إلى:
   - `C1-02a`: حدود المعاملة وIdempotency.
   - `C1-02b`: Policy/Approval Ports.
   أو تثبيت حد زمني وعقد أدنى قابل للتنفيذ.

3. **`W2-04` يمكن أن تتوازى مع `W2-01`:** كلتاهما تعتمد على `C1-04` لكن لا تعتمد إحداهما على الأخرى. الخطة تسمح بذلك ضمنياً، ويُفضّل توضيحه.

4. **`W2-03` يمكن تجهيز fixtures بالتوازي مع `C1-02`:** الخطة تذكر ذلك، وهو قرار جيد.

5. **`S4-01` و`S4-02` مستقلتان مبكراً:** قرار جيد، لكن `S4-02` تعتمد على آلية هوية غير موجودة. يجب أن يكون القرار: إما اعتماد آلية، أو تأجيل المصادقة صراحةً مع عدم اعتبار الشرط `#8` مكتملاً.

6. **`G5-01` بوابة واحدة في النهاية:** جيدة، لكنها ستكشف متأخراً أي فجوة غير مسندة (مثل Journal وSTD/AST). يجب أن تكون هناك بوابات وسيطة تشغيلية، لا فقط نهائية.

## 6. تعديلات مقترحة على الخطة

### تعديل 1 — توسيع `C1-01` أو إضافة `C1-06` لـ Journal

**العنوان المقترح:** `C1-06 — توفير Journal provisioning عام`

- **النطاق:** `CreateJournal`, `GetJournalByCode`, `ListJournals`، وربط `JournalCode` بالترحيل.
- **معايير القبول:**
  - مستهلك عام ينشئ دفتراً ثم يرحّل قيداً على PostgreSQL دون SQL.
  - `JournalID` يُحل من الدفتر المعتمد، وليس من `SourceModule`.
  - محاولة الترحيل إلى دفتر غير موجود تفشل بخطأ typed.

### تعديل 2 — توسيع `W2-03` أو إضافة `W2-05` لـ STD/AST/reporting

- **النطاق:** `GAP-STD-01/02`، `GAP-AST-01/02`، وإصلاح بناء `internal/reporting/gapred_test.go`.
- **معايير القبول:**
  - `go test -tags gapred ./...` لا يعيد أي فشل غير مصنف.
  - كل فشل سابق إما أُصلح أو حُوّل إلى `Skip` موثق بمالك وتاريخ.

### تعديل 3 — إضافة معيار Memory Balance Sheet

- **الموضع:** `C1-01` أو مهمة جديدة `C1-07`.
- **المعيار:**
  - `GetBalanceSheet` يرجع خطأ `GetIncomeStatement` ولا يخفيه.
  - تقارير Memory ترفض العملة غير المدعومة أو توثق سياسة التحويل.
  - اختبار عقد مشترك بين Memory وPostgreSQL.

### تعديل 4 — توسيع `W2-04` لـ JournalCode

- **المعيار:**
  - `JournalCode` ينتقل من Mapping إلى القيد.
  - `LedgerID` مختلف ينتج `JournalID` مختلفاً.
  - `JournalCode` غير موجود يفشل بخطأ واضح.

### تعديل 5 — توسيع `P3-04` لكسر تبعية SDK

- **المعيار:**
  - `storage/*` لا يستورد `pkg/sdk`.
  - عقود الأحداث في `pkg/spi/events`.
  - فحص imports يفشل عند إدخال اعتماد معكوس جديد.

### تعديل 6 — تشديد `C1-03`

استبدال عبارة «أو يُرفض عدم دعمها صراحة» بقائمة حقول إلزامية:

- `SourceModule`
- `FiscalPeriodID`
- `TransactionCurrency`
- `ExchangeRate`
- `ApprovalFingerprint`
- حقول الأبعاد المدعومة

مع اختبار round-trip لكل حقل، ورفض صريح لأي حقل غير مدعوم.

### تعديل 7 — تحديث بوابة `v1` الشرط `#4`

الخطة تعرّف الشرط `#4` كـ «بيانات وتقارير حقيقية وأخطاء قدرات صريحة». يجب توسيعه ليشمل:

- عدم إسقاط أخطاء التقارير.
- سياسة العملات.
- عدم وجود دالة عامة تخمّن الحسابات.
- أو خفض الحكم إلى «جزئي» كما في التحليل المرجعي.

### تعديل 8 — حسم `cmd/agy`

إما:

- توحيده مع `accounting-service`، أو
- إعلانه Legacy/خارج نطاق `v1` صراحةً.

وإلا سيظل مصدر التباس في شرط الخدمة `#8`.

## 7. الحكم النهائي

| المحور | التقييم |
| --- | --- |
| البنية والتنظيم | ممتاز |
| قابلية التنفيذ | عالية |
| الاعتماديات والتوازي | جيدة، مع اختناق في `C1-02` |
| معايير القبول | جيدة، لكن بعضها قابل للتأويل |
| التغطية مقابل تحليل الفجوات | ناقصة في 5 نقاط حرجة |
| الجاهزية كخطة إغلاق `v1` | غير مكتملة كما هي |

**الخلاصة:**

- الخطة **أساس قوي**، ولا تحتاج إعادة كتابة.
- لكن تنفيذها حرفياً سيؤدي إلى:
  - فشل `P3-02` أو `G5-01` بسبب غياب `Journal`.
  - فشل `P3-05` أو `G5-01` بسبب بقاء `GAP-STD/AST` حمراء.
  - احتمال نجاح مضلل للشرط `#4` بسبب خطأ Memory Balance Sheet.
  - بقاء `JournalCode` والتبعية المعكوسة دون معالجة.

**التوصية:** دمج التعديلات الثمانية أعلاه في الخطة **قبل بدء المرحلة 1**، خصوصاً تعديل `C1-01` الخاص بـ `Journal`، لأنه:

- رخيص الآن.
- مكلف جداً بعد بناء المستهلك الخارجي واختبارات التبديل.
- شرط مباشر لاجتياز الشرطين `#1` و`#7`.

بعد هذه التعديلات، تصبح الخطة **جاهزة فعلياً** كخطة إغلاق `v1`، وليست مجرد إطار عمل جيد.
