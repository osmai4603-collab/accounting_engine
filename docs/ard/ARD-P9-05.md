# ARD-P9-05: Structured disclosures framework

## Status

Implemented; P9-01 and P9-02 prerequisites are complete and verified.

## Decision

Provide a public, versioned disclosure value model and an optional
`standards.DisclosureProvider` contract. The SDK's `ReportingService` aggregates
disclosures from configured standard modules implementing that contract.
Providers remain responsible for calculating the disclosure from their
accounting sources; this framework validates, scopes, orders, and fingerprints
the returned values, but does not persist or calculate standard-specific notes.

## Public model

`reporting.StructuredDisclosure` contains:

- Company, stable disclosure code and title.
- Standard reference, reporting period, presentation currency, and schema
  version.
- One or more typed source references.
- JSON-serializable structured `Data` and optional explanatory `Narrative`.
- A SHA-256 `ContentHash` generated by the registry.

`reporting.DisclosureQuery` requires a company and start/end dates. Currency,
standard reference, and version are optional exact filters. Omitting version
returns all versions supplied for that scope; the framework does not guess
which schema version is newest.

## Reproducibility and validation

The registry normalizes period boundaries to UTC calendar dates, currencies to
uppercase, and textual identifiers by trimming surrounding whitespace. It
canonicalizes structured JSON, sorts sources and providers deterministically,
rejects duplicate disclosure identities, and sorts the final result by
standard reference, code, version, and currency. The content hash covers the
company, identity, period, currency, version, sources, structured data, and
narrative. A provider-supplied non-empty hash must match the canonical payload.

Each result must match the requested company and period and any supplied
filters. Invalid data, cross-company results, duplicate records, context
cancellation, and provider errors are returned explicitly; the registry does
not silently omit invalid records.

## Provider contract example

A provider implements
`GetDisclosures(context.Context, reporting.DisclosureQuery) ([]reporting.StructuredDisclosure, error)`.
It reads company-scoped accounting data through its configured ports and
returns records matching the query, with structured source references and
data. If a required source cannot be read, it returns an error. The SDK
integration test `TestBuilder_ReportingServiceAggregatesStructuredDisclosures`
demonstrates a sample provider and its retrieval through `ReportingService`.

## Boundaries and compatibility

- Implementing `DisclosureProvider` is optional for standard modules.
- No built-in module is claimed to satisfy every IFRS/IAS disclosure.
- A disclosure is reproducible only when its provider uses stable inputs and
  deterministic calculations; the registry makes no accounting judgment about
  provider data.
- The registry is read-only and does not create database tables or persist
  versions. Hosts/providers own their source-data retention and version
  lifecycle.
- `ReportingService` gains `GetDisclosures`; consumers implementing that
  interface must add the new method.

## Verification

Unit tests cover canonical hash stability, normalization, company/period/version
scope, duplicate identities and provider names, unavailable providers, stale
hashes, provider errors, and cancellation. An SDK integration test verifies
that a standard module provider is reachable through `ReportingService`.

The framework and both dependency capabilities are implemented. Their
respective verification records are in
[`ARD-P9-01-accounting-closing-design.md`](./ARD-P9-01-accounting-closing-design.md)
and [`ARD-P9-02.md`](./ARD-P9-02.md). This framework does not claim that any
built-in provider supplies every IFRS/IAS disclosure.
