# ARD-P10-03: Treasury and bank reconciliation

## Status

Implemented within `internal/subledgers/treasury.go`. The public API and SPI
models in `pkg/api/v1/subledger/models.go` and
`pkg/spi/subledger/stores.go` are consumed as-is; neither shared contract nor
the SDK builder is changed.

## Scope and decisions

- `TreasuryLedger` implements the frozen `TreasuryStore` contract for bank
  account and transaction metadata. Saving metadata is not a posting request.
- `CreateTransactionDraftContext` is the explicit direct-deposit/withdrawal
  posting path. It checks company, bank account, currency, date, and positive
  amount, builds a balanced two-line draft, validates it, and passes it to the
  supplied `JournalCreator` (the posting/application boundary).
- Interbank transfers use a shared clearing account. Initiation credits the
  source bank and debits clearing; settlement debits the destination bank and
  credits clearing. Each separately created draft is balanced and identified
  with the transfer ID.
- `ImportStatementContext` accepts already-structured statement lines,
  validates and normalizes them, and returns external/unrecorded items. It does
  not save ledger items or create journal entries; file-format parsers remain
  outside this scope.
- `ReconcileWithToleranceContext` and `ReconciliationReportContext` perform
  matching and return pending book items and unrecorded statement items. They
  update match metadata only, never create a GL draft. The report's balances
  are the signed unmatched statement amount and pending ledger amount,
  respectively, and `UnmatchedItems` counts both pending and unrecorded items.
- A fee difference through `ReconcileMultiLineContext` is rejected unless the
  caller uses `ReconcileMultiLineApprovedContext` with a non-empty approval ID,
  approver, reason, and approval time. The approved draft retains approver,
  approval ID/reason, and approval time. Matching without a difference remains
  non-posting. The deprecated `ReconcileMultiLine` compatibility method also
  requires the explicit approval-bearing operation before an adjustment draft
  can be created; fee-account parameters alone do not constitute approval.
- `ProcessBankFeeAtomicContext` likewise does not create a fee adjustment
  without approval. Use `ProcessBankFeeApprovedAtomicContext` for the
  approval-bearing atomic update of the bank item and draft.

## Validation and tests

`internal/subledgers/treasury_p10_03_test.go` covers public-store metadata
operations, direct deposit drafts, clearing-account transfers, statement
import and pending-item reporting without drafts, currency rejection, and the
explicit approval gate for fee adjustments.

## Known limitations

- The frozen public bank-account contract has no clearing-account field, and
  the frozen treasury SPI has no transfer or statement methods. Clearing
  accounts and transfer lifecycle therefore remain internal operations.
- The current `TreasuryLedger` stores public bank-account and transaction
  metadata in its own in-memory maps. A durable metadata repository is not
  provided by the frozen `TreasuryStore`/current treasury repository contracts.
- Transfer initiation and settlement are two application draft operations;
  durable transfer lifecycle persistence/atomic orchestration is outside the
  current contract.
