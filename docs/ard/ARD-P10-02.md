# ARD-P10-02: Fixed-asset subledger lifecycle

## Status

Accepted for the implementation in this repository.

## Decision

Keep fixed-asset registration, schedule calculation, and accounting posting as
separate operations. Registering an asset or calculating a schedule only reads
or writes subledger state; it does not create a journal entry. Depreciation,
revaluation, and disposal are accounting events and must be posted through the
posting engine.

The existing public API and SPI model/store declarations are shared P10-01
contracts and remain unchanged. The fixed-asset ledger implements the public
fixed-asset store for the accounting fields expressible by the DTO and the
monthly depreciation calculator for straight-line and declining-balance assets.
The public store treats `SaveAsset` as registration of a new asset; duplicate
IDs are rejected rather than overwriting accounting state without a journal.

## Accounting and atomicity

- Atomic depreciation derives the amount and journal lines from the stored
  asset, then posts the entry with an attachment that applies the accumulated
  depreciation and carrying-value update in the same posting transaction.
- `DepreciateAssetAdjustingAtomic` classifies a depreciation event as a
  provision-estimate adjustment. It requires explicit authorization, reason,
  approval reference, approver, and approval time; the existing
  `DepreciateAssetAtomic` remains compatible for regular posting workflows.
  Consumers requiring the P9 adjusting-entry policy must use the explicitly
  approved adjusting method.
- Atomic revaluation posts the fair-value movement and applies the carrying
  value, adjustment, surplus, and applied-entry marker in the same transaction.
  Upward movements are credited to revaluation surplus. Downward movements
  first consume the asset's existing surplus and charge any excess to the
  revaluation loss account.
- Atomic disposal clears gross carrying amount and accumulated depreciation
  and impairment, records proceeds, and books the resulting gain or loss. The
  asset's disposed state is committed with the posted entry.
- A failed post does not commit the corresponding asset mutation. The posting
  engine remains responsible for entry validation, period policy, sequence,
  and final ledger posting.

## Depreciation calculator

The public calculator calculates one nominal monthly amount without a posting
date: straight-line uses original depreciable cost over useful-life months;
declining-balance uses twice the useful-life monthly rate against net book
value. Both are rounded for posting and capped so that book value cannot fall
below salvage value. The dated internal schedule remains responsible for
partial-month proration.

## Consequences and boundaries

The current public DTO omits asset name/category, account mappings, declining
rate, components, and disposal details. Those values cannot be faithfully
round-tripped or configured through the existing `FixedAssetStore`; public
depreciation uses the standard double-declining rate, while detailed accounting
events remain available through the internal ledger. In particular, an asset
registered through the DTO has no GL account mapping and cannot be posted for
depreciation, revaluation, or disposal until an internal integration supplies
those account mappings. Expanding that capability requires a coordinated
P10-01-owned contract change, which was deliberately not made in P10-02.

This decision does not add a public posting command or a new builder capability.
Physical inventory and other descriptive-only asset changes remain
non-accounting operations.

## P10-02 acceptance status

- [x] Implement the existing public `FixedAssetStore` and
  `DepreciationCalculator` interfaces without changing their shared contracts.
- [x] Support straight-line and declining-balance public monthly estimates,
  including salvage-value caps and currency validation.
- [x] Post and atomically apply depreciation, revaluation, and disposal using
  the posting engine; the lifecycle test verifies balanced posted entries and
  the resulting asset state.
- [x] Keep registration/store reads and schedule calculation out of the posting
  path.
- [ ] Full public-DTO round-trip and public posting lifecycle: blocked by the
  missing descriptive fields and account mappings listed above.
- [ ] Require adjusting-entry authorization for every depreciation entry:
  supported by `DepreciateAssetAdjustingAtomic`, but not imposed on the existing
  regular-posting compatibility method.
