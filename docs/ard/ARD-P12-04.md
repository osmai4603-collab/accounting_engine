# ARD-P12-04 — Event Ingestion Recovery Verification

- **Status:** Complete
- **Date:** 2026-11-17
- **Scope:** Public SDK event-ingestion failure handling, idempotent redelivery, and recovery after interruption.
- **Decision:** Preserve durable idempotency as the only keyed-ingestion path and verify recovery through the public SDK and storage contracts. Do not promise exactly-once message delivery; at-least-once delivery plus durable idempotency provides effectively-once journal posting when the adapter satisfies its storage contracts.

## Evidence and behavior

Review of `pkg/sdk/event_ingestion.go` and the `ProcessEvent` flow confirmed
that keyed ingestion already requires a durable idempotency store, records
classified failures, and attempts recovery from a reserved entry identity.
No SDK behavior change was needed; this task closes the integration-evidence
and consumer-documentation gaps.

1. A draft rejected during posting is persisted as a terminal failure with a reason. The same engine subsequently accepts and posts a valid event, proving one rejected event does not stop the ingestion service.
2. An injected transaction serialization failure leaves the event retryable. Redelivery with the same key and payload completes the event and results in one balanced posting.
3. Redelivery after constructing a new SDK engine returns the original posted journal entry without a second posting.
4. A durable `started` record seeded with its reserved entry identity and draft snapshot is recovered by a new SDK engine, then completed with one balanced posting.
5. The public integration scenarios live in [`event_fault_recovery_test.go`](../../test/integration/event_fault_recovery_test.go). Existing SDK tests additionally cover concurrent same-key delivery, payload conflicts, missing durable stores, in-flight handling, terminal failures, and failures after commit.
6. [`sdk_developer_guide.md`](../sdk_developer_guide.md#event-delivery-and-recovery) documents the delivery contract, retry policy, and operational limits.

## Verification

- `go test ./test/integration -run 'TestEvent(ValidationFault|PostingFailure|DuplicateDelivery|Recovery)' -count=1` — passed.
- No dependencies were added and `go.mod` was not changed.

## Guarantees and limits

- A repeated `(company, source system, idempotency key)` with the same canonical payload returns the existing result; changed payloads conflict.
- Transient failures are retryable, while deterministic posting failures are terminal and retain a rejection reason.
- Recovery of an abandoned `started` record requires its reserved entry identity and snapshot. The SDK checks whether that entry already posted before resuming.
- The integration tests use the in-memory reference adapter and simulate a crash by persisting a `started` record before starting a new engine. They do not simulate machine failure or establish production durability. Cross-process durability depends on a production adapter's durable uniqueness, transaction, tenant-isolation, and persistence guarantees.
- Initial envelope validation that occurs before a durable claim returns an error but cannot persist an ingestion failure record.
