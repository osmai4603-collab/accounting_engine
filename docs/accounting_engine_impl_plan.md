# الخطة التنفيذية — Productization وإصلاحات Accounting Engine

- **نوع الخطة:** `accounting_engine`
- **الغرض:** تحويل Accounting Engine من نواة محاسبية ذات موائمات مدمجة إلى منتج محاسبي مستقل، بعقود عامة مستقرة، ومسار تطبيق موحد، وموائمات تخزين قابلة للاستبدال، وضوابط محاسبية وتشغيلية قابلة للإثبات.
- **المرجع:** تدقيق النسخة `engine5.zip` في هذه المحادثة، وملفات المشروع الحالية، ومبادئ إعادة التصميم التي حددها مالك المشروع، وملف `SKILL.md` المرفق.
- **تاريخ الإنشاء:** 2026-11-13
- **آخر تحديث:** 2026-11-14
- **النطاق:** `pkg/api/v1`، `pkg/sdk`، `pkg/spi`، `internal/sdkapplication`، `internal/posting`، `storage/postgres`، `storage/memory`، `modules/*`، `cmd/accounting-service`، `proto/accounting/v1`، `docs/`، واختبارات القبول.
- **قيد مهم:** هذه خطة تنفيذ وليست شهادة بأن الإصلاحات نُفذت. جميع المهام تبدأ بحالة `معلقة`. لا تُعلن أي وظيفة مكتملة محاسبيًا أو إنتاجيًا لمجرد وجود تنفيذ أو نجاح اختبار؛ يلزم إثبات السلوك المقصود ومعايير القبول المحددة.

## قواعد تنفيذ الخطة

1. يُجمّد التوسع في الميزات القطاعية والمعيارية حتى إغلاق بوابات المنتج الأساسية في `P1` إلى `P3`، إلا إذا كانت ميزة مطلوبة مباشرة لإزالة عائق في مهمة معتمدة.
2. لا تُكسر العقود العامة المنشورة بصمت. أي تغيير غير متوافق يُسجل كقرار إصدار ويُعالج بإصدار رئيسي أو فترة إهمال موثقة.
3. يبقى `internal/` داخليًا. لا تُحل مشكلة SPI بنقل تفاصيل التنفيذ الداخلية كما هي إلى واجهة عامة؛ المطلوب عقود عامة مستقلة تعبر عن القدرات المطلوبة فقط.
4. Storage Adapter مسؤول عن التخزين وحدود المعاملة؛ ولا يُطلب منه إنشاء Application Service أو تنفيذ منطق المحاسبة نيابة عن المحرك.
5. جميع عمليات إنشاء القيود والتحقق والترحيل والعكس والأحداث تمر عبر Application Layer واحدة. لا يجوز لـ HTTP أو gRPC أو SDK أو Industry Adapter تجاوزها.
6. لا تُنشأ `JournalID` أو `EntryID` أو `LineID` اصطناعية لتعويض بيانات أساسية مفقودة. تُرفض البيانات غير المكتملة أو تطبق سياسة هوية موثقة وصريحة.
7. يُمنع تشغيل Production على Memory تلقائيًا. استخدام Memory يكون اختيارًا صريحًا لبيئات الاختبار أو التطوير.
8. يجب الفصل بين صحة القيد المزدوج، وصحة الاعتراف والقياس وفق معيار بعينه، وجودة تنفيذ الكود. لا يستنتج أي مستوى من الآخر.
9. كل مهمة تُغلق بملف `docs/ard/ARD-<task-id>.md` يحتوي أدلة فعلية. لا تتحول الحالة إلى `منفذة` قبل اكتمال كل معايير القبول.
10. أي متطلب معياري غير محسوم يتطلب الرجوع إلى النص الرسمي الحالي، وتحديد إصدار المعيار وتاريخ سريانه والنطاق، ومراجعة محاسب مؤهل. لا يُستخدم وصف «متوافق مع IFRS» بناءً على اختبارات تقنية وحدها.

## تعريف حالات الاكتمال الوظيفي

| الحالة الوظيفية | المعنى |
| --- | --- |
| غير موجودة | لا يوجد عقد أو تنفيذ أو مسار قابل للاستدعاء. |
| غير منفذة | يوجد تصريح أو واجهة أو Stub، دون سلوك فعلي مكتمل. |
| مكتملة جزئيًا | يوجد سلوك فعلي لكن توجد حالات أو متطلبات غير مدعومة. |

| تحتاج تحققًا فعليًا | يبدو التنفيذ موجودًا لكن الدليل التشغيلي أو المحاسبي غير كافٍ. |

## 3. تفاصيل المهام

### المرحلة `P0` — تثبيت خط الأساس وقرارات المنتج

#### `P0-01` — اعتماد حدود المنتج ونطاق الإصدار الأول

- **المشكلة التي تحلها:** النسخة تجمع بين محرك محاسبي ومكونات ERP وتقارير ومعايير وخدمات دون حد فاصل دقيق بين Core وCapabilities اختيارية ومسؤوليات النظام المستهلك.
- **الهدف الذي تحققه:** وثيقة Product Boundary تحدد مسؤوليات المحرك والنظام المضيف والموائمات، وما يدخل الإصدار الأول وما يبقى خارجه.
- **نطاق المهمة:** تصنيف Core Ledger وMaster Data وPosting وReversal وAudit وReporting وGovernance وStandard Modules وIndustry Adapters. لا تشمل تعديل الكود أو إعلان امتثال معياري.
- **خطوات التنفيذ:**
  1. حصر الخدمات التي يجب أن يقدمها المحرك: إنشاء/قراءة القيود، التحقق، الترحيل، العكس، الأحداث، والسجل المحاسبي.
  2. حصر ما يملكه النظام المضيف: المبيعات والمخزون والرواتب والعمليات الزراعية/الصناعية وإدارة هوية المستخدمين عند توفيرها خارجيًا.
  3. تحديد الحد الأدنى من Master Data لتشغيل Posting: Company وAccounts وJournals وFiscal Periods وFunctional Currency والصلاحيات.
  4. تصنيف كل Capability إلى `core-required` أو `optional` أو `host-owned` أو `out-of-scope`.
  5. تعريف معايير قياس Industry Independence وInfrastructure Independence وExternal Consumption.
  6. تحديد نطاق الإصدار الأول دون وصف وحدات معيارية بأنها متوافقة بالكامل.
- **الاعتماديات:** لا شيء.
- **معايير القبول:**
  - [ ] وجود `docs/product_boundary.md`.
  - [ ] تصنيف كل Capability حالية ضمن أحد الأنواع الأربعة.
  - [ ] قائمة صريحة بالميزات المجمدة حتى إغلاق Productization.
  - [ ] مراجعة النطاق مقابل التجارة والزراعة والصناعة والخدمات.

#### `P0-02` — إنشاء خريطة الاعتماديات والحدود الحالية

- **المشكلة التي تحلها:** لا توجد خريطة موحدة لاتجاه الاعتماديات والتسرب من `internal` إلى واجهات المنتج، كما أن Root API و`pkg/sdk` يقدمان نقطتي دخول محتملتين.
- **الهدف الذي تحققه:** خريطة فعلية للحزم والاعتماديات ونقاط التسرب والتداخل في الملفات.
- **نطاق المهمة:** جرد imports والرموز المصدرة وعمليات كتابة DB وSQL والمشغلات. لا تشمل إعادة تصميم أو حذف حزم.
- **خطوات التنفيذ:**
  1. استخراج الحزم عبر `go list ./...`.
  2. استخراج import graph وتحديد Public Packages التي تستورد `internal/*` مباشرة أو غير مباشرة.
  3. جرد الأنواع والواجهات المصدرة في `engine.go` و`engine_observability.go` ومقارنتها مع `pkg/sdk`.
  4. رسم الاعتماديات بين `pkg/api/v1` و`pkg/spi` و`pkg/sdk` و`internal` و`storage` و`cmd`.
  5. حصر عمليات الكتابة والقيود والمشغلات وmigrations الخاصة بـ Posting وReversal وBalances وIdempotency.
  6. ربط كل Finding بمسار ملف ورمز واختبار متأثر.
- **الاعتماديات:** لا شيء.
- **معايير القبول:**
  - [ ] وجود `docs/architecture/current_dependency_map.md`.
  - [ ] الخريطة تعرض اتجاه الاعتماديات لا أسماء الطبقات فقط.
  - [ ] كل ملاحظة قابلة للتحقق من ملف أو رمز محدد.
  - [ ] تحديد الملفات المشتركة التي تتطلب تنسيقًا قبل تعديلها.

#### `P0-03` — تثبيت خط أساس الاختبارات وقاعدة البيانات

- **المشكلة التي تحلها:** لا يمكن قياس أثر إعادة التصميم دون baseline قابل لإعادة الإنتاج، ويجب فصل نتائج الاختبارات عن ادعاء أن الاختبارات سليمة.
- **الهدف الذي تحققه:** سجل تشغيل baseline للاختبارات والفحوص المعمارية وmigrations وPostgreSQL.
- **نطاق المهمة:** تشغيل الموجود وتسجيل النتائج كما هي. لا تشمل إصلاح الاختبارات أو إخفاء فشل قائم.
- **خطوات التنفيذ:**
  1. تسجيل إصدار Go الفعلي ومطابقته مع `go.mod` و`toolchain` وCI.
  2. تشغيل `gofmt` check و`go vet ./...` و`go test ./...` وتسجيل رمز الخروج.
  3. تشغيل `check_public_api_purity.sh` و`check_service_integration.sh` و`check_coverage.sh` و`scan_secrets.sh` عند توفر متطلباتها.
  4. تشغيل PostgreSQL tests على قاعدة اختبار مستقلة وتسجيل إصدار DB وإعدادات العزل ونتيجة migrations.
  5. تصنيف الإخفاقات إلى كود/بيئة/اعتماد خارجي/اختبار متذبذب.
  6. تسجيل coverage كمعلومة لا كدليل مستقل على الصحة المحاسبية.
- **الاعتماديات:** لا شيء.
- **معايير القبول:**
  - [ ] وجود `docs/baselines/engine5_baseline.md`.
  - [ ] كل أمر موثق ببيئته ونتيجته ورمز خروجه.
  - [ ] نتائج Memory منفصلة عن PostgreSQL.
  - [ ] لا توجد دعوى نجاح اختبارات دون سجل تشغيل.

#### `P0-04` — اعتماد قرارات التصميم وتجميد النطاق

- **المشكلة التي تحلها:** قد تختلف قرارات التنفيذ اللاحقة حول موضع Application Layer وملكية المعاملة وSPI وهوية المستخدم وحدود الوحدات المعيارية.
- **الهدف الذي تحققه:** ADRs ملزمة قبل تعديل العقود العامة.
- **نطاق المهمة:** قرارات معمارية ومنتج فقط. لا تشمل تنفيذها.
- **خطوات التنفيذ:**
  1. اعتماد قرار نقطة الدخول العامة وفصل API عن SPI.
  2. اعتماد قرار Application Layer وPorts/Adapters وUnit of Work.
  3. تحديد مسؤولية المحرك والنظام المضيف في Authentication/Authorization.
  4. تحديد مصدر Company/Tenant Context الموثوق.
  5. تحديد نطاق وإصدارات وحدات IAS/IFRS الاختيارية.
  6. اعتماد سياسة Memory/PostgreSQL وGo Module وSemVer.
  7. اعتماد تجميد الميزات الجديدة حتى اجتياز بوابات المنتج الأساسية.
- **الاعتماديات:** `P0-01`، `P0-02`، `P0-03`.
- **معايير القبول:**
  - [ ] ADR لكل قرار أو توثيق سبب دمج بعضها.
  - [ ] لا توجد قرارات أساسية معلقة تؤثر على Public API أو Storage SPI.
  - [ ] كل ADR يضم السياق والبدائل والقرار والنتائج.
  - [ ] تجميد التوسع موثق وموافق عليه.

### المرحلة `P1` — تأسيس Public API وPublic SPI

#### `P1-01` — جرد العقد العام ومنع تسرب Internal

- **المشكلة التي تحلها:** أنواع Root API المصدرة ترتبط بـ `internal`، بينما فحص النقاء الحالي يركز على `pkg/...` ولا يغطي كل نقطة دخول عامة.
- **الهدف الذي تحققه:** قائمة API/SPI رسمية وقاعدة آلية تمنع تسرب التنفيذ الداخلي.
- **نطاق المهمة:** `engine.go` و`engine_observability.go` و`pkg/api/v1` و`pkg/sdk` و`pkg/spi` والحزم المصدرة. لا تشمل حذف Root API.
- **خطوات التنفيذ:**
  1. استخراج كل الرموز المصدرة وتحديد جمهورها.
  2. تسجيل مالك كل نوع وسبب نشره واعتمادياته واستراتيجية توافقه.
  3. فصل DTOs العامة عن Domain Models الداخلية، ومنع كشف SQL Rows أو DB Handles.

- **الاعتماديات:** اكتمال جميع مهام `P0`.

  - [ ] وجود `docs/public_api_inventory.md`.

#### `P1-02` — تصميم عقود Public API وPublic SPI النهائية

- **المشكلة التي تحلها:** `CoreLedgerStore` يخلط التخزين بعملية `PostEntry`، و`LedgerApplicationProvider` يجعل التخزين ينشئ Application Service، وMasterData يُكتشف عبر Type Assertion إضافي.
- **الهدف الذي تحققه:** عقود تفصل Application Commands عن Persistence Ports وعن Integration Ports.
- **نطاق المهمة:** تصميم وتوثيق العقود قبل نقل كل الاستدعاءات.
- **خطوات التنفيذ:**
  1. تحديد Ports مستقلة للقيود والسطور والدفاتر والحسابات والفترات والتسلسل والأرصدة والتدقيق وIdempotency وأسعار الصرف عند الحاجة.
  2. تعريف `UnitOfWork` أو Transaction Runner محايد لا يكشف `pgx.Tx` أو PostgreSQL.
  3. تعريف Application Commands/Queries منفصلة عن Repositories.
  4. فصل Integration SPI لاستقبال أحداث النظام المضيف عن Persistence SPI.
  5. اعتماد حزم عامة واضحة مثل `pkg/spi/storage` و`pkg/spi/application` و`pkg/spi/integration` أو بديل موثق.
  6. تعريف Reporting وGovernance وStandards كـ Capabilities مستقلة لا كحقول إلزامية في Core Store.
  7. كتابة مثال Adapter لا يستورد أي `internal` ولا يعرف SQL.
- **الاعتماديات:** `P1-01`.
- **معايير القبول:**
  - [ ] وجود `docs/public_contracts_design.md` ومخطط تبعيات.
  - [ ] لا تتضمن العقود أنواعًا من `internal` أو `pgx` أو SQL-specific structs.
  - [ ] لا تحتوي Storage SPI على Post/Reverse أو إنشاء Application Service.
  - [ ] كل Capability اختيارية لها عقد مستقل.
  - [ ] تمت مراجعة التصميم من منظور مطور خارجي.

#### `P1-03` — تنفيذ Public SPI المستقل

- **المشكلة التي تحلها:** العقود العامة الحالية لا تكفي لتشغيل Application Layer من Adapter خارجي، بينما التنفيذ الداخلي يعتمد واجهات `internal/posting` و`internal/masterdata`.
- **الهدف الذي تحققه:** واجهات عامة مستقرة يمكن لمطور خارجي تنفيذها دون استيراد `internal`.
- **نطاق المهمة:** تنفيذ عقود `P1-02` ومحولات داخلية بينها وبين الخدمات الحالية. لا تشمل إعادة تنفيذ الموائمات بعد.
- **خطوات التنفيذ:**
  1. إنشاء الحزم العامة والأنواع والأخطاء المتفق عليها.
  2. تعريف Master Data Ports للشركة والحساب والدفتر والفترة والعملة الوظيفية.
  3. تعريف Ports للقيود والسطور والتسلسل والأرصدة والتدقيق وIdempotency وفق فصل المسؤوليات.
  4. تنفيذ Transaction Runner عام لا يمرر اتصال DB للمستهلك.
  5. فصل Application Contracts عن Storage Contracts.
  6. إضافة compile-time interface assertions واختبارات تجميع Adapter خارجي.
  7. توثيق ضمانات Atomicity والعزل والتفرد وترتيب الأقفال ومعاني الأخطاء.
- **الاعتماديات:** `P1-02`.
- **معايير القبول:**
  - [ ] مشروع Go خارجي يستطيع تنفيذ SPI دون `internal` imports.
  - [ ] العقود لا تتطلب `pgx` أو `sql.Tx` أو أسماء جداول أو SQL.
  - [ ] ضمانات كل Port موثقة وقابلة للاختبار.

- **ملاحظة التوازي:** يمكن تنفيذ `P1-06` بالتوازي بعد `P1-01`. لا تعدّل هذه المهمة `go.mod` أو سياسة الإصدار؛ نطاقها عقود `pkg/spi` ومحولات الحدود الداخلية فقط.

#### `P1-04` — إعادة بناء SDK Builder على العقود العامة

- **المشكلة التي تحلها:** `EngineBuilder.Build` يتطلب `LedgerApplicationProvider` من Storage Adapter ويكتشف `MasterDataStore()` عبر Type Assertion، فلا يستطيع المستهلك تركيب Adapter مستقل وتشغيل Application Layer التي يوفرها المحرك.
- **الهدف الذي تحققه:** SDK ينشئ Application Services من Public Ports ولا يطلب من التخزين إنشاء كائن تطبيق.
- **نطاق المهمة:** `pkg/sdk/builder.go` و`pkg/sdk/engine.go` والعقود المرتبطة؛ لا تشمل توحيد سياسات Posting كلها.
- **خطوات التنفيذ:**
  1. استبدال Store مركب بـ Dependencies صريحة أو `EngineConfig` موثق.
  2. تنفيذ Preflight Validation لكل Core Dependency قبل أي Initialize.
  3. حذف الاعتماد الإلزامي على `LedgerApplicationProvider` من التخزين.
  4. استبدال Type Assertion المخفي لعقد MasterData بعقد صريح.
  5. جعل Reporting/Governance/Standards اختيارية، ولا تقبل `nil` على أنها مفعلة.
  6. إرجاع أخطاء Build مجمعة ومحددة بالـ Capability والاعتمادية الناقصة.
  7. اختبار أن Build يفشل مبكرًا عند غياب Journal/Period/Reporting Sources المطلوبة.
- **الاعتماديات:** `P1-03`.
- **معايير القبول:**
  - [ ] Builder لا يستدعي `NewLedgerApplication()` من Storage Adapter.
  - [ ] Adapter خارجي يمكن تركيبه من Public Ports فقط.
  - [ ] لا يبدأ Initialize قبل نجاح Preflight كامل.
  - [ ] Core يعمل دون Reporting/Governance إذا لم تطلبا.
  - [ ] غياب Dependency مطلوب ينتج خطأ Build واضحًا.

#### `P1-05` — معالجة Root API وإزالة ازدواجية نقطة الدخول

- **المشكلة التي تحلها:** `engine.go` في الجذر يصدّر أنواعًا مرتبطة بـ `internal` في حين يوجد `pkg/sdk` بوصفه واجهة ثانية.
- **الهدف الذي تحققه:** مدخل منتج عام واحد موصى به وخطة توافق واضحة للواجهة القديمة.
- **نطاق المهمة:** Root API والوثائق وأدوات الفحص؛ لا تشمل تغيير قواعد المحاسبة.
- **خطوات التنفيذ:**
  1. حسم ما إذا كان Root API سيصبح Facade نظيفًا، أو سيُعلن Deprecated، أو ينقل إلى حزمة داخلية.
  2. إن بقي عامًا، استبدال كل توقيع يكشف `internal` بعقد عام.
  3. إن أُهمل، توثيق Deprecation وتحديد إزالة مستقبلية في إصدار MAJOR.
  4. توحيد الأمثلة على `pkg/sdk` بوصفه المدخل الموصى به.
  5. فحص كل `Config` و`Option` و`Port` و`Engine` المصدرة من الجذر.

- **الاعتماديات:** `P1-02`، `P1-04`.
- **معايير القبول:**

  - [ ] لا يكشف نوع عام `internal/*` في حقوله أو توقيعاته.
  - [ ] تغييرات التوافق موثقة.
  - [ ] أمثلة المستهلك لا تستورد Root API القديم إلا بقرار صريح.

#### `P1-06` — تثبيت مسار Go Module وسياسة SemVer

- **المشكلة التي تحلها:** `go.mod` يستخدم `module accounting_engine` ولا يحدد مسار استيراد منشورًا مستقرًا، كما أن `api/v1` وحدها لا تحدد سياسة توافق وحدة Go وSPI.
- **الهدف الذي تحققه:** مسار وحدة رسمي وسياسة إصدار وتوافق تشمل Go API وSPI وProtobuf.

- **خطوات التنفيذ:**

### المرحلة `P2` — توحيد Application Layer وPosting Pipeline

#### `P2-01` — تعريف أوامر ونتائج حالات الاستخدام المحاسبية

- **المشكلة التي تحلها:** واجهات SDK تستقبل `JournalEntry` مباشرة في Post وتقبل `reason string` فقط في العكس. هذا لا يمثل بوضوح هوية المنفذ ومفتاح التكرار ومرجع المصدر وسياسة الموافقة، ويخلط أمر الاستخدام بنموذج القيد المخزن.
- **الهدف الذي تحققه:** Commands/Queries واضحة وثابتة تمثل نية العملية وبياناتها الحوكمية والمحاسبية.
- **نطاق المهمة:** تصميم العقود العامة والاختبارات الأولية فقط؛ لا تشمل التخزين.
- **خطوات التنفيذ:**
  1. تعريف `CreateDraftCommand` و`ValidateEntryCommand` و`PostEntryCommand` و`ReverseEntryCommand` و`GetEntryQuery`.
  2. تضمين `CompanyID` و`ActorID` و`CorrelationID` و`IdempotencyKey` حيث تلزم، مع اعتبار الهوية المدخلة غير موثوقة قبل Authorization.
  3. تعريف `Reason` للعكس منفصلًا عن `ActorID`، وإضافة مرجع وتاريخ فعال عند الحاجة.
  4. تعريف نتائج تحفظ الهوية والحالة والرقم القانوني والتوقيت دون قيم مشتقة مضللة.
  5. توحيد أخطاء Validation/NotFound/Conflict/Unauthorized/Forbidden/PeriodClosed/DuplicateRequest/DependencyUnavailable/Internal.
  6. تعريف الفرق بين `EffectiveDate` و`PostingDate` و`CreatedAt` و`PostedAt` و`ApprovedAt` ومصدر كل قيمة.
- **الاعتماديات:** اكتمال جميع مهام `P1`.
- **معايير القبول:**
  - [ ] لكل عملية عامة Command/Query موثق.
  - [ ] سبب العكس لا يستخدم كهوية منشئ أو مرحّل.
  - [ ] مدخلات النظام المضيف مفصولة عن بيانات المحرك المثبتة.
  - [ ] اختبارات تحقق للمدخلات المطلوبة والاختيارية والتواريخ والمعرفات.

#### `P2-02` — إنشاء Application Layer واحدة لجميع العمليات

- **المشكلة التي تحلها:** `internal/sdkapplication` ينشئ Posting Engine بإعداد أساسي، بينما Root Engine يربط سياسات وموافقات وأبعادًا مالية مختلفة؛ لذلك قد يختلف السلوك حسب نقطة الإنشاء.
- **الهدف الذي تحققه:** Application Service واحدة تنفذ دورة العملية من التحقق حتى التخزين وتستخدمها كل الواجهات.
- **نطاق المهمة:** Create/Read/Validate/Post/Reverse. لا تشمل إعادة بناء IFRS أو Reporting.
- **خطوات التنفيذ:**
  1. اعتماد حزمة تطبيق واحدة؛ إعادة استخدام `internal/sdkapplication` أو نقلها إلى `internal/application` بقرار ADR.
  2. جعلها تعتمد على Public Ports عبر Adapters داخلية.
  3. بناء Pipeline: Context validation، Authorization hook، Input validation، Master Data validation، Policy/Approval، Posting Engine، Audit/Outbox، Result mapping.
  4. منع `cmd` وSDK وIndustry Adapters من استدعاء `posting.Engine` مباشرة.
  5. منع Storage Adapter من تنفيذ قواعد التوازن أو الموافقات أو بناء القيود.
  6. توثيق كل مسار Sequence من API حتى التخزين.
- **الاعتماديات:** `P2-01`.
- **معايير القبول:**
  - [ ] كل مداخل SDK وHTTP وgRPC والأحداث تستدعي Use Cases نفسها.
  - [ ] لا يوجد Posting Engine بتهيئة مستقلة خارج Composition Root.
  - [ ] اختبار Architecture يمنع استيراد `internal/posting` من `cmd` أو `pkg/sdk` مباشرة.
  - [ ] نفس الأمر يعطي قواعد تحقق وأخطاء دلالية متطابقة عبر Transports.

#### `P2-03` — توحيد إعداد Posting Engine والسياسات والموافقات

- **المشكلة التي تحلها:** يتم إنشاء `posting.Engine` بأكثر من موضع، وبعض الإنشاءات لا تربط Policy وApproval وFinancial Dimensions وMaker-Checker.
- **الهدف الذي تحققه:** Composition Root وحيد يحقن ضوابط Posting المطلوبة ويمنع الإعداد الجزئي غير المقصود.
- **نطاق المهمة:** تهيئة Posting Engine والسياسات والأبعاد والموافقات والتدقيق؛ لا تشمل بناء نظام هوية المستخدم.
- **خطوات التنفيذ:**
  1. تعريف `PostingConfig` يحدد سياسات القيد ومتطلبات الأبعاد والفترة والعملة والموافقة وMaker-Checker والتدقيق.
  2. الفصل بين Core Dependencies وCapabilities التي تفعّلها سياسة الشركة.
  3. بناء Factory داخلي وحيد ينشئ Posting Engine ويربط Dependencies.
  4. التحقق عند Build من وجود Approval Port عند اشتراط الموافقة ومصدر أبعاد عند اشتراطها.
  5. منع إنشاء Engine ناقص إذا فشل حقن ضابط مطلوب.
  6. إضافة اختبارات مقارنة بين SDK وHTTP وEvent Ingestion على نفس سياسة الشركة.
- **الاعتماديات:** `P2-02`.
- **معايير القبول:**
  - [ ] مكان واحد فقط لإنشاء Posting Engine.
  - [ ] كل Posting Path يمر بالسياسات نفسها.
  - [ ] السياسة ذات الاعتماد المفقود تفشل في Build لا أثناء الترحيل.
  - [ ] اختبارات تمنع الترحيل عند فشل Approval أو Maker-Checker أو الأبعاد المطلوبة.

#### `P2-04` — إصلاح Mapping بين Public DTOs والنماذج الداخلية

- **المشكلة التي تحلها:** Mapping الحالي يشتق `CreatedAt` من `EffectiveDate`، ويحوّل `PostedBy` إلى `ApprovedBy`، ويولد بعض المعرّفات، كما أن `mustPublicMoney` يخفي خطأ التحويل بإرجاع صفر.
- **الهدف الذي تحققه:** Mapping صريح يحافظ على الهوية والتوقيت والمعنى ولا يخفي أخطاء التحويل.
- **نطاق المهمة:** `internal/sdkapplication/mapping.go` واختباراته وعقود DTO ذات الصلة.
- **خطوات التنفيذ:**
  1. استبدال `mustPublicMoney` بدوال ترجع `(value, error)` ومعالجة كل خطأ.
  2. رفض Entry/Journal/Line IDs المفقودة إذا كانت مطلوبة؛ وعدم توليد Journal ID مشتق لتعويض دفتر غير موجود.
  3. فصل Created/Updated/Posted/Approved Timestamps أو توثيق سياسة مصدر كل واحد.
  4. فصل CreatedBy عن PostedBy وApprovedBy وعدم نسخ حقل إلى آخر.
  5. عدم تحويل ReferenceID إلى SourceEventID إلا وفق صيغة موثقة؛ وإلا يحفظ كمرجع.
  6. توحيد سياسة توليد المعرفات بين SDK وAdapters وقاعدة البيانات.
  7. إضافة round-trip tests لكل الحقول المالية والهوية والتاريخ والحالة والمرجع.
- **الاعتماديات:** `P2-01`.
- **معايير القبول:**
  - [ ] لا تتجاهل Mapping أي خطأ Money أو UUID.
  - [ ] لا تُولد Journal IDs اصطناعية لتعويض نقص البيانات.
  - [ ] حقول الإنشاء والترحيل والاعتماد غير مختلطة.
  - [ ] Round-trip يحافظ على الدلالة دون فقد أو تحويل صامت.
  - [ ] البيانات الإلزامية الناقصة ترفض بخطأ Validation محدد.
- **ملاحظة التوازي:** يمكن تنفيذها بالتوازي مع `P2-03` بعد `P2-01`. لا تعدّل Composition Root أو إعداد Posting Engine؛ نطاقها mapping فقط.

#### `P2-05` — تصحيح عقد العكس وسلامة دورة Reversal

- **المشكلة التي تحلها:** `ReverseEntry` يمرر سبب العكس كهوية منشئ ومرحّل ثم يضيفه إلى الاستجابة بعد التخزين. كما أن إنشاء مسودة العكس منفصل عن معاملة ترحيل العكس الذري، وقد يترك مسودة غير محسومة عند الفشل.
- **الهدف الذي تحققه:** عكس يحمل هوية المنفذ وسببًا دائمًا ومفتاح تكرار ويعطي حالة واضحة عند النجاح والفشل.
- **نطاق المهمة:** `ReverseEntryCommand` وApplication Use Case وReversal Engine/Repository وسجل التدقيق.
- **خطوات التنفيذ:**
  1. استخدام ActorID وReason منفصلين مع تحقق سياسة السبب.
  2. حفظ السبب والفاعل والوقت والمرجع ومفتاح العملية بصورة دائمة.
  3. حسم ذرية العملية: إنشاء المسودة والتحقق والترحيل والربط بمعاملة واحدة، أو حالة وسيطة موثقة قابلة للاستعادة دون تكرار.
  4. منع عكس فعال ثانٍ للقيد الأصلي بقيد DB أو قفل/تفرد موثق.
  5. التحقق من انعكاس كل سطر في الحساب والعملة الوظيفية وعملة المعاملة وسعر الصرف والأبعاد حسب السياسة.
  6. جعل Idempotency Key نفسه يعيد النتيجة ذاتها، والمفتاح نفسه بحمولة مختلفة ينتج Conflict.
  7. حقن فشل بعد إنشاء المسودة والسطور وقبل تحديث الأصل وبعد الترحيل وقبل الاستجابة.
- **الاعتماديات:** `P2-02`، `P2-04`.
- **معايير القبول:**
  - [ ] ActorID مستقل تمامًا عن Reason.
  - [ ] السبب محفوظ ويمكن استرجاعه بعد Restart.
  - [ ] لا يمكن إنشاء عكس ثانٍ تحت التزامن.
  - [ ] الفشل لا يترك الأصل والعكس في حالتين متعارضتين.

### المرحلة `P3` — استقلال التخزين والتكافؤ وإثبات Adapter خارجي

- **خطوات التنفيذ:**
  1. تنفيذ Public Ports الجديدة عبر Adapter داخل Postgres.
  2. تجميع كتابة القيد وتسلسله والأرصدة وحالة القيد والتدقيق وIdempotency داخل حدود المعاملة المطلوبة.
  3. مراجعة أقفال Journal/Entry/Account وترتيبها ومستوى العزل.
  4. مراجعة Foreign Keys وUnique/CHECK Constraints وTriggers لحماية Balance Integrity من مسارات الكتابة البديلة.
  5. استخدام Context-aware queries وإلغاء الاستعلامات عند انتهاء Context.
  6. ضبط Company/Actor context محليًا داخل كل معاملة ومنع التسرب عبر pooled connections.

- **معايير القبول:**

  - [ ] SDK والحزم العامة لا تستورد PostgreSQL.
  - [ ] فشل جزء من Atomic Posting يؤدي إلى Rollback لكل آثاره.
  - [ ] القيود والمشغلات تحمي Balance Integrity من الكتابة غير المباشرة.
  - [ ] اختبارات RLS تثبت عدم تسرب Company Context عبر Pool.
- **ملاحظة التوازي:** بعد `P3-01` يمكن تنفيذ `P3-03` و`P3-04` و`P3-05` بالتوازي. لا تعدّل هذه المهمة SPI أو Memory أو Test Harness المشترك؛ تقتصر على `storage/postgres` وmigrations.

#### `P3-03` — مواءمة Memory مع نفس العقود وخصائص السلوك

- **المشكلة التي تحلها:** Memory لا يضمن تلقائيًا نفس دلالات المعاملات والتفرد والعزل والتكرار التي يوفرها PostgreSQL، ولا يثبت Durability.
- **الهدف الذي تحققه:** Memory يحقق Public SPI نفسها ويستخدم لاختبارات التطبيق السريعة، مع توثيق ما لا يستطيع محاكاته.
- **نطاق المهمة:** `storage/memory` واختبارات العقود فقط؛ لا يستخدم Memory كدليل صلاحية إنتاجية.
- **خطوات التنفيذ:**
  1. تنفيذ Public Ports نفسها التي ينفذها PostgreSQL.
  2. تطبيق Atomic Mutation/locking بحيث لا تتسرب حالة جزئية عند فشل callback.
  3. جعل مفاتيح Idempotency مركبة حسب Company Scope وKey مع مطابقة Payload Hash.
  4. تعريف سياسة ترتيب المعرفات والتسلسل للمقارنة.
  5. توثيق أن Memory لا يثبت Durability أو RLS أو سلوك PostgreSQL.
  6. تشغيل Contract Tests نفسها دون نسخ منطق الاختبار أو تخفيف الشروط.
- **الاعتماديات:** `P3-01`.
- **معايير القبول:**

  - [ ] جميع Contract Tests المشتركة تمر على Memory.
- **ملاحظة التوازي:** لا تعدّل `storage/postgres` أو العقود العامة أو Test Harness المشترك أثناء عمل `P3-02` و`P3-05`؛ أضف تنفيذ Memory فقط.

#### `P3-04` — جعل Event Idempotency دائمة وذرية

- **المشكلة التي تحلها:** fallback الذاكرة يستخدم مفتاحًا لا يتضمن Company Scope ولا يثبت مقارنة Payload Hash، بينما يلزم ربط حجز المفتاح بالترحيل والنتيجة بشكل ذري.
- **الهدف الذي تحققه:** منع تكرار قيد الحدث عبر إعادة تشغيل الخدمة والتزامن وإعادة المحاولة.
- **نطاق المهمة:** Event Ingestion وPublic Idempotency Port وتنفيذات Postgres/Memory.
- **خطوات التنفيذ:**
  1. تعريف مفتاح فريد مركب من Tenant/Company Scope وIdempotency Key ومصدر الحدث عند الحاجة.
  2. حساب Canonical Payload Hash للحقول المؤثرة محاسبيًا مع Version للتطبيع.

  4. جعل حجز المفتاح وحفظ القيد والنتيجة النهائية ضمن Transaction Boundary واحدة في PostgreSQL.
  5. المفتاح نفسه والحمولة نفسها يعيد النتيجة؛ والحمولة المختلفة تنتج Conflict؛ والعملية الجارية تتبع سياسة انتظار واضحة.

- **الاعتماديات:** `P3-01`، `P2-06`.
- **معايير القبول:**

  - [ ] اختلاف Payload لنفس المفتاح ينتج Conflict.
  - [ ] السجل والنتيجة يظلان متسقين بعد نقاط الفشل المحقونة.

- **المشكلة التي تحلها:** Transaction Currency وFunctional Amount في القيد لا تعني دعم المحاسبة متعددة العملات كاملة؛ يجب فصل عملة المعاملة عن العملة الوظيفية وعملة العرض ومعالجة فروق الصرف والترجمة.
- **الهدف الذي تحققه:** نموذج عملات وسياسات تقييم وتحويل متسق مع نطاق واضح من IAS 21.
- **نطاق المهمة:** `internal/types` و`internal/valuation` و`internal/reporting/currency_translation.go` والعقود العامة؛ لا تشمل Consolidation كاملًا.
- **خطوات التنفيذ:**
  1. توثيق Transaction Currency وFunctional Currency وPresentation Currency ومصدر تحديد العملة الوظيفية.
  2. تحديد أنواع أسعار الصرف: تاريخ المعاملة، الإقفال، المتوسط عند السماح، مع سبب الاستخدام.
  3. تحديد مصدر السعر وتاريخه واتجاهه ودقته والتقريب، وحفظ السعر التاريخي المستخدم لإعادة إنتاج النتائج.
  4. تنفيذ فروق الصرف المحققة وغير المحققة ضمن نطاق الإصدار، وتحديد حسابات الربح/الخسارة أو الاحتياطي.
  5. فصل تحويل مبلغ سطر القيد عن ترجمة القوائم إلى Presentation Currency.
  6. تحديد نطاق ترجمة العمليات الأجنبية وربطه بـ Consolidation عند الحاجة.
  7. بناء Golden Scenarios للشراء والبيع والسداد وإعادة التقييم وترجمة القوائم.
  8. مراجعة الحالات مع النص الرسمي الحالي لـ IAS 21 ومحاسب مؤهل.
- **الاعتماديات:** `P4-01`، `P4-02`.
- **معايير القبول:**
  - [ ] لا تُستخدم عملة العرض كمرادف للعملة الوظيفية.
  - [ ] لكل تحويل سعر ومصدر وتاريخ وسياسة تقريب قابلة للتتبع.
  - [ ] فروق الصرف تعالج وفق السيناريو المعتمد.
  - [ ] يمكن إعادة إنتاج نتائج التحويل التاريخية.
  - [ ] Compliance Matrix توضح المدعوم وغير المدعوم من IAS 21.

#### `P4-04` — تدقيق Reversal محاسبيًا واختبار دورة العكس الكاملة

- **المشكلة التي تحلها:** وجود دالة عكس وربط بين قيدين لا يثبت صحة العكس في كل الحالات؛ يجب تدقيق العملات والتواريخ والأبعاد والمرجع والسبب ومنع التكرار.
- **الهدف الذي تحققه:** مواصفة عكس محاسبي قابلة للتدقيق ومتوافقة مع سياسات المؤسسة ودورة Posting.
- **نطاق المهمة:** `internal/posting/reversal*` وApplication Reversal وSQL constraints؛ لا تشمل شاشة العكس.
- **خطوات التنفيذ:**
  1. تحديد ما إذا كانت الحسابات والأبعاد الأصلية تُحفظ أو تسمح الاستثناءات بموافقة.
  2. تحديد تاريخ العكس: الأصل أو فترة لاحقة مفتوحة أو تاريخ يختاره المستخدم ضمن السياسة.
  3. التحقق من انعكاس Debit/Credit بالمبالغ الوظيفية ومبالغ المعاملة وفق سياسة العكس.
  4. تحديد أثر العكس على Reconciled Amount وMatching Number وSubledger Links وAttachments.
  5. منع عكس Draft أو قيد معكوس أو قيد خارج Company Context.
  6. ربط العملية بسجل دائم يحفظ الفاعل والسبب والوقت والمرجع.
  7. اختبار العكس بعد إقفال الفترة وفي فترة لاحقة وتحت التزامن وفشل خطوة وسطية.
- **الاعتماديات:** `P2-05`، `P3-06`.
- **معايير القبول:**
  - [ ] كل حالة عكس لها نتيجة متوقعة موثقة.
  - [ ] الأثر الصافي للأصل والعكس يساوي الصفر وفق العملة والسياسة المحددتين.
  - [ ] لا يمكن العكس مرتين تحت التزامن.
  - [ ] تفاصيل العكس قابلة للاسترجاع بعد Restart.
  - [ ] بوابات سلامة المعاملة تعمل على PostgreSQL.

#### `P4-05` — استكمال ضوابط Subledgers وControl Accounts وReconciliation

- **المشكلة التي تحلها:** وجود Receivables وPayables وFixed Assets وTreasury وReconciliation داخليًا لا يثبت اتصالها بالأستاذ العام أو مطابقة أرصدتها أو اكتمال واجهاتها.
- **الهدف الذي تحققه:** ربط واضح بين الأستاذ العام والأستاذ المساعد، مع كشف الفروقات ومنع عدم الاتساق.
- **نطاق المهمة:** `internal/subledgers` و`internal/reconciliation` وReporting Contracts والتخزين؛ لا تشمل بناء مبيعات/مشتريات كاملة.
- **خطوات التنفيذ:**
  1. حصر كل Subledger وتصنيف حالته: مكتمل ضمن نطاق، جزئي، غير موصول، أو غير منفذ.
  2. تعريف Control Account وربط كل حركة فرعية بأثر GL قابل للتتبع.
  3. تعريف قواعد تطابق تفاصيل Subledger مع Control Account في التاريخ والعملة نفسيهما.
  4. تعريف حالات Matching/Unmatched/Disputed/Resolved مع Actor وReason.
  5. جعل الفرق ينتج Exception أو قيد تسوية من Posting الرسمي، لا تصحيحًا صامتًا.
  6. توحيد الحدود المعاملاتية بين الحركة الفرعية والقيد أو Outbox قابل للاستعادة.
  7. إضافة Golden Scenarios للذمم والأصول والخزينة والبنوك حسب الوحدات الموجودة.
- **الاعتماديات:** `P3-07`، `P4-02`.
- **معايير القبول:**
  - [ ] لكل Subledger نطاق وعقد ربط مع GL.
  - [ ] يمكن إعادة احتساب Control Account ومقارنته بالتفاصيل.
  - [ ] كل فرق ينتج Exception قابلة للتتبع.
  - [ ] لا تترك حركة فرعية أثرًا غير قابل للاستعادة في GL.

#### `P4-06` — استكمال الإقفال المالي وإعادة الفتح

- **المشكلة التي تحلها:** التحقق من أن الفترة مفتوحة عند الترحيل لا يمثل دورة إقفال تشمل القيود المعلقة والتسويات والمطابقات والتقييمات والتقارير.
- **الهدف الذي تحققه:** Period Close منظمة وقابلة للتدقيق مع شروط منع الإقفال وإعادة الفتح.
- **نطاق المهمة:** `internal/reporting/closing_engine.go` وPeriod Services وAudit/Approval؛ لا تشمل تنفيذ كل التسويات المعيارية تلقائيًا.
- **خطوات التنفيذ:**
  1. تحديد Pre-Close Checks: Draft Entries، موافقات معلقة، أحداث غير معالجة، فروقات Subledger وحسابات مؤقتة.
  2. تعريف Close Checklist بنتائج Pass/Warning/Blocker مع أدلة.
  3. تنفيذ Closing Command عبر Application Layer مع قفل يمنع Posting المتزامن أثناء الإقفال.
  4. تعريف قيود الإقفال/التدوير وسياسة إعادة فتح الفترة التالية.
  5. فصل صلاحيات الإقفال وإعادة الفتح مع Reason وApproval وAudit.
  6. اختبار الفشل قبل/بعد الاعتماد ومحاولة Posting بالتزامن ومحاولة Reopen دون صلاحية.
- **الاعتماديات:** `P4-02`، `P4-05`.
- **معايير القبول:**
  - [ ] لكل فترة Close Checklist قابلة للتشغيل والتقرير.
  - [ ] لا تُغلق الفترة مع Blocker غير معالج.
  - [ ] لا يقبل Posting أثناء انتقال قفل الفترة النهائي.
  - [ ] Reopen يتطلب صلاحية وسببًا وسجلًا دائمًا.
  - [ ] تقارير الفترات المقفلة قابلة لإعادة الإنتاج.

#### `P4-07` — مراجعة Financial Reporting وسلامة القوائم

- **المشكلة التي تحلها:** وجود TB وGL وBS وIS لا يثبت تصنيف الحسابات والعرض والمقارنات والإيضاحات وترجمة العملات وربط الأرقام بالمصدر.
- **الهدف الذي تحققه:** تقارير قابلة للتتبع من القوائم إلى الأستاذ العام وبنطاق عرض/إفصاح موثق.
- **نطاق المهمة:** `internal/reporting` و`pkg/api/v1/reporting` وReporting Adapters؛ لا تشمل إفصاحًا شاملاً دون تحديد نطاقه.
- **خطوات التنفيذ:**
  1. تعريف Taxonomy للحسابات إلى أصول والتزامات وحقوق ملكية وإيرادات ومصروفات.
  2. بناء Reconciliation من TB إلى BS وIS وتفسير الحسابات غير المصنفة والمستبعدة.
  3. التحقق من اتساق Net Income مع حركة حقوق الملكية وفق النموذج المعتمد.
  4. إضافة المقارنات وسياسات العرض والعملات والتقريب وSign Conventions.
  5. ربط كل مبلغ بحساباته وقيوده وفترته وسعر الصرف المستخدم.
  6. توثيق متطلبات العرض والإفصاح المدعومة وغير المدعومة وعدم تسمية تقرير ناقص «IFRS Financial Statements».
  7. اختبار الحسابات غير المصنفة والأرصدة غير الطبيعية والفترات المقارنة وتغير السياسات.
- **الاعتماديات:** `P4-03`، `P4-05`، `P4-06`.
- **معايير القبول:**
  - [ ] TB متوازن وفق تعريف التقرير والعملة والفترة.
  - [ ] كل مبلغ قابل للتتبع إلى GL ومصدره.
  - [ ] القوائم تتصالح مع الأستاذ العام وفق القواعد المعتمدة.
  - [ ] لا تُخفى الحسابات غير المصنفة أو فروق التقريب.
  - [ ] نطاق التقارير مراجع محاسبيًا وموثق.

#### `P4-08` — اعتماد Golden Accounting Scenarios ومراجعة محاسبية مستقلة

- **المشكلة التي تحلها:** الاختبار قد يثبت أن الكود ينفذ القاعدة المكتوبة له، لكنه لا يثبت أن القاعدة صحيحة محاسبيًا أو أن الحالات تغطي المعيار.
- **الهدف الذي تحققه:** مرجع قابل للتكرار يحدد الوقائع والقيود والأرصدة والتقارير والأسباب المعيارية لكل حالة.
- **نطاق المهمة:** Golden Scenarios للنواة والعملات والعكس والإقفال والتقارير وSubledgers؛ لا تصادق على معايير غير منفذة.
- **خطوات التنفيذ:**
  1. اختيار سيناريوهات تجارية وخدمية وصناعية/زراعية دون إدخال منطق القطاع في Core.
  2. لكل حالة، كتابة الواقعة والسياسة والحقائق والقيود والأرصدة المتوقعة بعد كل خطوة.
  3. ربط السيناريو المعياري بمتطلب من النص الرسمي الساري مع الإصدار وتاريخ التطبيق والنطاق والاستثناءات.
  4. مراجعة النتائج من محاسب مؤهل مستقل عن مبرمج القاعدة وتسجيل القرارات.
  5. تحويل الحالات المعتمدة إلى Fixtures واختبارات PostgreSQL ومقارنات Adapters.
  6. منع تغيير Golden Output دون قرار محاسبي موثق وتحديث الاختبار.
- **الاعتماديات:** `P4-01` إلى `P4-07` (اكتمال جميع مهام P4 الأخرى).
- **معايير القبول:**
  - [ ] Golden Scenario لكل وظيفة يراد اعتمادها.
  - [ ] لكل حالة مدخلات وقيود وأرصدة وتقارير متوقعة.
  - [ ] المتطلبات المعيارية مرتبطة بنص رسمي وإصدار ونطاق.
  - [ ] مراجعة محاسبية موثقة لا تعتمد على نجاح الاختبار وحده.
  - [ ] الحالات تعمل على PostgreSQL وتقارن مع Memory/Adapter خارجي حيث ينطبق.

### المرحلة `P5` — Bootstrap وCapabilities والوحدات الاختيارية

#### `P5-01` — بناء Module Registry وDependency Graph

- **المشكلة التي تحلها:** `StandardModule` يعرّف Dependencies بأسماء وحدات، ولا توجد إدارة موحدة للنسخ والقدرات والتبعيات الدائرية وترتيب التهيئة والإغلاق.
- **الهدف الذي تحققه:** Registry يحل الاعتماديات ويحدد التوافق والإصدارات قبل التهيئة.
- **نطاق المهمة:** `pkg/spi/standards` و`pkg/sdk/builder.go` والحزم الداخلية اللازمة؛ لا تشمل تنفيذ IFRS.
- **خطوات التنفيذ:**
  1. تعريف Descriptor يحوي Name وVersion وRequires وProvides وCompatibility وLifecycle Metadata.
  2. اعتماد معرف ثابت للوحدة لا يعتمد على الاسم البشري وحده.
  3. بناء Dependency Graph وكشف Missing/Duplicate/Version Conflict/Cycle.
  4. ترتيب التهيئة Topologically.
  5. جعل Registry يكتشف Capabilities المعلنة دون Type Assertions غير موثقة.
  6. توفير Engine Diagnostics يوضح الفعال والمعطل وسبب الحالة.
- **الاعتماديات:** اكتمال جميع مهام `P1` و`P2`.
- **معايير القبول:**
  - [ ] كشف التبعيات المفقودة والمكررة والدائرية قبل Initialize.
  - [ ] ترتيب Initialize/Close حتمي.
  - [ ] لكل وحدة اسم ثابت وإصدار وقدرات معلنة.
  - [ ] يمكن الاستعلام عن Capabilities الفعالة وأسباب غياب غير الفعالة.

#### `P5-02` — تنفيذ Capability Preflight وFeature Dependency Validation

- **المشكلة التي تحلها:** يمكن إعداد Reporting/Governance بقيم ناقصة أو `nil`، ولا يتحقق Builder دائمًا من مصادر البيانات المطلوبة.
- **الهدف الذي تحققه:** لا تُفعّل ميزة إلا مع اكتمال اعتمادياتها، وإلا يفشل Build مبكرًا برسالة دقيقة.
- **نطاق المهمة:** Builder وRegistry وعقود Capability؛ لا تشمل تنفيذ بيانات التقارير أو المعايير.
- **خطوات التنفيذ:**
  1. تحديد Core مقابل Optional Capabilities لكل خدمة.
  2. جعل Reporting يعلن مصادر كل تقرير: Ledger Read Model وAccount Classification وCurrency Translation عند الحاجة.
  3. جعل Governance يعلن Audit Store وApproval Store وFingerprint Store وفق الوظائف المطلوبة.
  4. جعل Standards Module يعلن Master Data وPosting وValuation وReporting dependencies.
  5. تنفيذ Preflight Validation قبل Initialize وإظهار جميع النواقص معًا.
  6. منع Capability فعالة بواجهة `nil` أو Port لا يحقق العقد.
  7. إصدار Config Snapshot يوضح الميزات والاعتماديات المحققة.
- **الاعتماديات:** `P5-01`.
- **معايير القبول:**
  - [ ] Reporting لا يعمل عند غياب مصادر البيانات المطلوبة.
  - [ ] Governance لا يظهر فعالًا دون مخازنه المطلوبة.
  - [ ] الوحدة تفشل قبل Initialize إذا غابت Dependency معلنة.
  - [ ] لا توجد `nil` تفسر على أنها Capability مفعلة.

#### `P5-03` — تنفيذ Lifecycle آمن مع Rollback وScheduled Jobs

- **المشكلة التي تحلها:** قد تبقى آثار تهيئة جزئية إذا فشلت وحدة بعد تهيئة أخرى؛ و`RunScheduledJobs` موجود في العقد دون مسار تشغيل موحد واضح.
- **الهدف الذي تحققه:** تهيئة وإغلاق آمنان وتشغيل مجدول مضبوط وتنظيف عند فشل Bootstrap.
- **نطاق المهمة:** Module Lifecycle وEngine Close وScheduler Integration؛ لا تشمل بناء Scheduler موزع إلا بقرار مستقل.
- **خطوات التنفيذ:**
  1. تهيئة الوحدات حسب Dependency Order وتسجيل الوحدات التي نجحت.
  2. عند الفشل، إغلاق ما تمت تهيئته بترتيب عكسي وتجميع أخطاء الإغلاق.
  3. جعل `Engine.Close` idempotent ويحترم Context/Deadline.
  4. تعريف Scheduler Port وتوقيت الوظائف ومنع تكرار التنفيذ عبر أكثر من نسخة.
  5. تعريف Job Execution Record/Idempotency للوظائف ذات الأثر المحاسبي.
  6. اختبار Init Failure وClose Failure وCancellation وDuplicate Job Execution.
- **الاعتماديات:** `P5-01`.
- **معايير القبول:**
  - [ ] أي فشل Bootstrap ينظف الموارد التي تمت تهيئتها.
  - [ ] `Close` آمن عند الاستدعاء المتكرر.
  - [ ] لكل Job سياسة Idempotency وتزامن.
  - [ ] لا تعمل Jobs قبل جاهزية Core Dependencies.

#### `P5-04` — إعادة تعريف Standard Module وحدود الادعاء المعياري

- **المشكلة التي تحلها:** وحدات `modules/ifrs15` و`ifrs16` و`ifrs9` و`ias12` تسجل قواعد ثابتة، ولا توصل بالضرورة محركات `internal/*`؛ فيبدو الاسم أوسع من التنفيذ الفعلي.
- **الهدف الذي تحققه:** عقد معياري يفصل تسجيل القواعد عن Workflow المحاسبي ويعلن النطاق والإصدار والاعتماديات والمخرجات.
- **نطاق المهمة:** `pkg/spi/standards` و`modules/*` ووثائق الامتثال؛ لا تشمل تنفيذ المعايير كلها هنا.
- **خطوات التنفيذ:**
  1. تعريف Standard Profile: Standard Name/Edition/Amendments/Effective Date/Jurisdiction/Supported Requirements/Exclusions.

  4. منع إنتاج القيد قبل اكتمال القياس والتحقق من البيانات اللازمة.
  5. إلزام كل قاعدة تنتج قيدًا بدفتر يومية حقيقي أو Mapping مطلوب، دون UUID اصطناعي.
  6. إنشاء Compliance Matrix تربط كل متطلب بالتنفيذ والاختبار والحالة.
- **الاعتماديات:** `P5-02`، `P5-03`.
- **معايير القبول:**
  - [ ] كل وحدة تعلن إصدار المعيار وتاريخ النفاذ والنطاق والاستثناءات.
  - [ ] لا تنتج الوحدة قيدًا بلا Journal Mapping حقيقي.
  - [ ] لا يوحي الاسم أو التوثيق بامتثال أوسع من التنفيذ.
  - [ ] كل Requirement له Implementation Reference وTest Evidence أو حالة غير منفذ.

#### `P5-05` — ربط IFRS 15 ضمن نطاق معتمد

- **المشكلة التي تحلها:** قاعدة `IFRS15_REVENUE_RECOGNITION` الثابتة لا تمثل نموذج الاعتراف بالإيراد كاملًا، ووجود `internal/ifrs15` لا يثبت تشغيله عبر Module العام وSDK.
- **الهدف الذي تحققه:** Workflow اختياري للإيراد ينفذ متطلبات محددة ويولد الأثر عبر Application Layer.
- **نطاق المهمة:** `internal/ifrs15` و`modules/ifrs15` وعقودها. لا تشمل إدارة المبيعات أو الفوترة.

- **المشكلة التي تحلها:** HTTP/gRPC لا يربطان الطلب بهوية موثقة وتفويض على الشركة والعملية؛ `company_id` القادم في الطلب ليس مصدرًا موثوقًا للصلاحية.

## 5. بوابات الإصدار الإلزامية (Release Gates)

لا تُحسب هذه البوابات ضمن مجموع النقاط الموزون ولا يمكن تعويض فشلها بدرجات مرتفعة في محاور أخرى.

| البوابة | شرط النجاح | المهام التي تثبتها |
| --- | --- | --- |
| G1 — Double Entry Integrity | لا يمكن إنشاء/ترحيل قيد غير متوازن، وتتطابق حركة الأستاذ مع الأرصدة حسب العملة والسياسة. | `P4-01`، `P4-08` |
| G2 — Atomic Posting | القيد والسطور والتسلسل والأرصدة والتدقيق وIdempotency لا تترك حالة جزئية بعد الفشل. | `P3-02`، `P3-04`، `P3-06` |
| G3 — Reversal Integrity | العكس كامل وموثق وغير مكرر ولا يترك الأصل والعكس متعارضين. | `P2-05`، `P4-04` |
| G4 — External Consumption | مستهلك مستقل يستخدم Public API/SPI دون `internal` أو معرفة SQL/PostgreSQL أو `posting.Engine`. | `P1-03`، `P1-04`، `P3-05`، `P7-01` |
| G5 — Infrastructure Independence | Core Scenarios متكافئة عبر PostgreSQL وMemory وExternal Adapter مع توثيق حدود المحاكاة. | `P3-07`، `P7-01` |
| G6 — Company Isolation | لا يمكن لمستخدم/شركة الوصول إلى بيانات شركة أخرى مع تزوير Company ID أو إعادة استخدام الاتصال. | `P6-02`، `P6-03` |
| G7 — Production Safety | لا يبدأ Production على Memory افتراضيًا ولا يعمل دون إعدادات التخزين والأمان المطلوبة. | `P6-01`، `P7-03` |
| G8 — Accounting Scope Honesty | كل ادعاء معياري مرتبط بنطاق ومتطلبات وأدلة ومراجعة؛ لا توجد دعوى IFRS عامة غير مثبتة. | `P4-08`، `P5-04` إلى `P5-09`، `P7-05` |

## 6. تعريف الإنجاز النهائي

لا يعد Accounting Engine جاهزًا كمنتج مستقل إلا عند تحقق جميع النقاط التالية:

1. يستطيع مشروع Go خارجي استيراد الإصدار واستخدام SDK دون استيراد `internal` أو كتابة SQL خاص بالمحرك.
2. يستطيع المستهلك تنفيذ Storage Adapter من Public SPI، بينما يبقى Application Layer وPosting Pipeline داخل المحرك.
3. تمر كل العمليات عبر Application Layer موحدة وبإعداد Posting موحد وسياسات وموافقات وتدقيق متسق.
4. لا توجد تحويلات صامتة للهوية أو العملة أو التاريخ أو المراجع، ولا تُنشأ Master Data اصطناعية لتعويض نقص البيانات.
5. تثبت اختبارات PostgreSQL الذرية والتزامن وإعادة المحاولة والعكس وIdempotency سلامة النتائج بعد الفشل وRestart.
6. Reporting وGovernance وIFRS/IAS اختيارية حقًا ولا تتفعل دون Dependencies، ونطاق كل وحدة موثق.
7. ينجح اختبار لقطاع تجاري وزراعي وصناعي/خدمي دون تغيير Core Ledger.
8. الخدمة محمية بالمصادقة والتفويض وعزل الشركات، مع Readiness وObservability وBackup/Restore مجرب.
9. توجد Golden Accounting Scenarios ومراجعة محاسبية موثقة لكل نطاق يُعلن دعمه.
10. جميع Release Gates من G1 إلى G8 مجتازة، ويوجد تقرير Go/No-Go وARD لكل مهمة منفذة.

## 7. القرارات التي يجب حسمها قبل التنفيذ

هذه ليست مهامًا مخفية؛ بل قرارات يجب أن تُحسم في P0 أو تسجل ضمن ADR:

- عنوان Go Module الرسمي الذي سيحل محل `module accounting_engine`.
- هل سيُحافظ على Root API كواجهة توافقية أم يُهمل لصالح `pkg/sdk`؟
- هل الإصدار الأول Library فقط أم Library وخدمة HTTP/gRPC معًا؟ يجب فصل أمن المكتبة عن أمن الخدمة.
- النطاق المعياري الدقيق المراد دعمه في الإصدار الأول لكل معيار IAS/IFRS.
- هل Memory أداة اختبار فقط أم مسموح استخدامه بتطبيقات تجريبية؟ لا يوصى به لتشغيل مالي إنتاجي.
- آلية هوية المستخدم والشركة التي يوفرها النظام المضيف ومسؤولية المحرك في Authorization.
- متطلبات الاحتفاظ بالتدقيق والنسخ الاحتياطي والتعافي.
- قواعد العملة الوظيفية وعملة العرض وسياسة التقريب ومصدر أسعار الصرف لكل شركة.

## 8. طريقة متابعة التنفيذ

1. عند بدء المهمة، غيّر حالتها إلى `قيد التنفيذ` بعد التأكد من إغلاق اعتمادياتها ووجود ARD لمهام الاعتماد.
2. لا تعدّل ملفات خارج نطاق المهمة؛ أي اكتشاف جانبي يسجل في ARD كـ Finding أو مهمة لاحقة.
3. استخدم الاختبارات القائمة وأضف اختبارًا يثبت معيار القبول. لا يكفي `go test ./...` إذا كان المطلوب PostgreSQL أو Adapter خارجيًا أو مراجعة محاسبية.
4. سجل الأوامر والنتائج والبيئة وCommit Hash في ARD.
5. عند فشل معيار قبول، تبقى المهمة `قيد التنفيذ` أو تعاد `معلقة` ولا تنشئ ARD نهائيًا على أنها منفذة.
6. بعد تحقق كل معيار، أنشئ `docs/ard/ARD-<task-id>.md` ثم حدّث الحالة إلى `منفذة` وأضف مسار التقرير.
7. لا تبدأ مرحلة لاحقة اعتمادًا على اكتمال الكود فقط؛ يلزم اكتمال ARDs لكل مهام المرحلة.

## 9. المراجع الفنية أثناء التنفيذ

- **Go Modules:** وثائق Go الرسمية لتنظيم الوحدات والحزم وحدود `internal` وإصدارات Go Modules.
